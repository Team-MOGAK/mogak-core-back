목표구조결정검증이해 점검

목표와 비목표

목표: Nest monorepo의 libs/core와 libs/modules library를 만든다. 현 apps/api/src/core는 libs/core로, 현 apps/api/src/infrastructure와 기존 provider 조립은 libs/modules로 이동한다. apps/api/src/api/<feature>에는 controller·guard·request/response type을 둔다.

비목표: HTTP route·request/response·오류 계약 변경, DB schema/FK migration, 탈퇴 정책 및 잠금 정책 변경, Job/Cloud Tasks 도입, 저장소 로직 개선을 이 리팩터링에 섞지 않는다.

결정(제안): Nest 교체 가능성이 낮아 adapter를 순수 TypeScript로 재작성하지 않는다. 대신 이미 Nest 독립적인 domain/application/port는 libs/core에 유지하고, Nest DI를 쓰는 repository·DB·인증/storage adapter와 service provider 조립은 libs/modules로 옮긴다. API feature module은 새로 만들지 않는다. API의 AppModule이 controller·guard를 등록하고 libs/modules의 기능 module을 import한다.

결정과 불변 조건

  1. nest-cli.json을 Nest monorepo workspace로 전환하고 libs/core·libs/modules를 library project로 등록한다. 허용 의존은 apps/api → libs/core, apps/api → libs/modules, libs/modules → libs/core뿐이며 역방향·순환 import는 금지한다.
  2. root build는 core → modules → API 순서로 실행하며, 실행 entrypoint는 기존처럼 API의 main.ts가 소유한다.
  3. core는 port/service/domain type을 export한다. modules는 기존 repository·DB·인증 adapter와 Nest feature module을 export한다. root AppModule이 controller·guard를 등록하고 modules feature module을 import한다. 기존 @infra/*·@core/* alias는 각 library alias로 치환한다.
  4. 현재 API module별 provider 그래프(Auth, Users, Mogak, Post, Social, Storage)는 유지한다. controller의 route와 request/response mapping은 이동만 하며 의미를 바꾸지 않는다.
핵심 위험: 물리 이동 중 circular import 또는 DI token identity가 달라지면 Nest가 provider를 해석하지 못하거나 런타임에 다른 instance를 주입할 수 있다. token은 core가 단일 export하고, adapter/service binding은 modules feature module에 집중하며 API는 해당 module만 import한다.

실패·복구: 단계별 build/typecheck와 기능별 controller 테스트로 첫 실패 경계를 찾는다. import/DI 실패는 해당 feature 이동 커밋 안에서 경로·export·provider binding만 되돌려 복구하며, route/DB migration 변경으로 우회하지 않는다.

검토한 대안

apps/api/src 내부 폴더 이동만 수행
논리 정리만 되고 HTTP 배포물과 core가 물리 분리되지 않아 기각.
repository·DB를 API에 남김
향후 Job이 API 내부 구현을 재사용하게 되어 이슈의 재사용 목표를 충족하지 못해 기각.
바로 Job 앱도 추가
실행 환경·운영 계약이 추가되는 범위 확대이므로 후속으로 분리.

구조 결정 점검

결정(제안)
API feature module을 추가하지 않고 AppModule이 controller·guard를 등록하며 modules feature module을 import한다.
근거·가정
현재 controller 수와 API feature 수는 root module이 관리 가능한 수준이며, HTTP feature별 module이 실제로 제공하는 추가 격리가 없다.
이 결론이 실패한다면
API controller·guard의 feature 수가 늘어 AppModule이 의존성 목록을 이해하기 어렵게 되는 경우다. 그때만 해당 feature에 AuthHttpModule을 추가한다.
미룬 범위·재검토 조건
API feature module 생성은 미룬다. controller/guard 조립이 feature별로 복잡해지거나 두 번째 HTTP adapter가 생기면 재검토한다.
