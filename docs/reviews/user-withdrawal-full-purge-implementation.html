회원 탈퇴 전체 삭제 구현 기록

설계 기준: user-withdrawal-full-purge-design.html

  • 탈퇴 성공 계약을 204 No Content로 변경하고 본문을 제거한다.
  • AuthRepository가 관련 사용자 lock union을 먼저 획득한 뒤, set-based SQL로 모든 회원 소유/작성 관계를 자식부터 삭제한다.
  • 공통 transaction advisory lock helper를 만들고 Auth, User, Consent, Mogak, Post, Social의 mutation에 적용한다.
  • 삭제 및 HTTP 계약 테스트로 회귀를 확인한다.

승인된 추가 범위

2026-08-23 승인: 탈퇴 cascade의 raw DELETE USING과 테이블명 SQL을 Drizzle query builder/subquery로 교체했다. lock 대상 조회는 Drizzle typed CTE target_posts 하나를 재사용하는 단일 SQL로 합쳤다. 또한 advisory lock 후 중복 hierarchy join을 PK 존재 재확인으로 축소했다. HTTP 204, 도메인 오류, transaction 및 lock 집합은 유지한다.

재승인 구현 범위

2026-08-23 승인: 모든 mutation에 삽입한 transaction advisory lock은 탈퇴 동시성의 수단으로 사용하지 않는다. 탈퇴 transaction이 users 및 삭제 트리 부모 행을 FOR UPDATE로 선점하고, FK 참조의 KEY SHARE 대기와 삭제 대상 재계산으로 경합을 처리한다. 필요한 인덱스 migration과 두 connection 경합 통합 테스트를 포함한다.

구현 결과

AuthRepository.deleteUser는 users, modarat, mogak, jogak, schedules, post를 부모부터 FOR UPDATE로 선점한 뒤 삭제 대상을 다시 계산한다. daily_jogak 행은 post의 FK 부모가 아니므로 lock 대상에서 제외한다. 게시글·모각 트리·계정 직접 관계는 각각 Drizzle $with·delete·schema column으로 구성한 data-modifying CTE 한 statement로 명시 삭제하고, CTE 실행 의존성만 작은 sql 조건으로 연결한다. 마지막 users DELETE ... RETURNING으로 성공 여부를 판정한다. 따라서 delete 왕복은 15회에서 4회로 줄고, 전체 요청은 lock 6회 포함 약 10회다. 관계 사용자 목록 CTE와 transaction advisory lock helper, 일반 mutation의 lock 호출 및 advisory-lock 테스트를 제거했다. drizzle/0004_withdrawal_purge_indexes.sql에는 삭제/FK 확인 조건 인덱스 10개를 추가했다.

리뷰 개선: 0005_remove_withdrawal_fk_cascades.sql이 회원·게시글 관계 FK 12개의 ON DELETE CASCADE를 NO ACTION으로 교체한다. 이로써 모든 정상 삭제 경로가 자식 명시 delete를 수행하지 않으면 부모 삭제가 실패한다. concurrent index 선적용 runner는 실제 배포 경로에 연결되지 않아 제거하고, 현재 규모에서는 일반 migration만 적용한다.

검증 보강 결과

2026-08-23 승인 범위를 완료했다. PostgreSQL 통합 테스트는 전체 회원 관계 삭제, 빈 계정 삭제·없는 사용자 재시도, 실제 deleteUser()가 lock을 보유한 상태에서 댓글·좋아요·팔로우 insert가 대기 후 FK 23503으로 실패하는지를 검증한다. AuthService 단위 테스트는 deleteUser=false를 USER_NOT_FOUND로 변환하는 경계를 검증한다. 런타임 코드·HTTP 계약은 변경하지 않았다.

  • pnpm format:check, pnpm lint, pnpm typecheck, git diff --check 통과.
  • pnpm test --runInBand: 54 suites, 256 tests 통과.
  • pnpm test:integration --runInBand: 3 suites, 20 tests 통과.
  • 전용 mogak_test에 0005를 적용한 뒤 users/post를 참조하는 FK의 confdeltype = 'c'(cascade)가 0개임을 확인했고, 전체 integration suite가 통과했다.

현재 규모에서는 일반 migration만 적용한다. FK 변경은 짧은 DDL lock을 획득하므로 트래픽이 낮은 배포 창에서 실행한다.

이슈 등록

해결됨 — 직접 사용자 FK 생성 경로의 lock 후 재검증 누락: createModarat, createSession, 두 동의 upsert가 lock 뒤 동일 transaction에서 users를 재조회한다. 사용자가 없으면 컨텍스트별 전용 예외를 던지고 서비스 경계에서만 USER_NOT_FOUND로 변환한다. 전역 FK 23503 변환은 사용하지 않는다.

해결됨 — schedule weekday purge 테이블명 불일치: 실제 PostgreSQL 통합 테스트에서 단수형 jogak_schedule_weekday 참조가 실패한 것을 발견했다. 런타임 schema와 같은 복수형 jogak_schedule_weekdays로 수정했고, 게시물 의존 관계 삭제·rollback·두 connection advisory-lock 대기 테스트를 포함한 전체 integration suite가 통과했다.

해결됨 — lock 경합 증거: 통합 테스트는 두 번째 connection의 pg_locks.granted=false를 확인한 뒤 첫 transaction을 commit하고 실제 AuthRepository.deleteUser() 완료를 확인한다.

운영 이해 점검

post 생성은 먼저 소유 jogak을 검증하고 현재 사용자를 작성자로 저장한다. 탈퇴가 users·jogak을 선점한 뒤에는 해당 생성의 FK 참조가 대기하며, 탈퇴 커밋 후에는 상위 행 부재로 실패한다. 외부 사용자의 댓글·좋아요는 post 행 lock이 같은 방식으로 차단한다.
