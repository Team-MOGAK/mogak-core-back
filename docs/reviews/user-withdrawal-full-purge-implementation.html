회원 탈퇴 전체 삭제 구현 기록

설계 기준: user-withdrawal-full-purge-design.html

  • 탈퇴 성공 계약을 204 No Content로 변경하고 본문을 제거한다.
  • AuthRepository가 관련 사용자 lock union을 먼저 획득한 뒤, set-based SQL로 모든 회원 소유/작성 관계를 자식부터 삭제한다.
  • 공통 transaction advisory lock helper를 만들고 Auth, User, Consent, Mogak, Post, Social의 mutation에 적용한다.
  • 삭제 및 HTTP 계약 테스트로 회귀를 확인한다.

승인된 추가 범위

2026-08-23 승인: 탈퇴 cascade의 CTE·DELETE USING·테이블명 raw SQL을 Drizzle query builder/subquery로 교체했다. 또한 advisory lock 후 중복 hierarchy join을 PK 존재 재확인으로 축소했다. HTTP 204, 도메인 오류, transaction 및 lock 집합은 유지한다.

이슈 등록

해결됨 — 직접 사용자 FK 생성 경로의 lock 후 재검증 누락: createModarat, createSession, 두 동의 upsert가 lock 뒤 동일 transaction에서 users를 재조회한다. 사용자가 없으면 컨텍스트별 전용 예외를 던지고 서비스 경계에서만 USER_NOT_FOUND로 변환한다. 전역 FK 23503 변환은 사용하지 않는다.

해결됨 — schedule weekday purge 테이블명 불일치: 실제 PostgreSQL 통합 테스트에서 단수형 jogak_schedule_weekday 참조가 실패한 것을 발견했다. 런타임 schema와 같은 복수형 jogak_schedule_weekdays로 수정했고, 게시물 의존 관계 삭제·rollback·두 connection advisory-lock 대기 테스트를 포함한 전체 integration suite가 통과했다.

해결됨 — lock 경합 증거: 통합 테스트는 두 번째 connection의 pg_locks.granted=false를 확인한 뒤 첫 transaction을 commit하고 실제 AuthRepository.deleteUser() 완료를 확인한다.

운영 이해 점검

확인 중. 운영자는 DB 통합 환경에서 advisory lock 대기, rollback, A/B 데이터 보존 suite를 실행해 결과를 확인해야 한다.
