우선 발견 사항

R1 · P1 · open · Blocker — 레거시 반복 요일이 한 요일로 바뀜

레거시 호환 SQL:69–70은 반복 요일 원본 대신 effective_from의 요일 하나를 넣는다. 복수 요일 또는 시작일과 다른 요일로 반복하던 일정이 바뀐다.

조건·영향
대상 요일 행이 아직 없고 주간 반복이 존재할 때. 예: 원본 월·수 → 이관 후 월요일만 조회되고 수요일 실행/회고 대상이 사라진다. 원본 데이터 삭제를 재현한 것은 아니며, 새 서버가 사용하는 일정의 의미가 손실된다.
실행 근거
임시 PG17 테이블에서 현재 SQL 마지막 두 문장을 그대로 실행: original {MONDAY,WEDNESDAY} / migrated {MONDAY}. 트랜잭션은 롤백했다.
수정 방향
실제 Spring 요일 관계에서 전체 집합을 복사하고 전후 집합을 비교한다. 이미 채워진 잘못된 행은 NOT EXISTS 때문에 재실행으로 복구되지 않으므로 별도 충돌 탐지·복구가 필요하다.
미확인
운영에 이미 SQL을 적용했는지, 잘못 이관된 행이 몇 개인지는 미확인. 별도 요일 무결성 설계는 기존 문서로 연결하며 이번에 수정하지 않았다.

R2 · P1 · open · Blocker — 유휴 DB 연결 단절이 API 전체를 종료함

database.provider.ts:14–28은 Pool을 생성하지만 error 이벤트 처리기를 등록하지 않는다.

조건·영향
성공한 DB 요청 이후 유휴 연결이 서버 재시작·장애 조치 등으로 끊기면 요청 밖에서 error 이벤트가 발생한다. 프로세스가 종료돼 같은 인스턴스의 다른 요청도 중단될 수 있다.
실행 근거
현재 dist/main.js 실행 → 메타데이터 200 → 리뷰 전용 application_name의 idle backend만 종료 → Unhandled 'error' event / exitCode 1.
수정 방향
Pool 생성 경로를 통합해 오류 처리·안전한 로그를 등록하고 복구 테스트를 둔다. 연결/쿼리 대기 상한도 운영 예산에 맞춰 설정한다.

이 동작은 node-postgres Pool 공식 문서의 error 이벤트 설명과 일치한다.

R3 · P1 · open · Blocker — 날짜 범위·페이지 크기가 요청당 자원 소비를 제한하지 못함

jogakSchedule.policy.ts:116–130은 날짜 형식·순서만 검사한다. jogaks.service.ts:266–287는 일정마다 전체 요청 날짜를 동기적으로 다시 펼친다.

조건·영향
등록 사용자가 긴 기간을 요청하고 해당 기간에 일정이 하나 이상 있을 때. 이벤트 루프 지연·메모리 증가가 발생하며 다수 일정/요청에서 다른 사용자 요청에도 영향을 준다. IP당 요청 횟수 제한으로 한 요청의 비용을 제한할 수 없다.
실행 근거
실제 요청 스키마와 도메인 검사가 0001-01-01 … 9999-12-31을 허용한다(3,652,059일). 안전한 축소 재현에서 1,000년/365,243일 배열 생성만 약 219ms의 동기 작업이었다. 전체 최대 요청이나 운영 부하 테스트는 실행하지 않았다.
같은 보호 공백
social.request.ts:6–20과 post.request.ts:31–33에는 size 상한이 없다. size=1000000000 검증 통과를 확인했다. 피드 조회는 게시글·이미지·댓글을 메모리로 구성하며 요약 응답도 전체 댓글을 조회한다.
수정 방향
서버 측 최대 조회 일수·페이지 크기·offset을 제한하고, 날짜를 한 번 계산하거나 일정 유효 구간과 교차시킨다. 댓글 페이지화 및 요약 경로의 불필요한 댓글 조회 제거도 필요하다.

R4 · P2 · open · Blocker — 최초 동시 로그인 충돌 복구가 실패함

auth.repository.ts:127–136, 268–277은 PostgreSQL 오류를 최상위에서만 확인한다. 현재 Drizzle은 실제 23505와 제약 이름을 DrizzleQueryError.cause에 넣는다.

조건·영향
계정이 아직 없는 동일 소셜 식별자로 로그인 두 요청이 겹친다. 한 요청은 성공하고 다른 요청은 중복 사용자 재조회 경로에 진입하지 못해 서버 오류가 된다. DB UNIQUE는 중복 계정 생성을 막으므로 데이터 중복으로 과장하지 않는다.
실행 근거
현재 선언 스키마를 갖춘 임시 PG17에서 기존 auth-concurrency.integration.spec.ts의 “같은 social identity의 동시 로그인은 한 사용자와 두 세션으로 수렴한다” 실패. 내부 원인: duplicate key … uq_social_account_provider_user.
수정 방향
실제 오류 cause를 안전하게 추적해 DuplicateSocialAccountException으로 변환하고 기존 계정 재조회로 수렴시킨다. 기존 DB 통합 테스트를 배포 검증에 포함한다.

R5 · P2 · open · 보안 위험 — DB 오류 로그에 원문 파라미터가 포함됨

globalException.filter.ts:137–143은 Error의 message와 stack을 그대로 보존한다. Drizzle 실패 메시지에는 SQL과 파라미터 문자열이 포함된다. 요청 body의 토큰 마스킹은 이 문자열까지 가리지 못한다.

조건·영향
요청 데이터를 사용한 DB 쿼리가 실패하고 Drizzle 오류가 필터에 도달할 때, 회고 본문·댓글 등 원문이 중앙 로그에 들어갈 수 있다. 토큰 원문 유출이나 외부 공개를 확인한 것은 아니다.
실행 근거
리뷰 DB의 읽기 전용 실패 쿼리에 합성 표식을 넣고 실제 필터로 처리한 결과 raw SQL parameter retained in exception log: true.
수정 방향
DB 오류는 SQLSTATE·제약·테이블·안전한 작업 식별자 중심으로 기록하고 SQL 파라미터가 들어간 message/stack을 별도로 정제한다.

잔여 위험과 확인이 필요한 조건

R6 · open
헬스·준비 상태
health.controller.ts:7–9는 상수 200이다. 스키마가 없는 DB에서도 health 200/metadata 500을 재현했다. 단순 생존 확인 용도로는 타당하나 배포 성공·DB 준비 판정 근거로는 부족하다. 별도 readiness 또는 실제 DB 경유 smoke 검증이 필요하며, 현재 운영 probe 설정은 미확인이다.

qs 6.15.3에 배열 제한 우회와 isBuffer 서비스 거부 권고가 있다. 두 건 모두 6.16.0에 수정됐다. pnpm은 moderate 2건으로 집계하나 첫 권고의 작성자 표시는 Low다. 현재 Express query parser는 simple이고 앱에 comma:true 또는 qs.stringify 경로가 없어 악용 가능성을 확정하지 않았다. 의존성 갱신 대상으로 관리한다.

trust proxy=1, 인스턴스별 메모리 throttling이다. 실제 Cloud Run ingress hop, LB 추가 여부, 인스턴스 수, 외부 WAF/전역 제한은 미확인이다.
DB 자원·보안
코드에 연결/쿼리 timeout 설정이 없다. DB/연결 문자열의 외부 설정으로 보완됐는지, Cloud Run 최대 인스턴스 × pool 크기, TLS/접근 제한/DB 계정 권한은 미확인이다.
기존 운영 전환
현재 운영 스키마의 auth_sessions, social_account, role 값, 제약 이름, 중복·고아 데이터, 원본 요일, 스키마 변경 이력, 백업 복원 가능성은 미확인. README의 신규 DB 안내와 실제 기존 DB 전환 절차가 다르므로 복제본에서 승인된 전환 절차를 먼저 검증해야 한다.
권한 검토에서 주요 사용자·게시글·댓글 수정/삭제의 추가 소유권 우회는 발견하지 못했다. JWT 검증 뒤 활성 세션의 사용자 ID를 확인하고, 탈퇴는 트랜잭션으로 관련 행을 정리한다. 이 확인은 모든 공격 경로가 안전하다는 보증이 아니다.

리뷰 판단과 배포 전 조건

blocker 있음. 현재는 기존 Spring DB 대상 운영 배포를 보류하는 것이 타당하다. 코드·이미지 빌드는 가능하지만 데이터 전환과 가용성에 재현된 문제가 남아 있다.

  1. 레거시 반복 요일 집합을 보존하도록 전환·복구를 검증하고, 실제 적용 이력과 대상 행을 대조한다.
  2. Pool error 처리 및 장애 복구, 날짜·페이지 상한, 로그인 UNIQUE 예외 처리를 수정한 뒤 위 재현을 다시 통과시킨다.
  3. SQL 원문 로그를 정제하고 운영 JWT·세션 정리·이미지 출시 범위를 확인한다.
  4. 운영 DB 복제본에서 전체 레거시 전환과 로그인·조회·작성·삭제·탈퇴 smoke 테스트를 수행한다.
  5. 배포할 정확한 revision에 대해 DB 포함 게이트를 실행하고, 백업 복원/롤백·readiness·자원 제한·권한 설정을 확인한다.
