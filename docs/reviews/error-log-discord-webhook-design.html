error 로그 Discord 웹훅 전달 설계

GitHub 이슈: #18 · warn/error 기준 통일과 error 로그 Discord 웹훅 전달

목적 · purpose
운영 API의 error를 Discord에서 확인하고 원본 로그를 추적한다.
사용자 · audience
운영 장애를 확인하고 알림 전달 경로를 관리하는 백엔드 개발자와 운영자.
문제 · problem
warn/error 분류 누락과 웹훅 경로 부재로 실제 5xx와 DB 장애를 놓친다.
핵심 흐름 · core-flow
오류 분류 → 대표 error JSON → Cloud Logging sink → Pub/Sub → 독립 relay와 채널 제어 → Discord 또는 DLQ.
추적 메타데이터
2026-10-15 사용자 요청: warn/error 개선 설계와 GitHub 이슈, 현재 error만 웹훅. 조사 commit: 83be31c54c62d5c8959e3bd17e7206f2d6aa5046.

외부 알림이라는 새 목적의 동료 산출물이다. 기존 Pino 로그 출력 설계를 대체하지 않는다. 구현 기록을 별도로 유지한다.

배경 · 목표와 현재 승인 범위 · 설계 제안 · 완료 조건 · 검증 계획 · 제외 범위와 후속 후보 · 공식 근거 · 의사결정 · 자기점검 · 승인

배경

현재 API는 Pino JSON 로그와 서버 생성 요청 ID를 사용하지만, 운영 오류를 Discord로 전달하는 경로는 없다. warn/error 분류에도 누락이 있어 웹훅을 붙이기 전에 기준을 통일해야 한다.

코드 조사 기준: 83be31c54c62d5c8959e3bd17e7206f2d6aa5046.

  • GlobalExceptionFilter는 모든 DomainException을 warn으로 기록한다. 실제로 STORAGE_DISABLED는 503이므로 현재 상태에서 error만 전송하면 이 오류가 빠진다.
  • Pino HTTP 설정에 상태별 customLogLevel과 Cloud Logging 표준 severity 매핑이 없다. 설치된 pino-http 11의 자동 완료 로그는 기본 info다.
  • readiness는 DB 실패 때 예외를 던지지 않고 직접 503을 반환한다. 예외 필터만 알림 대상으로 삼으면 놓친다.
  • DB pool 오류는 console.error(object)를 사용해 공통 Pino JSON 계약 밖에 있다.
  • cloudbuild.yaml의 CLOUD_LOGGING_ONLY는 빌드 로그 설정이다. 운영 Cloud Run의 sink·알림·Discord 연동 구성은 저장소에서 확인되지 않았다.

목표와 현재 승인 범위

warn과 error를 일관되게 분류하고, 운영 API의 알림 대상 error만 Discord 웹훅으로 전달한다. 2026-10-15 사용자 지시 “브랜치 따고 워크트리 따서 구현 작업 진행해”로 이 설계의 저장소 구현을 승인받았다. 승인 범위: API 로그 계약, 독립 relay, 배포 가능한 설정과 운영 문서, 로컬 검증. 운영 리소스 변경과 실제 Discord 발송은 배포 단계에서 수행한다.

이번 버전의 error는 Pino level=50 / Cloud Logging severity=ERROR로 명시한다. warn=40은 전송하지 않는다. 현재 호출부가 없는 fatal=60과 플랫폼 시스템 로그 알림은 후속 범위로 둔다.

설계 제안

1. 레벨 기준

상황 기준 비교
상황로그 레벨웹훅
HTTP 2xx/3xx 완료info제외
입력 검증, 인증·권한 거절, 리소스 없음, 충돌 등 예상된 4xxwarn제외
429, 잘못된 multipart 입력warn제외
DomainException의 최종 매핑 상태가 5xxerror대상
미등록 domain code가 최종 500으로 매핑됨error대상
5xx HttpException, 처리되지 않은 예외error대상
예외 없이 직접 반환한 5xx, readiness 503 포함error대상
DB 연결 풀 오류 등 요청 밖의 인프라 실패error대상
기존 repository의 처리된 누락·경합 경고warn제외
실제 내부 불변식 실패 또는 처리할 수 없는 실패error대상

예외 클래스 이름만으로 분류하지 않는다. 현재 API의 최종 상태와 실패 결과를 기준으로 한다. STORAGE_DISABLED는 기능이 의도적으로 꺼져 있어도 요청을 이행하지 못하고 503을 반환하므로 error다. 알림량을 줄이기 위해 warn으로 낮추지 않는다. 기존 응답 상태·본문은 유지한다.

Pino의 숫자 level은 유지하고 severity를 추가한다: trace/debug→DEBUG, info→INFO, warn→WARNING, error→ERROR, fatal→CRITICAL. 운영 LOG_LEVEL은 info를 유지하고, error를 숨기는 설정은 배포 점검에서 거부한다.

2. 같은 실패의 알림 소유권

  • 요청 오류는 서버 생성 req.id를 errorId로 사용한다. 요청 밖 오류에는 UUID를 생성한다.
  • 예외 필터의 5xx 로그가 대표 오류다. errorId, event, statusCode, code, alertEligible=true를 기록하고 response-local marker를 공유한다.
  • 자동 요청 완료 로그는 <400 info / 4xx warn / 5xx error로 분류한다. 이미 대표 오류가 있으면 같은 errorId와 alertEligible=false를 기록해 이중 알림을 막는다.
  • 대표 오류 없이 직접 5xx를 반환한 경우 자동 완료 로그가 alertEligible=true인 대표 오류가 된다. readiness 503이 이 경로를 검증한다.
  • DB pool 오류는 같은 JSON 형식의 Pino error로 전환하고 alertEligible=true를 부여한다. 내부 raw message/stack/SQL/params 비출력 정책은 유지한다.
  • 새 error 호출부에도 알림 대상 여부를 명시한다. 대상 여부가 누락된 error는 계약 검사에서 발견하게 하고, 운영에서는 조회 가능한 누락 지표를 둔다.

이 소유권은 의도적으로 생성되는 예외/완료 로그의 중복만 제거한다. Pub/Sub 재전달·Discord 응답 유실로 인한 중복 가능성은 별도 전달 제한이다.

3. 전달 구조

API는 stdout에 기록한다. 외부 전송·재시도·웹훅 secret은 중계 서비스가 소유한다. API 응답은 Discord 응답을 기다리지 않는다. Cloud Logging 원본 보관은 유지하고 sink가 사본을 Pub/Sub로 전달한다.

sink 필터 예시이며 실제 식별자는 운영 inventory 후 확정한다:

resource.type="cloud_run_revision"
resource.labels.project_id="<PROJECT_ID>"
resource.labels.service_name="<PRODUCTION_API_SERVICE>"
logName="projects/<PROJECT_ID>/logs/run.googleapis.com%2Fstdout"
severity=ERROR
jsonPayload.level=50
jsonPayload.environment="production"
jsonPayload.alertEligible=true

정규화 로그에는 schemaVersion=1, service/environment, event, errorId, alertEligible를 둔다. 중계 서비스도 수신 envelope·resource·schema·정확한 레벨·eligible를 재검증한다. 다른 서비스, 개발 환경, warn, 누락·손상된 입력을 Discord에 보내지 않는다. malformed 입력은 안전하게 격리한다.

sink는 API 서비스만 포함한다. 중계 서비스의 자체 error가 다시 같은 웹훅 입력으로 돌아오는 재귀 호출을 방지한다.

4. Discord 메시지와 권한

Discord에는 원본 로그를 복사하지 않고 허용 필드로 새 메시지를 만든다.

  • 허용: 발생 시각, 환경/서비스/revision, errorId, 고정 event와 고정 요약, 숫자 상태, 검증된 앱 오류 코드, HTTP method, 정적 route template, Cloud Logging 조회 링크.
  • 제외: body/query/params/headers, 원본 URL과 path ID, 사용자 작성 내용, raw exception message/stack/cause, SQL/DB parameter, DB table/constraint, webhook URL.
  • 요약은 event·앱 오류 코드의 고정 사전에서 가져온다. 알 수 없는 값은 일반적인 서버 오류 문구로 대체한다. raw err.message로 fallback하지 않는다.
  • 본문은 최대 1,800자로 제한한다. 값과 URL query를 안전하게 인코딩하고 allowed_mentions: { parse: [] }로 멘션을 막는다. 링크는 검증된 프로젝트와 errorId 기반으로 만든다.
  • wait=true로 전송 성공을 확인한다. 성공 응답의 메시지 ID만 내부 진단에 기록하고 Discord 응답 본문·요청 URL은 로깅하지 않는다.
  • webhook URL은 Secret Manager에 보관하고 중계 서비스 계정만 접근한다. API에는 secret을 주입하지 않는다. push는 인증을 요구하고 허용된 서비스 계정에만 relay invoke 권한을 준다. HTTPS Discord webhook endpoint만 허용하고 redirect를 따라가지 않는다.

5. 전송 실패와 중복

Pub/Sub push는 최소 한 번 전달 방식이다. Discord에 정확히 한 번 표시되는 것을 보장하지 않는다. 성공 후 ACK 유실이나 전송 timeout에서는 같은 errorId가 다시 표시될 수 있다. v1에는 오류별 영속 dedup ledger·집계를 넣지 않는다.

결과 기준 비교
결과처리
Discord 성공 응답source ACK
network/timeout/Discord 5xxnon-2xx로 반환해 유한한 Pub/Sub retry + DLQ 사용
Discord 429Retry-After/retry_after를 읽어 채널 cooldown 저장. 이후 전달은 시각이 되기 전 Discord를 호출하지 않고 재시도 대기
Discord 400 등 영구 payload 오류허용 필드와 오류 사유만 격리 topic에 저장한 뒤 ACK. 격리 저장 실패 시 ACK하지 않음
Discord 401/403/404채널 전송 중단 상태 저장, 격리 후 ACK. secret/권한 수정과 명시적 재개 전 반복 호출 금지
malformed 입력raw payload를 외부로 보내지 않고 제한된 진단 정보로 격리
제어 상태 저장소 장애Discord 호출 없이 non-2xx. 원본 메시지는 재시도 또는 DLQ에 남김

Pub/Sub의 backoff는 best effort이며 webhook의 공유 cooldown을 대신하지 못한다. 따라서 relay 전용 Firestore의 채널 제어 문서에 nextAllowedAt, 짧은 전송 lease, disabled, secret version을 저장하는 안을 제안한다. 오류 원문·webhook URL·API 사용자 데이터는 저장하지 않는다. API PostgreSQL 장애 때도 알림이 동작하도록 API DB에 의존하지 않는다.

송신 전 transaction으로 lease와 cooldown을 확인하고 claim한다. Discord HTTP 호출은 transaction 밖에서 수행한다. 429 후 cooldown은 늦은 시각을 보존하고, lease 해제와 결과 저장을 마친다. 미래 시각/유효한 lease가 있으면 송신 없이 non-2xx를 반환한다. 제어 상태에 성공 저장하기 전 crash가 발생하는 모호한 구간은 남으며, exactly-once로 표현하지 않는다.

초기 운영값 제안: Discord HTTP timeout 5초, relay request budget 15초, lease 30초, push ACK deadline 30초, subscription exponential backoff 10–600초, DLQ 최대 delivery attempts 100, subscription/DLQ 보존 7일. Pub/Sub delivery attempts는 정확한 비즈니스 재시도 횟수가 아니며 cooldown 대기·플랫폼 실패도 포함할 수 있다. DLQ에는 자동 무한 replay를 붙이지 않는다.

cooldown이나 장기 장애 때문에 DLQ로 이동한 메시지는 원인 수정 후 운영자가 동일 errorId를 보존해 수동 replay한다. 재시도/lease/DLQ의 운영값은 staging의 실제 rate-limit 응답과 처리량으로 확인한다. relay 동시성과 최대 인스턴스도 작게 제한한다.

6. 운영 전제와 단계적 적용

저장소 조사만으로 확인하지 못한 항목: 운영 project/service/region, 서비스 계정, sink/IAM 관리 저장소, 현재 로그의 수집 형태, Secret Manager 정책, Firestore 사용 가능 여부와 비용. 이는 사실로 가정하지 말고 구현 착수 전 inventory한다. Firestore를 사용할 수 없으면 cooldown/중단 상태를 보장하는 독립 대안을 다시 설계한다.

  1. 실제 runtime JSON과 GCP 리소스/소유 주체를 확인한다.
  2. API의 레벨·severity·대표 오류 계약과 DB pool 로그를 구현한다.
  3. 독립 relay, 채널 제어, 격리/DLQ, IAM과 secret 주입을 구성한다.
  4. 운영과 분리한 topic·서비스·테스트 웹훅으로 합성 오류를 검증한다.
  5. production sink를 활성화한다. 장애 시 sink/push를 중지하고 원본 Cloud Logging 조회로 대응한다.

backlog age, DLQ 증가, relay 실패, 제어 저장소 실패를 Cloud Monitoring에서 볼 수 있게 한다. Discord 자체 장애를 Discord만으로 감지한다고 가정하지 않는다. 독립 운영 알림 채널은 후속 후보로 둔다. 신규 GCP 리소스의 비용은 구현 전 추정하며, 서로 다른 실제 error는 v1에서 집계하지 않아 장애 폭증 시 알림 지연이 생길 수 있다.

완료 조건

  • 4xx DomainException/HttpException, 429, multipart 거절은 WARNING/40이고 Discord 0건이다.
  • STORAGE_DISABLED 503, INTERNAL_SERVER_ERROR와 미등록 domain code의 500은 ERROR/50이다.
  • 5xx HttpException과 unknown Error는 대표 eligible 오류를 하나 만든다.
  • 예외 로그와 5xx 완료 로그가 모두 error여도 eligible=true는 한 건이다.
  • readiness의 직접 503은 완료 로그 fallback으로 eligible 오류를 만든다.
  • DB pool error는 Pino JSON ERROR/50, errorId, eligible 계약을 따른다.
  • info/warn/fatal, 개발 환경, 다른 서비스, schema 누락 입력이 웹훅에서 제외된다.
  • 중계 서비스 자체 error는 sink로 재유입되지 않는다.
  • Discord 요청 body에 민감 sentinel·원본 요청값·원본 오류 message/stack·SQL·path ID가 없다.
  • 429 후 cooldown과 중계 재시작/동시 수신을 검증한다. 유효한 cooldown 전에는 다음 Discord 호출이 없다.
  • timeout/5xx, 영구 4xx, 잘못된 secret, 격리 저장 실패, Firestore 장애가 위 표대로 처리된다.
  • Pub/Sub redelivery/응답 유실의 중복 가능성과 errorId 보존을 검증하고 운영 문서에 남긴다.
  • backlog/DLQ 조회, secret 교체·채널 재개, 수동 replay, sink 중지 절차가 준비된다.
  • 로그 변경 전후 기존 HTTP 상태·응답 본문 계약이 유지된다.

검증 계획

기존 Pino 옵션/통합, 전역 예외 필터, DB provider, health E2E 테스트에 실제 JSON·대표 오류 소유권 사례를 추가한다. relay는 fake Discord 서버와 제어 저장소 fixture로 성공/429/5xx/timeout/영구 4xx/재전달을 검증한다.

pnpm test --runInBand test/infrastructure/logging test/common/http/globalException.filter.spec.ts test/database/database.provider.spec.ts
pnpm test:e2e --runInBand test/e2e/health.e2e.spec.ts
pnpm format:check
pnpm lint
pnpm typecheck
pnpm build

relay의 정확한 검증 명령은 독립 deployable의 build 경계를 정할 때 계약에 추가한다. staging에서는 실제 Cloud Logging severity 승격, sink 선택, 테스트 webhook 수신과 중계 실패 시 API 응답 독립성을 확인한다. 이번 설계 작업에서는 구현 테스트·운영 리소스 변경·웹훅 전송을 수행하지 않는다.

제외 범위와 후속 후보

  • warn/fatal/플랫폼 시스템 로그와 초기 logger 준비 전 프로세스 종료 알림, 기존 API 응답 변경
  • API 프로세스의 직접 웹훅 호출, 원본 전체 로그의 Discord 복사
  • 오류별 영속 dedup ledger와 exactly-once 보장
  • 동일 오류 집계, 장애별 incident/recovery 메시지, trace 전파, 대시보드 구축
  • 기존 로그 자체의 보관·개인정보 정책 전면 재설계

공식 근거

  • Cloud Run 로그 수집과 structured JSON
  • Cloud Logging의 Pub/Sub 로그 라우팅
  • Pub/Sub retry policy와 best-effort 제한
  • Pub/Sub push의 exactly-once 미지원
  • Discord webhook의 wait/allowed_mentions/메시지 형식
  • Discord rate-limit 응답과 Retry-After

설계 의사결정 기록

진행 상태: 제안 정리 완료. 사용자 확정 범위: warn 제외, error만 웹훅, 설계와 이슈 생성.

의존 순서: 레벨 기준 → 대표 오류 소유권 → source 필터 → 메시지 경계 → 전송 실패와 공유 제어 → 운영 검증.

독립 읽기 전용 압박 검토로 5xx DomainException 누락, readiness 직접 503 누락, numeric level과 severity 불일치, 이중 로그, 재전달 중복을 확인했다. 일반 로그 조회와 외부 메시지의 개인정보 경계를 분리했다.

기술 제안: 독립 relay와 source의 대표 오류 소유권. 오류별 dedup ledger는 후속으로 두고, API DB와 분리한 채널 제어 저장소로 공유 cooldown을 처리한다. GCP 사용 가능 여부와 비용은 구현 전 검증할 가정이다.

검증 필요: 운영 project/service/region, 서비스 계정과 IaC 소유 주체, 실제 수집 로그, Firestore 정책·비용. 확인되지 않은 환경은 확정된 사실로 간주하지 않는다.
선택하지 않은 대안
API 직접 webhook 호출
외부 지연과 전송 실패가 API 요청 처리와 엮인다.
프로젝트 전체 ERROR sink
다른 서비스와 relay error가 유입되어 재귀가 생긴다.
오류별 영속 dedup ledger
현재 전달 요구보다 범위가 크고 Discord까지 exactly-once를 보장하지 못한다.
Pub/Sub retry만으로 429 처리
best-effort backoff는 서로 다른 메시지의 공유 cooldown을 대체하지 못한다.
