백엔드 오류 Discord 알림 설계

GitHub PR #19 · error 로그를 Discord로 전달

목적 · purpose
운영 백엔드의 error를 Discord에서 확인하고 원본 로그를 추적한다.
사용자 · audience
운영 장애를 확인하는 백엔드 개발자와 운영자.
문제 · problem
운영 error 로그가 Discord 알림으로 전달되지 않아 실제 5xx와 DB 장애를 놓친다.
핵심 흐름 · core-flow
오류 분류 → 안전한 요약 생성 → 백엔드 내 alerting 모듈이 Discord webhook에 비동기 전송 → errorId로 Cloud Logging 원본 조회.
추적 메타데이터
2026-10-19 사용자 요청: PR #19의 별도 relay 설계를 백엔드와 함께 배포하는 논리 모듈로 단순화.

이전 설계의 재검토 사유: 독립 이미지·Cloud Run relay·Pub/Sub·격리 topic/DLQ는 사용자가 원한 배포 모델보다 복잡하다. 사용자는 백엔드 프로세스 안에서 논리적으로 분리하고, 오류 시 Discord webhook으로 직접 알리길 원한다.

목표 · 흐름 · 계약 · 실패 · 검증 · 자기점검 · 승인

목표와 범위

  • API와 같은 Node/Nest 프로세스에 alerting 모듈을 둔다. 모듈 경계는 코드에서 유지하고 이미지·Cloud Run 서비스·배포 revision은 백엔드와 공유한다.
  • 기존 4xx는 warn으로 기록하고 Discord 알림에서 제외한다. 최종 5xx와 요청 밖 DB pool error는 error 알림 대상으로 둔다.
  • 원래 HTTP 상태 코드와 응답 본문은 Discord 상태와 무관하게 유지한다.
  • 실제 Discord 전송, GCP 리소스 변경, Secret Manager 값 생성은 구현 범위가 아니며 별도 운영 작업이다.

구성 흐름

  • AlertingModule은 API의 기존 DI 및 빌드에 등록한다. 독립 apps/alerting 앱 프로세스, Dockerfile, Cloud Build relay 설정을 두지 않는다.
  • 대표 5xx 예외는 global exception filter가 알림을 한 번 요청한다. 요청 완료 로그는 이미 대표 오류가 기록된 경우 재알림하지 않는다. 대표 예외가 없고 최종 응답이 5xx인 경우에는 완료 로그 경계가 fallback 알림을 맡는다.
  • DB pool error는 요청 밖 오류이므로 해당 provider의 canonical error handler가 알림을 한 번 요청한다.

알림 계약과 개인정보 경계

항목설계
알림 대상최종 상태가 5xx인 오류와 DB pool 오류. 예상된 4xx·429·입력 거절은 warn이며 Discord 전송 없음.
식별·추적요청 오류는 서버 생성 errorId, 요청 밖 오류는 UUID. 같은 ID가 Cloud Logging과 Discord 요약에 나타난다.
허용 payload발생 시각, errorId, event, service, environment, appCode/appCodeSummary, statusCode, HTTP method, 정적 route template 등 허용 목록 필드만 보낸다.
제외 payload원본 exception message/stack, SQL/parameters, request body, 실제 URL/query/path ID, 인증 정보, webhook URL은 보내지 않는다.
비밀값DISCORD_WEBHOOK_URL은 Cloud Run Secret Manager 환경변수로 주입한다. 값은 코드·응답·로그에 출력하지 않는다.
Secret 누락사용자 결정: alerting만 비활성화하고 startup warning을 남긴다. API 서버는 계속 기동한다.

전송 실패와 운영 동작

  • Discord 호출은 API 흐름을 기다리게 하지 않는 비동기 best-effort다. 정해진 짧은 timeout 안에 응답하지 않거나 네트워크 오류·429·5xx가 나면 해당 알림은 실패 처리한다.
  • 영속 queue, DLQ, 재시작 후 replay, 자동 retry는 없다. 프로세스 중단이나 Discord 장애 중 알림이 유실될 수 있음을 수용한다.
  • 전송 실패는 안전한 warn 로그로 기록하고 같은 오류를 다시 알림하지 않아 재귀를 막는다. 오류 식별자로 Cloud Logging 원본을 찾는다.
  • 알림 폭주나 Discord의 rate limit에는 별도 저장소/공유 cooldown을 추가하지 않는다. 일회 전송 실패와 유실은 운영 잔여 위험이다.

가장 강한 반증: 장애 순간 backend 프로세스가 종료되거나 Discord rate limit이 발생하면 알림이 조용히 유실될 수 있다. 이를 허용한 대신 API 경로를 외부 Discord 상태에 묶지 않고 Pub/Sub/DLQ 운영 비용을 제거한다.

구현 후 검증 계획

  • focused command: pnpm test --runInBand test/infrastructure/alerting/discordWebhookSender.spec.ts test/common/http/globalException.filter.spec.ts test/database/database.provider.spec.ts test/infrastructure/logging/pinoHttp.options.spec.ts. Alert payload allowlist, success/error/timeout/429, webhook 누락 startup, unhandled rejection 부재, 5xx 단일 발송, 4xx 제외, DB pool error를 fake HTTP server로 검증한다.
  • 기존 global exception filter, Pino request completion, DB provider 회귀 검증으로 상태·응답·중복 여부를 확인한다.
  • format/lint, typecheck, build와 CI 전체 검사를 확인한다. 실제 Discord 전송·GCP Secret Manager/IAM·Cloud Run 배포는 하지 않는다.
  • Secret Manager 참조와 런타임 service account 권한은 배포 전 운영자가 확인한다. 로컬 테스트 성공은 실제 채널 수신을 증명하지 않는다.
이전 독립 relay 설계 기록

이전 안은 Cloud Logging → Pub/Sub → 별도 private Cloud Run relay → Discord였고, OIDC push 계정, relay 계정, source/quarantine/DLQ topic과 subscription, cooldown 저장소, 독립 이미지 및 배포 스크립트를 포함했다. 사용자의 현재 단순화 요구와 맞지 않아 제안에서 제외했다. 이전 구현의 안전한 분류·allowlist 아이디어만 현재 기준선에 반영한다.
