목표와 범위

기존 legacy 생성 형식에서 isRoutine: false이면 today를 생략할 수 있다. 생략 시 서비스가 사용하는 KST 기준 오늘 날짜를 일회성 일정의 effectiveFrom으로 저장한다. today를 보내면 그 값을 그대로 사용한다.

명시 schedule: { scheduleType: 'ONCE', effectiveFrom } 형식은 이미 날짜를 명시하므로 변경하지 않는다. 루틴의 시작일·요일 규칙, 다른 필드 혼용 거부, 목록·실행 API는 범위 밖이다.

변경 모델

  1. 컨트롤러는 legacy 요청이 isRoutine: false이고 today가 없을 때, 일정을 강제로 만들지 않고 “기본 일회성 일정” 의도를 application 계층에 전달한다.
  2. 서비스는 이 경우 주입된 today() 값을 사용해 { scheduleType: 'ONCE', effectiveFrom: today() }를 만든 뒤 기존 일정 검증·저장 흐름을 사용한다.
  3. today가 있으면 기존처럼 그 날짜를 effectiveFrom으로 쓴다. 루틴은 계속 시작일이 필요하다.

핵심 위험과 불변식

날짜 기준 위험: 서버 시각을 컨트롤러에서 직접 읽으면 테스트와 KST 날짜 경계가 흔들릴 수 있다. 따라서 이미 서비스에 주입된 today() 단일 기준을 사용한다.

불변식: 기본값은 오직 명시적으로 isRoutine: false인 legacy 요청에만 적용한다. isRoutine 자체가 없거나 루틴 요청의 시작일이 없는 경우는 계속 잘못된 요청으로 거부한다.

검증 계획

  • presentation 테스트: isRoutine: false와 생략된 today가 기본 일정 의도로 서비스에 전달되는지 확인한다.
  • application 테스트: 고정된 today()에서 기본 ONCE 일정이 그 날짜로 저장되고, 명시 today는 덮어쓰지 않는지 확인한다.
  • 회귀 테스트: 루틴의 시작일 누락과 필드 혼용은 기존 오류로 유지되는지 확인한다.
