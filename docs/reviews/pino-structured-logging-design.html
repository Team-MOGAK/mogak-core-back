Pino 구조화 로깅 전환 설계

목적
Nest API의 운영 로그를 Pino 기반 JSON 로그로 일관되게 출력하고 요청 단위 상관관계를 확보한다.
사용자
장애·입력 오류를 조사하고 클라우드 로그에서 API 동작을 추적하는 백엔드 개발자와 운영자.
문제
현재 Nest 기본 텍스트 logger는 구조화된 로그 수집과 요청별 연관 분석에 적합하지 않으며, Pino로 전환할 때 기존 예외 로그의 안전 경계를 잃으면 안 된다.
핵심 흐름
환경 설정 → nestjs-pino 전역 등록 → PinoLogger 호출과 원본 예외의 안전한 snapshot 변환 → 요청 ID가 붙은 HTTP·예외 JSON 로그 → stdout 수집.
목표변경 모델결정위험·복구검증설계 이해 점검승인

목표와 비목표

운영·개발 환경 모두 한 줄당 하나의 JSON을 stdout으로 출력한다. HTTP 요청 완료 로그와 애플리케이션 이벤트 로그를 공통 필드(level, 시간, context, 요청 ID)로 검색 가능하게 한다.

비목표: 파일 로테이션, 외부 로그 SaaS 전송, 로그 저장소·대시보드 구성, 응답에 요청 ID 헤더를 추가하는 API 계약 변경은 이번 범위에 포함하지 않는다.

시스템 모델

  1. AppModule에 LoggerModule.forRootAsync를 한 번 등록하고 ConfigService로 level을 결정한다.
  2. main.ts에서 bufferLogs: true로 생성한 뒤 nestjs-pino의 Logger를 app.useLogger(app.get(Logger))로 적용한다. 부팅 이후 Nest 시스템 로그도 Pino를 사용한다.
  3. pino-http가 요청마다 내부 UUID를 생성해 req.id로 두고, 완료 로그 및 같은 비동기 흐름의 애플리케이션 로그에 같은 요청 ID를 붙인다.
  4. GlobalExceptionFilter는 Nest Logger를 직접 생성하지 않고 @InjectPinoLogger(GlobalExceptionFilter.name)로 PinoLogger를 주입받아 warn/error를 출력한다.

불변 조건

  • HTTP 상태 코드와 errorResponse 본문은 변경하지 않는다.
  • 도메인 예외의 민감 키 제거, multipart body 생략, 깊이·크기 절단 및 정제 실패 시 응답 유지 규칙을 보존한다.
  • 로그는 파일이 아니라 stdout으로만 출력하며, 운영 환경에서도 사람이 읽는 pretty transport를 사용하지 않는다.
  • 클라이언트가 준 요청 ID는 신뢰하지 않고 서버가 UUID를 생성한다. 이 ID를 응답 헤더에 노출하지 않는다.
  • 원본 Error/HttpException은 안전한 snapshot 생성의 입력으로만 읽고, response, cause, query, parameters를 포함한 원본 객체 자체는 Pino payload에 직접 전달하지 않는다.
  • repository의 경고 logger는 필수 DI 의존성이다. 테스트 수동 생성도 명시적 stub을 제공해 로그 누락을 숨기지 않는다.

결정과 마이그레이션 범위

확정된 설계 결정(구현 승인과 별개): Pino 직접 결합 대신 nestjs-pino를 Nest 통합 경계로 사용한다. 사용자 확인: 2026-08-24 “nestjs-pino 우선 쓰자”.

재승인 대상 결정: 원본 예외는 safeErrorSnapshot의 입력으로 읽되 err에는 새 Error snapshot만 기록한다. snapshot은 실패 안전하게 읽은 name, message, stack과 이미 별도 allowlist인 DB code/constraint/table만 포함한다. 원본 response, cause, query, parameters는 전달하지 않는다.

근거·가정: 기존 정책은 DomainException 요청값의 민감 키를 제거하지만 예외 객체의 enumerable 부가 속성에는 적용되지 않는다. Pino에 raw Error를 넘기는 대신 source snapshot을 주 방어선으로 삼고, 고정 경로 redaction은 보조 방어로만 검토한다.

가장 강한 반증 또는 완화: 예외의 message/stack 자체에 자격증명 또는 SQL parameter가 들어가는 실제 오류 유형이 발견되면 이 snapshot도 충분하지 않다. 그 경우 진단성·비밀 비노출 정책을 별도로 결정하기 전 구현을 중단한다.

미룬 범위·재검토 조건: custom transport, 로그 SaaS, 클라이언트 request ID 신뢰, lazy-loaded module을 도입할 때 또는 실제 Pino JSON이 snapshot 밖 필드를 복원할 때 이 선택을 재검토한다.

실패·복구와 잔여 위험

부팅 실패: 잘못된 LOG_LEVEL 또는 logger 모듈 설정 오류는 서버 기동 전에 실패한다. 배포 전 설정 단위 테스트와 시작 smoke test로 막고, 발생 시 유효한 환경값으로 되돌린다.

민감정보 노출: 자동 HTTP 로그 serializer와 Pino redaction을 이중 적용하되, 원본 예외는 safeErrorSnapshot으로 변환한 값만 기록한다. response.token, cause.secret, query, parameters를 포함한 Error를 실제 Pino stream으로 직렬화해 sentinel 비노출을 확인한다.

로그량 증가: 자동 요청 완료 로그가 매 요청 한 줄을 추가한다. level은 운영 info이며, 비용·보존 정책은 수집 플랫폼의 후속 운영 범위다.

복구: 문제 발생 시 logger 모듈 등록 및 main.ts adapter 연결을 되돌리면 기존 Nest text logger로 복귀한다. 데이터·API migration은 없다.

구현 순서와 검증 계획

  1. 의존성과 LOG_LEVEL 예시·파싱을 추가한다.
  2. root module의 Pino 구성과 bootstrap logger 연결을 구현한다.
  3. 필터의 오류 로그를 safeErrorSnapshot 기반 err로 바꾸고, 네 repository logger를 필수 DI로 이식한다.
  4. 자동 HTTP·예외 로그에서 요청 ID·상태·허용 오류 필드가 나오고 body/header/예외 sentinel 비밀값이 없음을 실제 stream JSON으로 통합 테스트한다.
