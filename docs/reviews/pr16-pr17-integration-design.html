목표와 제외 범위

  • PR16의 Spring 운영 DB 안정화 기능과 PR17의 API 자원·동시성 보호 기능을 모두 보존한다.
  • 공통 파일에는 두 기능을 합친 단일 구현만 남긴다. 자동으로 한쪽 변경을 선택하지 않는다.
  • 각 PR은 별도 리뷰 단위를 유지하되, PR17은 PR16을 먼저 병합해야 하는 stacked PR로 운영한다.
  • 실제 운영 DB 실행, Cloud Run 변경, 외부 트래픽 전환은 이 작업에서 수행하지 않는다.

제안 병합 모델

현재 PR17을 PR16 위로 rebase하거나 merge commit으로 재구성하고, PR17의 base를 PR16으로 설정한다. PR16 병합 후 PR17을 main으로 retarget하고 incremental diff와 CI를 확인한다. 원격 브랜치 history를 덮어쓰는 force push는 기본 경로로 사용하지 않는다.

불변식과 공통 구현 원칙

  1. 선택한 경우 PR16의 `/health/ready`, legacy migration preflight/rollback, 만료 세션 cleanup을 PR17 재구성 과정에서 삭제하지 않는다.
  2. PR17의 page/date bound, offset overflow 방지, transaction/advisory lock과 lock ordering을 유지한다.
  3. globalException.filter.ts, request schema, post/social service, auth repository/token, database provider에는 중복 상수·서로 다른 오류 계약을 남기지 않는다.
  4. 충돌은 파일별로 의도와 불변식을 확인해 해결한다. “ours/theirs 전부 선택”을 허용하지 않는다.
  5. migration은 테스트용 격리 PostgreSQL에서만 검증하고 실제 운영 DB에는 접근하지 않는다.

실패·복구와 외부 효과

충돌 해결 중 동작 선택이 새로 필요하거나 PR16/17의 범위가 달라지면 구현을 멈추고 설계 승인을 다시 받는다.
  • 통합 브랜치에서 typecheck·lint·test가 실패하면 원인별로 수정하고, 의미가 불명확한 실패는 원격 push 전에 중단한다.
  • 원격 변경 전 현재 head를 별도 백업 ref로 기록한다. merge commit 경로에서는 force push를 하지 않는다.
  • PR16 merge 후 PR17의 base를 변경할 때 GitHub diff와 mergeability를 새로 확인한다. 운영 배포나 DB migration 실행은 후속 승인 범위다.

검증 계획

  1. 격리 worktree에서 PR16과 PR17의 3-way merge를 수행하고 15개 충돌을 파일별로 해결한다.
  2. pnpm format:check, pnpm lint, pnpm typecheck, pnpm test --runInBand를 실행한다.
  3. PR16 migration/session/readiness와 PR17 concurrency/resource 경계의 관련 통합 테스트를 별도로 확인한다.
  4. 실제 원격 push 전 git diff --check와 변경 파일·PR diff를 재검토한다.
