1. 구현 제어 상태

상태: 구현 완료 · 운영 연결 보류 · 승인 기준: G1-A app-only CI/CD · 개발자 운영 이해: 미실시

이 기록은 승인된 설계와 실제 변경·검증 결과를 분리해 추적한다. 구현 중 설계의 material decision이나 DB 접근 범위가 바뀌면 구현을 중지하고 설계 재승인을 받는다.

2. 승인 범위와 불변식

이번 구현에서 허용·금지되는 경계
구분계약
허용.github/workflows/ci.yml, Dockerfile의 digest pinning, cloudbuild.yaml, app-only release runbook, 구현 통제 문서와 승인 문서의 상태 기록.
허용Artifact Registry app image, Cloud Run no-traffic revision, revision tag GET /health smoke. traffic 전환·이전 revision rollback은 운영자 승인 후 별도 명령으로만 다룬다.

불변식CI는 GCP credential을 갖지 않고, CD는 $COMMIT_SHA/digest artifact를 사용하며, target preflight가 통과되지 않으면 image push를 하지 않는다. smoke는 정적 /health만 호출하고 초기 Cloud Build는 smoke 후 traffic을 바꾸지 않는다.

5. 구현 이슈 등록부

미해결 이슈와 조치 조건
ID·상태영향최소 조치
I1 · open · P1 read-only preflight에서 기존 mogak-spring과 backend-core는 asia-northeast3에 있고, asia-northeast1에는 해당 repository가 보이지 않았다. 실제 Cloud Run service명, Tokyo repository, runtime service account와 trigger 권한은 미확정이다. 설정은 이제 모든 target 값을 명시하도록 요구하고, build·push 전에 같은 region의 기존 resource를 확인한다. 기존 Seoul service를 Tokyo로 옮길지 새 service를 만들지 별도로 결정한다. production trigger 활성화 전 IAM review와 substitution 확정을 수행한다. preflight가 실패하면 resource를 자동 생성하지 않고 build·push도 시작하지 않는다.
I2 · open · P2 Cloud Build build 간 동시 배포 순서는 이 설정만으로 보장되지 않는다. bootstrap approval에서 최신 commit만 승인한다. 무인 CD는 별도 concurrency/deployment lock 설계 후 다룬다.
I3 · open · P1 기존 main trigger는 read-only 확인상 기본 Compute SA를 사용하고 approval 설정이 출력되지 않았다. 기존 trigger를 수정하기 전 deployer/runtime SA 분리와 approval 정책을 별도 검토·승인한다. 이번 작업에서는 trigger와 IAM을 변경하지 않았다.

7. 잔여 위험과 운영 전 확인

  • 실제 GCP preflight 전에는 service명·repository·runtime SA를 추정해 배포하지 않는다. Cloud Build 자체도 placeholder와 region 불일치를 build·push 전에 거부한다.
  • Cloud Run custom domain은 smoke 대상이 아니다. 새 revision tag URL을 사용하고, domain/DNS/certificate는 별도 운영 설정으로 확인한다.
  • revision tag는 rollback window 동안 유지하고 이후 runbook으로 제거한다. revision 삭제는 자동화하지 않는다.
  • 현재 /health는 정적 응답이지만, 향후 DB query/write를 추가하면 smoke 안전성 재검토가 필요하다.

구현 파일과 control 기록을 다시 읽어 승인 범위, artifact 고정, step 순서, placeholder fail-safe, DB 금지 경계를 대조한다.

리뷰 finding
ID·상태관찰된 사실영향·최소 조치
R1 · resolved · 운영 연결 보류 cloudbuild.yaml이 target preflight, image build/push, digest 조회, no-traffic deploy, ID token smoke까지만 소유한다. 실제 Tokyo service/repository/runtime SA/IAM은 아직 확정되지 않았고, 운영 trigger와 traffic은 변경하지 않았다. G1-A를 반영해 YAML을 최소화했다. traffic/수동 rollback/tag cleanup은 운영 runbook의 별도 명령으로 둔다. 실제 GCP 연결 전 read-only preflight와 IAM 검토가 필요하다.
R2 · open · P1 · blocker (guard mitigated) cloudbuild.yaml은 _REGION, _AR_REPOSITORY, _SERVICE, _RUNTIME_SERVICE_ACCOUNT를 모두 __SET_IN_TRIGGER__로 시작하게 하고, build·push 전에 placeholder를 거부한다. 이어서 지정 region의 기존 repository·Cloud Run service·runtime service account를 read-only로 describe한다. 이전 read-only preflight에서는 기존 service와 backend-core repository가 asia-northeast3에 있었고 Tokyo repository는 확인되지 않았다. 잘못된 region이나 없는 service를 무심코 생성하는 경로는 preflight로 차단했다. 다만 실제 Tokyo service/repository/runtime SA와 trigger substitution은 아직 확정되지 않았으므로 운영 blocker는 남아 있다. 실제 target 확인 전에는 새 service bootstrap이나 production trigger 활성화를 하지 않는다.
R3 · open · P1 · blocker 현재 trigger identity와 IAM은 저장소에 고정되어 있지 않고, 이전 preflight상 기존 trigger는 기본 Compute SA를 사용하며 approval 여부도 미확정이다. 그런데 cloudbuild.yaml은 Artifact Registry push, Cloud Run deploy with --service-account, tagged revision ID-token smoke를 수행한다. 전용 Cloud Build SA에 repository-level Artifact Registry Writer, Cloud Run deploy 권한, target preflight read 권한, runtime SA에 대한 Service Account User, smoke caller의 iam.serviceAccounts.getOpenIdToken (최소 roles/iam.serviceAccountOpenIdTokenCreator), 대상 service의 Cloud Run Invoker가 없으면 push/deploy/smoke가 실패한다. 반대로 기본 SA에 광범위한 권한을 부여하면 least privilege를 위반한다. 전용 SA·최소 IAM·trigger approval을 검토하고 실제 no-traffic smoke 전까지 운영 trigger를 활성화하지 않는다.
R4 · fixed · P2 · non-blocking risk workflow action은 full SHA로 고정되어 있고, cloudbuild.yaml의 docker/cloud-sdk builder와 Dockerfile의 node:24.18-alpine base image도 검토된 digest로 고정했다. 현재 build executor와 Node base image가 tag 이동으로 바뀌지 않는다. digest 갱신은 별도 dependency update review와 함께 수행한다.
R5 · open · P2 · non-blocking risk build ID prefix를 포함한 고유 verify tag를 사용하고, revision·tag·smoke URL·digest를 build log에 출력한다. docs/runbooks/cloud-run-app-only-release.md가 이전 100% revision 확인, tag 기반 update-traffic, 앱 rollback, rollback window 후 tag 제거를 규정한다. 운영자가 동일 build의 candidate를 정확히 선택하고 tag collision을 피할 수 있다. revision 삭제는 rollback 불능이 되므로 자동화하지 않고, tag cleanup은 승인된 보존 정책 후 수동 실행한다. 다만 보존 기간 자체는 서비스 owner가 production 전에 정해야 하므로 P2 잔여 이슈로 남긴다.

추가 잔여 위험: /health는 DB-free 정적 응답이므로 container startup과 HTTP 경계만 검증하고 production DB 연결성은 증명하지 않는다. 이는 DB 보호를 위한 의도된 범위지만, DB read-only smoke를 도입할 때는 별도 안전 설계가 필요하다.

검증 한계: YAML parser, yamllint, Cloud Build shell syntax, G1-A step/order·target boundary·image pinning, HTML syntax, pnpm verify:local --dry-run은 통과했다. 이전 application static gates도 통과했지만, Docker daemon 미실행으로 실제 runtime image/local integration과 GCP deploy/smoke는 실행하지 못했다.

현재 판정: blocker 있음. 저장소 설정과 운영 handoff는 개선됐지만, R2의 실제 GCP target과 R3의 dedicated IAM/approval을 해결하기 전에는 production trigger 활성화나 traffic 변경을 승인할 수 없다. R5의 보존 기간도 production 전 owner가 확정해야 한다.

10. 다음 행동

  1. 새 target preflight와 image pinning을 포함한 정적 boundary·YAML·shell 검증과 저장소 local-gate를 기록한다.
  2. GCP mutation 없이 실제 Tokyo service·repository·runtime SA·trigger 권한·approval을 read-only로 확인하고 substitutions를 채운다.
  3. 운영 trigger는 dedicated deployer/runtime SA와 approval 정책을 확인한 뒤 첫 no-traffic smoke에만 사용한다.
  4. traffic 전환·rollback·tag cleanup은 운영 runbook의 승인 절차로 검증하며 revision 삭제는 자동화하지 않는다.
