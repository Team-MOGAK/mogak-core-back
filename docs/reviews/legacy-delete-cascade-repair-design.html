레거시 삭제 연쇄 복구 설계

목적
운영의 레거시 PostgreSQL에서 모다랏·모각·조각은 삭제하되, 연결된 게시글과 게시글 하위 데이터는 보존하면서 삭제가 완료되게 한다.
사용자
모다랏·모각·조각을 삭제하는 로그인 사용자와 운영 배포 담당자
문제
Cloud Run revision mogak-spring-00029-7xx에서 DELETE modarat가 DB 제약 오류로 실패하며, 게시글은 조각 삭제 뒤에도 남겨야 한다.
핵심 흐름
삭제 요청 → 소유권 확인 → 조각·일정·실행 삭제 → 게시글의 이전 실행 ID는 값으로 보존 → 원본 삭제 → 2xx 응답 및 목록 갱신

생성: 2026-08-17 · 갱신: 2026-08-17 · 승인: 2026-08-17 16:45 KST

근거 · 변경 모델 · 불변조건 · 실패·복구 · 자체 확인 · 승인

관측 근거와 범위

운영 로그는 DELETE /api/modarats/7가 500으로 끝났고, 소유 조건이 포함된 다음 원본 삭제가 실패했음을 보인다. 배포 revision은 mogak-spring-00029-7xx, commit은 5dd94ab64f5b288a7dc219f39f6b0a502ba8fda5다.

delete from "modarat" where ("modarat"."modarat_id" = $1 and "modarat"."user_id" = $2) returning "modarat_id"

애플리케이션 스키마는 modarat → mogak → jogak → daily_jogak → post를 모두 ON DELETE CASCADE로 선언한다. 이는 새 요구사항과 다르다. post.daily_jogak_id는 숫자 참조값으로 남기되 FK constraint를 제거해야 한다. 운영은 기존 Spring 테이블을 사용하며, 호환 스크립트는 새 일정 테이블의 FK만 생성하고 기존 체인의 실제 FK 삭제 규칙을 교정하지 않는다.

제안 변경 모델

  1. 운영 DB 카탈로그에서 modarat부터 post_like까지 실제 FK와 confdeltype을 읽어 원인 constraint를 확인한다.
  2. 호환 마이그레이션에 멱등적인 FK 교정 단계를 추가한다. modarat → mogak → jogak → daily_jogak와 일정 체인은 cascade로 보정하되, post.daily_jogak_id의 FK는 제거한다.
  3. 게시글의 이미지 메타데이터·댓글·좋아요는 post를 부모로 계속 cascade한다. 조각·모각·모다랏 삭제 후 post와 이 하위 데이터는 남고, 과거 daily_jogak_id 값만 고아 참조값으로 남는다.
  4. GET /api/posts/:postId는 상위 실행·조각·모각을 LEFT JOIN한다. 상위 데이터가 있으면 기존 mogakId, jogakId, targetDate를 반환하고, 삭제됐다면 세 필드를 null로 반환한다.
  5. 조각·날짜로 게시글을 찾는 API와 모각별 게시글 목록은 원본 조각·모각이 존재할 때만 의미가 있으므로, 삭제된 원본의 게시글을 그 경로에서 재노출하지 않는다. 소셜·지역 피드, 게시글 상세, 게시글 수정·삭제·댓글·좋아요는 계속 동작한다.
  6. 제약 교정 전후 모두 원인 constraint 이름을 로깅해 다음 운영 장애의 진단 가능성을 높인다. 개인정보·요청 본문은 기록하지 않는다.

비범위: soft delete, 보관함, 외부 Storage 객체 삭제, API 경로·응답 계약 변경, 데이터 보존 정책 변경.

결정과 불변조건

삭제 경계 결정표
항목결정이유
삭제 방식조각 계층까지만 DB FK cascade, post의 실행 FK는 제거일정·실행은 삭제하면서 커뮤니티 게시글은 보존한다.
원자성한 SQL 삭제의 트랜잭션 의미를 보존부분 삭제 후 실패를 만들지 않는다.
소유권현행 user_id 소유 조건 유지다른 사용자의 데이터를 삭제할 수 없다.
삭제 범위모다랏·모각·조각은 일정·실행까지 삭제, post·이미지·댓글·좋아요는 보존게시글의 과거 실행 ID는 FK가 아닌 값으로 유지한다.
게시글 상세 계약상위 원본이 없으면 mogakId·jogakId·targetDate를 null로 반환게시글·댓글 열람을 유지하면서 삭제된 조각을 가리키는 잘못된 식별자를 응답하지 않는다.

실패 처리·복구·검증

운영 위험: FK 재생성은 잠시 잠금을 잡을 수 있다. 트래픽이 낮은 시점에 배포하고, 사전 카탈로그 조회 결과가 예상과 다르면 마이그레이션을 중단한다. 데이터 행을 삭제하거나 변환하지 않는다.
  • 사전: pg_constraint 조회로 실제 제약명과 삭제 규칙을 기록한다.
  • 검증: 하위 일정·실행·게시글·댓글·좋아요·이미지가 있는 fixture에서 조각, 모각, 모다랏을 각각 삭제한다. 일정·실행은 0건, post와 게시글 하위 행은 남아 있어야 한다. 이후 GET /api/posts/:postId가 200과 세 nullable 상위 필드를 반환하는지 확인한다.
  • 장애 시: API는 500 대신 DB constraint 식별자를 가진 안전한 서버 로그를 남긴다. 배포 문제면 이전 revision으로 롤백하고, 스키마 교정 SQL은 이미 적용된 항목을 재적용하지 않는다.
