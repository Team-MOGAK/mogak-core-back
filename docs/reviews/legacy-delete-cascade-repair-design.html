레거시 삭제 연쇄 복구 설계

목적
운영의 레거시 PostgreSQL에서 모다랏·모각·조각은 삭제하되, 연결된 게시글과 게시글 하위 데이터는 보존하면서 삭제가 완료되게 한다.
사용자
모다랏·모각·조각을 삭제하는 로그인 사용자와 운영 배포 담당자
문제
Cloud Run revision mogak-spring-00029-7xx에서 DELETE modarat가 DB 제약 오류로 실패하며, 게시글은 조각 삭제 뒤에도 남겨야 한다.
핵심 흐름
삭제 요청 → 소유권 확인 → 애플리케이션 트랜잭션에서 자식부터 명시 삭제 → 게시글의 이전 실행 ID는 값으로 보존 → 원본 삭제 → 2xx 응답 및 목록 갱신

생성: 2026-08-17 · 갱신: 2026-08-17 · 재승인: 2026-08-17 18:00 KST

근거 · 변경 모델 · 불변조건 · 실패·복구 · 자체 확인 · 승인

관측 근거와 범위

운영 로그는 DELETE /api/modarats/7가 500으로 끝났고, 소유 조건이 포함된 다음 원본 삭제가 실패했음을 보인다. 배포 revision은 mogak-spring-00029-7xx, commit은 5dd94ab64f5b288a7dc219f39f6b0a502ba8fda5다.

delete from "modarat" where ("modarat"."modarat_id" = $1 and "modarat"."user_id" = $2) returning "modarat_id"

현재 PR은 modarat → mogak → jogak → daily_jogak 및 일정 체인을 ON DELETE CASCADE로 보정한다. 이는 새 요구사항과 다르므로 이번 조각 계층 삭제 경로에는 DB cascade를 사용하지 않고, 애플리케이션이 자식부터 명시 삭제해야 한다. post.daily_jogak_id는 숫자 참조값으로 남기되 FK constraint를 제거한다. 기존 게시글 삭제의 하위 FK 정책은 이번 범위에서 변경하지 않는다.

제안 변경 모델

  1. 운영 DB 카탈로그에서 조각 계층과 일정의 실제 FK·confdeltype을 읽어 해당 경로에 cascade constraint가 없는지 확인한다.
  2. 호환 SQL은 FK를 생성·교체하지 않는다. post.daily_jogak_id FK를 제거하고, 필요한 중복 방지 규칙만 UNIQUE CONSTRAINT로 선언한다. 별도 일반 index는 이번 범위에서 추가하지 않는다.
  3. 모다랏·모각·조각 삭제 repository는 한 트랜잭션에서 jogak_schedule_weekdays → jogak_schedules → daily_jogak → jogak → mogak → modarat 순으로 대상 범위의 행을 명시 삭제한다. 모각·조각 단건 삭제도 같은 순서의 필요한 하위 집합을 사용한다.
  4. 게시글의 이미지 메타데이터·댓글·좋아요는 post를 부모로 계속 cascade한다. 조각·모각·모다랏 삭제 후 post와 이 하위 데이터는 남고, 과거 daily_jogak_id 값만 고아 참조값으로 남는다.
  5. GET /api/posts/:postId는 상위 실행·조각·모각을 LEFT JOIN한다. 상위 데이터가 있으면 기존 mogakId, jogakId, targetDate를 반환하고, 삭제됐다면 세 필드를 null로 반환한다.
  6. 조각·날짜로 게시글을 찾는 API와 모각별 게시글 목록은 원본 조각·모각이 존재할 때만 의미가 있으므로, 삭제된 원본의 게시글을 그 경로에서 재노출하지 않는다. 소셜·지역 피드, 게시글 상세, 게시글 수정·삭제·댓글·좋아요는 계속 동작한다.
  7. 제약 교정 전후 모두 원인 constraint 이름을 로깅해 다음 운영 장애의 진단 가능성을 높인다. 개인정보·요청 본문은 기록하지 않는다.

비범위: soft delete, 보관함, 외부 Storage 객체 삭제, 일반 index 설계, API 경로·응답 계약 변경, 데이터 보존 정책 변경.

결정과 불변조건

삭제 경계 결정표
항목결정이유
삭제 방식조각 계층에는 DB FK cascade 없음; 애플리케이션이 자식부터 명시 삭제삭제 범위와 실패 지점을 애플리케이션에서 통제한다.
원자성repository 트랜잭션 하나에서 자식 삭제와 부모 삭제를 수행부분 삭제 후 실패를 만들지 않는다.
소유권현행 user_id 소유 조건 유지다른 사용자의 데이터를 삭제할 수 없다.
삭제 범위모다랏·모각·조각은 일정·실행까지 삭제, post·이미지·댓글·좋아요는 보존게시글의 과거 실행 ID는 FK가 아닌 값으로 유지한다.
게시글 상세 계약상위 원본이 없으면 mogakId·jogakId·targetDate를 null로 반환게시글·댓글 열람을 유지하면서 삭제된 조각을 가리키는 잘못된 식별자를 응답하지 않는다.
중복 방지UNIQUE CONSTRAINT만 추가하고 일반 index는 추가하지 않음중복 데이터 방지만 이번 목적에 필요하며, 성능 index 설계는 별도 근거가 필요하다.

실패 처리·복구·검증

운영 위험: 명시 삭제 순서가 하나라도 틀리면 FK 위반으로 전체 트랜잭션이 롤백된다. 트래픽이 낮은 시점에 SQL을 적용하고, 조각 계층의 사전 카탈로그 조회에서 cascade가 남아 있으면 마이그레이션을 중단한다.
  • 사전: pg_constraint 조회로 조각 계층의 실제 제약명과 삭제 규칙을 기록하고, 대상 FK의 confdeltype이 cascade가 아님을 확인한다.
  • 검증: 하위 일정·실행·게시글·댓글·좋아요·이미지가 있는 fixture에서 조각, 모각, 모다랏을 각각 삭제한다. 애플리케이션 트랜잭션 뒤 일정·실행은 0건, post와 게시글 하위 행은 남아 있어야 한다. 이후 GET /api/posts/:postId가 200과 세 nullable 상위 필드를 반환하는지 확인한다.
  • 장애 시: 명시 삭제 중 어느 단계가 실패해도 트랜잭션 전체를 롤백한다. API는 DB constraint 식별자를 가진 안전한 서버 로그를 남긴다.
