구현 기준

승인된 범위는 users.email 유니크 제거, (provider, providerUserId) exact identity 유지, PENDING token-role 유지와 TOKEN_REFRESH_REQUIRED(HTTP 403 / T006) 분기, 가입 완료 race의 선착순·멱등 처리와 회귀 검증이다. G1-A의 T006 프런트 release gate와 G2-C의 stale 가입 요청 T005 처리 계약도 포함한다. 별도 onboarding token과 타 세션 일괄 폐기는 금지한다.

현재 구현 (as-built)

  1. libs/modules/src/infrastructure/database/schema/users/user.table.ts에서 이메일 유니크를 제거하고 nickname 유니크만 유지했다. drizzle/0006_allow_duplicate_email_users.sql은 users_email_unique 제약을 삭제하며 journal idx 6에 등록했다. 이 migration은 변경이 한 줄인 수동 SQL·journal 기록으로 작성했다.
  2. AuthService와 AuthRepository는 이메일 사전 조회·충돌 예외를 사용하지 않는다. 생성 충돌은 social identity 유니크 제약으로만 판정하고, 충돌 후 (provider, providerUserId)를 재조회해 승자에게 세션을 발급한다. 따라서 같은 이메일의 다른 provider는 별도 사용자가 된다.
  3. AuthService.authenticateAccessToken은 JWT 검증과 세션 활성 여부만 확인하고 PENDING principal의 role을 바꾸지 않는다. 따라서 일반 access 요청마다 DB role을 재조회하지 않는다. RegisteredUserGuard는 PENDING이면 TOKEN_REFRESH_REQUIRED(HTTP 403 / T006), 그 밖의 권한 부족은 기존 FORBIDDEN(T004)을 반환한다.
  4. UserService.join은 현재 사용자를 다시 읽는다. 이미 USER면 기존 가입 정보를 반환하면서 USER 세션을 재발급하고 현재 세션을 교체한다. current session이 이미 사라진 race는 비활성 세션인 LOGOUT_TOKEN(HTTP 403/T005)으로 변환한다. PENDING이면 UserRepository.completeRegistration의 UPDATE ... WHERE role = 'PENDING'가 첫 완료를 확정한다.
  5. 동시 가입의 후속 요청은 업데이트 행이 없을 때 사용자 행을 잠금 조회한다. 이미 USER가 되었으면 동의 중복 기록 없이 세션만 멱등 교체한다. 동일 currentSessionId가 먼저 교체되어 삭제된 경우에는 CurrentSessionNotActiveException을 거쳐 HTTP 403/T005로 반환하고, 아직 완료되지 않았거나 상태가 비정상이면 persistence 오류로 처리한다. nickname 사전 조회는 제거해 DB 유니크 제약이 race를 판정하게 했다.
  6. 실제 PostgreSQL 경계를 고정하는 test/database/auth-concurrency.integration.spec.ts와 test/database/users-concurrency.integration.spec.ts를 추가했다. 동일 identity 로그인, 서로 다른 세션의 동시 가입 완료, 동일 세션의 중복 가입 완료, logout과 replaceSession 경합을 각각 검증한다. replaceSession은 current session을 DELETE ... RETURNING으로 먼저 삭제하고 정확히 1행일 때만 replacement를 insert하며, 0행이면 persistence 오류로 transaction을 rollback한다. 가입 완료 loser가 이미 USER를 확인한 뒤 맞닥뜨린 0행도 같은 T005 경계로 전달한다.

검증 해석

영향 범위의 타입·정적 검사와 전체 Jest 회귀는 통과했다. 실제 DB migration·다중 요청 통합 검증과 빌드는 환경을 준비한 뒤 별도 운영 게이트로 남긴다.

검증 공백

  1. 실제 PostgreSQL에서 ALTER TABLE "users" DROP CONSTRAINT "users_email_unique" 적용 전후 검증 없음. pnpm db:generate는 비대화형 실행에서 prompt로 중단되어 생성 결과를 사용하지 않았다.
  2. 같은 social identity 로그인과 같은 PENDING user 가입의 실제 동시 요청 통합 테스트는 test/database/auth-concurrency.integration.spec.ts와 test/database/users-concurrency.integration.spec.ts로 추가했지만, PostgreSQL 연결 부재로 아직 실행하지 않았다.
  3. replaceSession의 logout 경합에서 삭제된 current session을 replacement가 되살리지 않도록 삭제 선행·영향 행 검사를 구현하고 단위 테스트로 확인했다. 실제 DB lock 경합 결과는 PostgreSQL 실행 후 확정한다. 가입 완료 loser의 동일 세션 0행은 LOGOUT_TOKEN(HTTP 403/T005)으로 매핑하며 서버에 replacement/revocation 상태를 추가하지 않는다.
  4. worktree에 ts-loader가 없어 Nest build 게이트를 실행하지 못했다.
  5. 같은 email을 가진 서로 다른 provider의 두 계정 생성은 서비스 단위 테스트로만 확인했다. 실제 PostgreSQL에서 users email 제약 제거와 provider별 독립 insert를 함께 검증하는 케이스는 migration 게이트와 통합 테스트에 추가해야 한다.

잔여 위험

이메일은 더 이상 사용자 식별자가 아니다. 새 코드가 email로 사용자를 단건 조회하거나 provider를 생략하면 다른 계정으로 연결할 수 있으므로, 계정 조회·세션 발급·복구 경로는 반드시 userId 또는 exact social identity를 사용해야 한다.

migration 적용 전에는 기존 users_email_unique 제약이 남아 정책과 DB가 불일치한다. migration 적용 실패 시 배포를 중지하고 백업·제약 상태를 먼저 확인한다.

설계 차이

registrationContinuation 표식은 현재 구현에 남기지 않았고, stale PENDING token은 서버의 명시적 T006 계약으로 refresh 경계를 전달한다. 2026-08-30 설계 승인에 따라 통합 테스트는 동시성 경계를 고정하며, 프런트는 T006에 한해 refresh 1회와 원 요청 1회만 재시도해야 한다. 동일 세션의 stale /join은 T005가 될 수 있으므로 /join·/refresh를 반복하지 않고 같은 authGeneration·joinAttemptId의 single-flight 결과와 그 결과가 저장한 공용 pair만 확인한다.

AUTH-001 · fixed Blocker UserService.join에서 persisted USER인 경우 access token의 서명된 current.role === 'PENDING'일 때만 세션을 재발급하도록 제한했다. AuthService.authenticateAccessToken은 PENDING token을 DB role로 승격하지 않는다. USER 전용 API는 RegisteredUserGuard가 T006으로 명시한다. 일반 USER access token은 USER_ALREADY_EXISTS로 거부되어 refresh token 교환 경계를 우회하지 않는다. stale PENDING 재개, 일반 USER 거부, PENDING 전용 T006 분기를 각각 단위 테스트한다.
MIG-001 · open Blocker drizzle/0006_allow_duplicate_email_users.sql은 제약 삭제만 기록되어 있고 실제 PostgreSQL 적용·중복 email insert·rolling rollout 순서는 검증되지 않았다. 새 코드의 AuthRepository.createAccount는 email unique 충돌을 더 이상 별도 처리하지 않는다. migration보다 애플리케이션을 먼저 배포하면 같은 email의 다른 provider 가입이 generic persistence 오류로 실패할 수 있다. 백업 후 migration 선적용, 제약 상태 확인, 실제 중복 insert와 social identity unique 검증을 배포 게이트로 추가해야 한다.
AUTH-002 · mitigated Non-blocking risk 기존 UserRepository.replaceSession은 replacement session을 먼저 insert하고 current session delete의 영향 행 수를 확인하지 않았다. logout 선행 경합을 재현하는 PostgreSQL integration test를 추가했다. 동일 transaction에서 current session을 먼저 삭제하고 1행일 때만 replacement를 insert하도록 보강했다. current session이 없으면 예외와 transaction rollback으로 replacement를 남기지 않는다. 단위 테스트는 통과했으며 실DB lock 경합 검증만 남았다.
AUTH-003 · mitigated 릴리스 의존 서버는 RegisteredUserGuard에서 PENDING token을 HTTP 403 / T006으로 구분하지만, 이 worktree에는 공통 HTTP client 구현이 없다. migration handoff는 T006에 대해 single-flight refresh 1회와 원 요청 1회 재시도를 요구한다. G1-A를 확정하고 서버의 T006 guard·HTTP contract test와 모바일 handoff를 고정했다. 프런트 interceptor는 별도 릴리스 gate로 남는다. T006 전용 single-flight refresh 1회, 원 요청 1회 재시도, 두 번째 T006의 가입 화면 이동, T004 비-refresh를 프런트 출시 전에 확인해야 한다.
AUTH-004 · implemented Non-blocking risk 같은 currentSessionId를 가진 두 POST /api/users/join이 guard를 통과해 동시에 실행되면, 후속 요청은 USER 행을 확인한 뒤 replaceSession의 DELETE ... RETURNING에서 0행을 받을 수 있다. 이 경로를 CurrentSessionNotActiveException으로 유지하고 HTTP 403 / T005로 매핑했다. 단위·HTTP 테스트와 동일 세션 PostgreSQL integration test를 추가했다. G2-C 계약에 따라 두 번째 응답은 generic 500이 아닌 T005일 수 있다. 클라이언트는 /join을 auth context별 joinAttemptId로 single-flight 직렬화하고, T005에서 같은 authGeneration의 진행 결과와 그 결과가 저장한 공용 pair만 확인한다. 실제 PostgreSQL 동시성 실행은 DATABASE_URL 게이트다.
AUTH-005 · resolved Non-blocking risk POST /api/users/join은 AccessTokenGuard를 먼저 통과한다. 첫 요청이 replaceSession으로 기존 session을 삭제한 뒤 도착한 동일 token의 후속 요청은 AuthService.authenticateAccessToken에서 LOGOUT_TOKEN(HTTP 403/T005)으로 종료될 수 있다. 이 결과는 새 USER replacement session의 로그아웃이 아니라 오래된 token의 비활성화다. service까지 도달한 0행도 같은 CurrentSessionNotActiveException 경계로 매핑한다. 응답은 세션 교체 타이밍에 따라 T005가 될 수 있다. 프런트가 이를 즉시 전역 로그아웃으로 처리하면 첫 요청의 최신 pair를 지울 수 있으므로, join single-flight와 T005 수신 시 동일 authGeneration·joinAttemptId 결과만 복구하는지 별도 릴리스 gate로 검증한다. 서버에 replacement/revocation 상태나 tombstone을 추가하지 않는다.
DOC-001 · resolved Non-blocking 기존 handoff와 fallback 설계·구현 문서가 users.email UNIQUE 및 같은 이메일의 다른 identity에 대한 U012 계약을 설명하고 있었다. handoff는 부분 대체 상태와 현재 문서 링크로 갱신했고, 이전 fallback HTML은 대체됨을 표시했다. 현재 provider 분리·T006·G2-C(T005) 계약은 이 문서와 최신 설계 문서를 단일 기준으로 삼는다.
VER-001 · resolved Non-blocking risk 과거 전체 suite에서 posts multipart 테스트의 일회성 socket hang up이 발생했다. 2026-08-30 전체 Jest 재실행은 55 suites·269 tests로 통과했다. 실제 DB migration·동시 요청 integration test는 DATABASE_URL 부재로 실행하지 못했다. 전체 Jest 회귀는 녹색으로 확인됐다. DB migration과 PostgreSQL 동시성 검증은 별도 운영 게이트로 남긴다.

리뷰 판단

배포 blocker 있음. AUTH-001은 수정·재검증되어 해소됐다. AUTH-002는 삭제 선행·영향 행 검사로 완화됐지만 실DB race 검증이 남아 있다. AUTH-003은 T006 서버·handoff 계약을 고정했으며 프런트 interceptor release gate가 남아 있다. AUTH-004는 service/repository 경계의 동일 세션 후속 요청을 403/T005로 매핑하도록 정리했다. AUTH-005는 서버 상태를 늘리지 않고 G2-C 프런트 계약으로 해소했지만, auth generation·join attempt correlation을 포함한 single-flight와 stale T005 처리 검증이 남아 있다. 실제 PostgreSQL 실행과 MIG-001 migration 적용·rollout 순서는 배포 blocker로 유지한다. DOC-001은 superseded 표기와 현재 문서 링크로 해소했다. 전체 Jest·정적 검증은 통과했으며, 통합 DB 검증은 환경 게이트다.
