목표와 표준 모델

독립적으로 선택 가능한 JSON 리소스 필드의 일부 수정은 PATCH와 application/merge-patch+json을 정본 계약으로 쓴다. RFC 7396 문서 병합을 DB 객체에 기계적으로 적용하지 않는다. 요청을 패치 의도로 해석하고 소유권·현재 상태·전체 도메인 불변식을 검증한 뒤 한 트랜잭션으로 저장한다.

비목표: issue #6이 제외한 Jogak 동일 시작일 버그 자체, 실행·일정 이력 재작성, 모든 API의 일괄 PATCH 전환, multipart 이미지의 JSON화, 최소 지원 모바일 버전의 임의 결정.

현재 갭과 목표 계약

코드 조사 기준 수정 API 분류
경로 현재 계약·갭 결정
PUT /api/modarats/:id title·color 모두 필수지만, 사용자는 두 필드 중 일부만 독립적으로 편집할 수 있다. PATCH 전환. 같은 배포에서 기존 PUT route를 제거한다. title과 color를 독립 scalar로 PATCH하고, 누락 필드는 보존한다.
PUT /api/mogaks/:id title 필수, category·color 생략 시 보존이 아니라 재해석·null reset될 수 있다. 실제 UI가 일부 속성만 바꾸면 의도치 않은 값 손실 위험이 있다. PATCH 전환. 같은 배포에서 기존 PUT route를 제거한다. title·color는 독립 scalar, category는 { type: 'SYSTEM', code: string } 또는 { type: 'CUSTOM', name: string } 전체를 보내는 원자적 중첩 객체로 한다. type·필수 값이 맞지 않거나 두 형태의 필드를 혼합하면 400으로 거부한다.
PATCH /api/jogaks/:id title 또는 전체 schedule; start는 요청 불가. schedule은 단순 중첩 병합이 아니라 일정 이력 도메인 전이다. PATCH 유지하되 도메인 PATCH 예외로 문서화. whole weekdays 교체·불변 start·후속 일정 경계를 고정한다.
PUT /api/posts/:id, PUT /comments/:id 변경 가능한 필드는 contents 하나이며 필수다. PUT 유지. PATCH 이득이 없다.
PUT /api/users/profile/nickname, /job 독립 scalar 하위 리소스의 완전한 교체다. PUT 예외로 유지. 통합 profile PATCH는 후속 후보만 둔다.
PUT /api/users/profile/image multipart; 누락 파일은 삭제다. 비 JSON 예외로 PUT 유지. 의도치 않은 삭제·저장소 보상을 별도 검증한다.
PUT /api/users/consents 선택 항목을 upsert하며 생략은 빈 배열이 된다. 전체 컬렉션 교체가 아니다. PATCH 전환 금지. 집합 전체 교체 PUT 또는 명시적 batch command 중 하나를 별도 결정한다.
PATCH /api/users/marketing-consent 두 boolean 중 하나 이상; omission은 변경 없음, null 거부. 첫 RFC 7396 기준 구현 후보. canonical media type과 empty patch 정책을 보강한다.
공통 갭: CORS와 Zod strict 입력은 있으나 application/merge-patch+json 강제, Accept-Patch, canonical Content-Type, 415 오류, legacy 전환 지표가 없다.

제안 규칙과 불변식

Merge Patch 프로필
항목 결정·테스트 기준
미디어 타입 정본 PATCH는 application/merge-patch+json 및 Accept-Patch. 배포 즉시 application/json을 포함한 다른 PATCH media type은 415로 거부한다. 비교는 소문자화된 media type만 사용하고 ; charset=utf-8 같은 parameter는 허용한다.
경계 구현 각 controller에서 method·헤더 문자열을 직접 비교하지 않는다. @MergePatch() 복합 decorator가 PATCH route와 정책 metadata를 선언하고, 공통 guard가 media type을 검증하며, interceptor가 Accept-Patch를 응답에 붙인다. 이전 PUT 경로는 중앙 registry 기반 tombstone handler로 405 Method Not Allowed와 Allow: PATCH를 응답한다.
누락·빈 객체 누락은 변경 없음, 빈 객체는 400. 모든 PATCH는 최소 한 개의 허용 변경 필드를 요구한다.
null 기본 거부. 명시 nullable로 선언한 필드만 제거 의미를 가진다. 현재 RFC 대상은 null 제거를 열지 않아 400 INVALID_PARAMETER.
중첩·배열 schedule은 원자적 도메인 교체; RFC 대상 배열은 전체 교체이며 요소 단위 merge 금지. consent 배열은 PATCH 대상이 아니다.
Mogak category category가 없으면 기존 카테고리를 보존한다. 있으면 SYSTEM은 활성 값 테이블의 code를, CUSTOM은 name을 반드시 가진 하나의 형태만 허용한다. 두 표현을 모두 받던 기존 평면 요청은 이 PATCH 계약에서 지원하지 않는다.
Jogak scheduleType schedule.scheduleType은 요청 스키마에서 ONCE 또는 WEEKLY만 허용한다. controller mapper는 제거하고 요청 DTO를 application command로 직접 전달한다. 허용하지 않는 값은 서비스 오류가 아니라 요청 검증 오류(400 Z005)로 거부한다.
불변·서버 소유 id, owner, timestamps, 실행 이력, Jogak effectiveFrom은 무시하지 않고 400으로 거부한다.
오류·관측 400 형식/불변, 401/403, 404, 415 media type. route·media type·rejection을 구조화 계수로 남긴다.

이 결론이 실패한다면: 모든 PUT을 PATCH로 일괄 변경해 단일 scalar·multipart·동의 집합의 의도를 흐리고 호환 비용만 늘리는 경우다. 그래서 PUT이 진짜 전체 교체인 곳은 남긴다.

호환·배포와 후속 분할

  1. RFC/OpenAPI에 위 분류·예시·오류를 확정한다.
  2. 서버가 canonical PATCH만 지원하도록 배포한다. Modarat·Mogak의 이전 PUT은 중앙 tombstone 정책으로 405와 Allow: PATCH를 응답하고, canonical이 아닌 PATCH media type은 415로 즉시 실패한다.
  3. 첫 구현은 marketing-consent, Modarat PATCH, Mogak PATCH, Jogak canonical화 순서다. consent collection 의미 재설계는 별도 승인 작업이다.
  4. 모바일 최소 버전·활성 호출 기준·Deprecation/Sunset 헤더는 사용하지 않는다. 이 변경은 서버와 클라이언트를 같은 릴리스 단위로 즉시 전환한다.
  5. 배포 전 모바일 요청을 PATCH와 canonical media type으로 바꾸고, 문서·계약 테스트를 같은 변경 단위에서 갱신한다.

결정/위험: 하위 호환·점진 전환은 하지 않는다. 구형 모바일이 독립 배포되어 새 서버에 접근하면 수정 요청이 즉시 실패한다. 따라서 서버 배포 전 해당 클라이언트의 요청 method와 Content-Type을 함께 바꾸는 것이 필수다.

검증 계획

  1. 계약: 대소문자·charset parameter를 포함한 canonical Content-Type, 비정본 415, 이전 PUT의 405/Allow, 빈 PATCH, unknown, null, 불변, 전체 배열·중첩 객체를 route별 검증한다.
  2. 회귀: 유지 PUT의 scalar/multipart/동의 검증과 소유권·멱등성을 확인한다.
  3. 관측: 405·415를 route별 집계하고 민감 본문 미기록을 검증한다.
  4. 문서: OpenAPI와 모바일 가이드의 null·배열 설명을 계약 테스트와 대조한다.

설계 승인 상태

approval-state: 부분 설계 승인됨 (2026-08-22 KST, 사용자 “ㄱㄱ”). 기존에 승인된 Mogak category: { code, name? } 계약을 tagged union { type: 'SYSTEM', code } | { type: 'CUSTOM', name }으로 바꾸므로 PATCH /api/mogaks/:mogakId의 category 계약에 한해서만 재승인이 필요하다. Modarat·Jogak·consent의 Merge Patch 분류와 공통 media type 규칙은 기존 승인을 유지한다. 이 변경은 Mogak을 호출하는 모바일 요청·OpenAPI·계약 테스트 갱신을 포함한다. 추가로 Jogak scheduleType의 허용값 검증을 controller Zod schema로 이동하고, 잘못된 값의 오류 코드를 400 Z005로 바꾸며 controller mapper를 제거한다. If-Match·ETag·버전 기반 낙관적 잠금은 JSON Merge Patch 계약의 범위 밖으로 제외한다.

이 문서는 Jogak 동일 시작일 일정 편집 설계와 목적·핵심 흐름이 달라 별도 RFC 기준 문서다. 승인 전에는 구현 코드·테스트 계약을 변경하지 않는다.
