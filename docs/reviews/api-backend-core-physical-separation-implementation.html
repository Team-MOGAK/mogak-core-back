API와 core/modules library 분리 구현 제어

목적
승인된 API/core/modules 물리 분리의 구현과 검증을 제어한다.
사용자
MOGAK API·batch 개발자와 배포·유지보수 담당자
문제
API 배포물 안에 HTTP API, Nest 독립 domain/application, Nest 기반 adapter가 함께 있어 재사용 경계가 흐리다.
핵심 흐름
API controller → core use case/port → modules adapter/DB, AppModule이 controller·guard와 backend module을 연결
기준 설계
설계 기준선, 2026-08-24 승인
강도 · 상태
Standard · 구현 및 회귀 검증 완료

승인 기준선

libs/core에는 Nest 독립 domain/application/port를, libs/modules에는 Nest 기반 adapter와 feature module을 둔다. API AppModule이 controller·guard를 등록하고 modules feature module을 import한다.

현재 구현

apps/api/src/core/**는 libs/core/src/core/**로, infrastructure와 feature provider module은 libs/modules/src/**로 이동했다. apps/api/src/composition/**은 제거했고 API controller·guard 등록은 apps/api/src/app.module.ts가 맡는다. API controller가 필요한 application service는 각 modules feature module이 export한다.

구현 상태

구현 및 회귀 검증 완료 — Nest workspace library 등록, alias·Jest·Drizzle 경로, 번들 빌드 의존성을 새 경로에 맞췄다.

이슈 등록

상태관찰·영향조치·검증
해결됨core 전체를 Nest 독립화하는 방향은 현재 adapter의 decorator·ConfigService 결합을 불필요하게 재작성하게 했다.이미 Nest 독립인 core와 Nest 기반 modules를 별도 library로 분리했다.
해결됨controller를 AppModule로 옮기자 sibling feature module에 있던 application service가 DI 범위 밖이 됐다.controller가 직접 주입하는 service를 feature module의 exports에 명시했다. health·rate-limit e2e 통과.

검증 증거

pnpm typecheck, architecture boundary test, lint, format check, pnpm build가 통과했다. Nest bundle은 기존처럼 dist/main.js를 생성한다. 개선 후 단일 프로세스 전체 회귀는 55 suites, 257 tests가 통과했다.

검증 공백

DB integration test는 로컬 DB가 필요한 별도 명령(pnpm test:integration)으로 남아 있다.

잔여 위험

core token과 modules provider binding의 identity·lifecycle을 보존해야 한다. API feature module은 AppModule이 복잡해질 때에만 후속으로 도입한다.
