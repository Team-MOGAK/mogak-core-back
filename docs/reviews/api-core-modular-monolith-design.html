API-Core 모듈러 모놀리스 분리 설계

목적
단일 Nest API 서버 내부에서 HTTP·프레임워크 어댑터와 비즈니스 core를 물리·의존성 측면에서 분리한다.
사용자
Mogak 백엔드를 유지·확장하는 개발자와 운영 담당자
문제
현재 feature별 application 서비스가 Nest DI, HTTP 예외, Express 업로드 타입을 직접 알아 core 경계가 불명확하다.
핵심 흐름
HTTP 요청 → API adapter의 검증·변환 → core use case와 port → infrastructure adapter → 기존 HTTP 응답·오류 형식

Standard

목표와 비목표

목표: 실행·배포 대상은 하나(apps/api)로 유지하면서, business rule·use case·port가 Nest, Express, HTTP, Drizzle을 import하지 않게 만든다.

성공 신호: core unit test는 Nest testing module 없이 실행되고, 기존 endpoint·상태 코드·오류 코드·응답 JSON·DB transaction 의미는 그대로다.

비목표: 마이크로서비스화, 별도 core 프로세스, DB 분리, API 버전 변경, 이벤트 버스·generic repository 도입, 모든 테이블의 기계적 entity화는 이번 범위에 넣지 않는다.

오류 경계 결정: core는 HTTP status를 모르는 feature-level CoreError 또는 reason union을 사용한다. API의 filter/mapper가 현재 AppErrorCode로 1:1 변환한다. 이 매핑표가 빠지면 같은 실패가 500으로 바뀔 수 있으므로, 이동보다 먼저 고정한다.

명시적으로 미루는 선택

Core를 별도 Nest app·별도 프로세스로 분리하지 않는다. 또한 현재 domain/entity 금지 정책을 이번 디렉터리/의존성 분리에서 뒤집지 않는다. entity 정본(Drizzle row 대 독립 모델)은 별도 설계에서 결정한다.

점진적 이관 계획

  1. 기준선과 앱 루트 전환: 현재 검증을 기록한 뒤 src/**를 apps/api/src/**로 구조 이동하고 nest-cli.json, TypeScript·Jest·Docker·scripts의 source root만 갱신한다. 이 단계는 경로 변경만 하며 API 동작을 바꾸지 않는다.
  2. 경계 디렉터리 도입: 이동한 feature의 presentation을 api/<feature>, repository/verifier/storage/database를 infrastructure/**, domain/application을 core/<feature>로 재배치한다. 기존 Nest module은 composition으로 모은다. 아직 decorator 제거 전에는 Core 후보 경로에 두지 않는다.
  3. Core 오류와 API 매핑: feature별로 core error/reason을 만들고, 현재 AppErrorCode와의 매핑을 API에 추가한다. Auth → Users → Mogaks → Posts → Social 순서로 characterization test와 endpoint test를 통과시키며 DomainException 사용을 제거한다.
  4. DI·입력 정화: service에서 @Injectable/@Inject를 제거하고 composition factory가 port 구현체를 주입한다. Express.Multer.File은 API가 BinaryUpload 같은 core 계약으로 바꾼다. 특히 UserService.updateProfileImage의 upload/delete 흐름을 core use case와 storage port로 보존한다.
  5. 컨텍스트 계약 정리: Posts가 직접 사용하는 Mogaks의 소유 확인 계약은 core/posts가 소유하는 gateway 또는 명시적 public contract로 바꾼다. Users/Auth의 principal·token 계약도 auth core 공개 계약으로 정한다. Social feed는 cross-context read model임을 유지하고 write-domain 모델로 승격하지 않는다.
  6. 강제와 마감: architecture test에 core outbound import 금지, API의 infrastructure 직접 호출 금지(허용된 composition 제외), 허용된 cross-context contract만 추가한다. 전체 회귀와 배포 이미지를 검증한다.

불변식과 실패 복구

  • 모든 기존 route, HTTP status, error code/message, JSON envelope를 golden controller/e2e test로 보존한다.
  • DB schema, migration history, foreign key, repository transaction 의미를 변경하지 않는다.
  • core 단위 테스트는 Nest module·Postgres·Express 없이 port fake로 실행한다.
  • 어느 feature든 한 slice가 실패하면 해당 slice의 import/오류 mapping만 되돌릴 수 있도록 feature별로 커밋·검증한다.

복구 방식: 이관 중 API 매핑에 없는 core error가 관찰되면 일반 500으로 숨기지 않는다. 테스트를 추가하고 해당 error mapping을 보완한 뒤 slice 검증을 재실행한다. DB migration은 포함하지 않으므로 DB 복구 작업은 발생하지 않는다.

압력 검사

이 결론이 실패한다면: 디렉터리만 옮기고 service의 Nest/HTTP 의존을 남겨 core라는 이름만 생기는 경우다.

완화: 각 feature 이동 완료 조건을 “core import ban 통과 + Nest 없는 unit test + controller 계약 회귀 통과”로 둔다.

가정 / 확신도: 현재 단일 API 배포와 DB를 유지한다는 가정은 높음. package manager workspace 전환, Docker build context, CI deploy 경로는 현 설정을 추가 조사해 1단계에서 확정한다.

Q1. Core에서 DB 저장이 필요할 때 올바른 호출 방향은?

Core는 port만 의존해야 API·Drizzle 교체와 독립 테스트가 가능하다.

다음: API와 Core의 오류 책임을 확인한다.

Q2. Core use case가 ‘게시물을 찾지 못함’을 판단하면 HTTP 404는 어디에서 정해져야 하나?

HTTP는 inbound adapter의 계약이다. API mapper가 기존 API 호환성을 보존한다.

다음: 물리적 분리의 실행 단위를 확인한다.

Q3. 이번 설계에서 apps/api와 core의 실행 형태는?

목표는 마이크로서비스가 아닌 단일 배포 단위의 modular monolith다.

다음: transport 타입 누수를 확인한다.

Q4. profile image 업로드를 core로 옮길 때 Express.Multer.File은 어떻게 다루나?

API가 transport adapter 역할을 맡고, core는 업로드·삭제의 business sequence만 유지한다.

다음: cross-context 의존을 확인한다.

Q5. Posts가 Mogaks의 소유 occurrence 확인이 필요할 때 허용할 방식은?

컨텍스트 간 협력은 필요한 능력만 노출해야 순환 의존과 내부 모델 누수를 막는다.

다음: API 호환 실패 시 복구 원칙을 확인한다.

Q6. 이관 뒤 core error 하나가 API mapper에 누락된 사실을 발견했다. 안전한 다음 행동은?

이 설계의 핵심 불변식은 공개 오류 계약 보존이다. 누락은 다음 단계로 넘기지 않는다.
