API-Core 모듈러 모놀리스와 import alias 설계

목적
단일 Nest API 서버의 계층 경계를 유지하면서 긴 상대 import를 읽기 쉬운 alias로 바꾼다.
사용자
Mogak 백엔드 개발·운영 담당자
문제
apps/api/src의 깊은 계층에서 ../../../ import가 의존 방향을 흐린다.
핵심 흐름
TypeScript/Jest/Nest build가 같은 alias를 해석하고, core DomainException은 API가 기존 HTTP 오류 계약으로 변환한다.
강도
Compact
범위
@api/*, @core/*, @infra/*, @composition/* 및 그 소비 import를 적용한다.
상태
설계 승인됨 — 2026-08-17 사용자 “적용 ㄱ”. 기존 계층 분리 설계에 build/runtime alias와 core 소유 DomainException 전략이 추가된다.
갱신
2026-08-17
변경 모델 · 위험 · 검증 · 점검 · 승인

변경 모델

  • tsconfig.json에 baseUrl과 네 alias paths를 추가한다.
  • jest.config.ts의 moduleNameMapper로 같은 source 별칭을 매핑한다.
  • tsc-alias를 개발 의존성으로 추가하고 nest build 뒤 dist import를 상대 경로로 치환한다.
  • 상대 import는 레이어 루트 사이 참조에만 alias로 바꾼다. 동일 feature 내부의 짧은 상대 import는 유지한다.

핵심 불변식과 위험

alias는 경계를 우회하지 않는다. @core는 API/infrastructure/composition을 import할 수 없고, 빌드된 dist/main.js는 별도 runtime alias loader 없이 시작해야 한다. DomainException은 core의 code만 가지며 HTTP status/message는 API AppErrorCode가 계속 소유한다.

핵심 위험은 TypeScript/Jest만 alias를 알아 Node가 Cannot find module '@core/...'로 기동 실패하는 것이다. 따라서 build 산출물을 검사하고 실제 node dist/main.js 기동 경로를 검증한다.

검증 계획

  1. format, lint, typecheck를 실행한다.
  2. unit/e2e와 architecture boundary test를 실행한다.
  3. pnpm build 후 rg "@(?:api|core|infra|composition)/" dist가 비어 있는지 확인한다.
  4. 기존 환경 변수로 build 산출물의 기동 검증을 수행하며, 환경이 없으면 공백으로 기록한다.
