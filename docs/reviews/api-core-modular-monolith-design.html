API-Core 모듈러 모놀리스 분리 설계

목적
단일 Nest API 서버에서 HTTP 어댑터와 비즈니스 core를 분리한다.
사용자
Mogak 백엔드 개발·운영 담당자
문제
현재 application 서비스가 Nest DI, HTTP 오류, Express 업로드 타입에 직접 결합돼 있다.
핵심 흐름
HTTP 요청 → API adapter → core use case/port → infrastructure adapter → 기존 HTTP 응답
강도
Standard
범위
apps/api/src 단일 실행체 안에서 api, core, infrastructure, composition을 분리한다.
상태
설계 승인됨 — 2026-08-17 사용자 “구현 ㄱㄱ”

승인된 모델

apps/api/src/
  api/             # Nest, controller, guard, request/response, HTTP filter
  core/            # domain, use case, port, command/query/result
  infrastructure/  # Drizzle, repository, JWT, storage
  composition/     # Nest DI/module assembly
  main.ts

허용 방향은 api → core ← infrastructure이며 composition만 전체를 조립한다. core는 Nest, Express, HTTP, Drizzle을 import하지 않는다.

결정과 불변식

  • 별도 core 프로세스·DB 분리·마이크로서비스화는 하지 않는다.
  • 기존 route, HTTP status, error code/message, JSON envelope, DB schema와 transaction 의미를 유지한다.
  • core 오류는 API mapper가 기존 AppErrorCode로 변환한다.
  • 컨텍스트 간 협력은 좁은 public contract/gateway만 통과한다.

구현 순서

  1. 앱 셸을 apps/api/src로 이동하고 빌드·테스트 설정을 갱신한다.
  2. presentation을 API, DB·repository·verifier·storage를 infrastructure, domain/application을 core로 이동한다.
  3. core service에서 Nest DI, HTTP 오류, Express 타입을 제거하고 composition에서 주입한다.
  4. core 오류 API 매핑과 cross-context gateway를 도입한다.
  5. architecture test 및 전체 회귀 검증으로 마감한다.

검증

pnpm format:check, pnpm lint, pnpm typecheck, pnpm build, unit, e2e, DB test를 단계별로 실행한다.

설계 통제 상태

미실시 — HTML 점검은 정보용이며 결과가 Codex에 자동 전달되지 않는다. 승인 근거는 사용자의 명시적 구현 지시다.

  1. Core의 저장 요청은 port를 통해 infrastructure adapter로 간다.
  2. HTTP status/error JSON 변환은 API가 담당한다.
  3. apps/api만 실행하고 core는 내부 코드다.
  4. 업로드는 API가 프레임워크 독립 입력으로 변환한다.

승인 상태

설계 승인됨. 승인 범위: 단일 실행체의 API/Core/Infrastructure/Composition 분리와 HTTP·DB 계약 보존. 제외 범위: 별도 core 서버, DB migration, 공개 API 변경.
