GitHub Actions CI와 Cloud Build·Cloud Run CD 설계

목적 (purpose)
저장소의 소스 변경을 검증하고, 승인된 커밋을 Cloud Build로 빌드·Cloud Run에 안전하게 배포하는 app-only CI/CD 운영 흐름을 정의한다. 초기 CD는 운영 DB를 변경하지 않는다.
사용자 (audience)
MOGAK 백엔드 개발자, GitHub 저장소 관리자, GCP 배포·운영 담당자.
문제 (problem)
현재 cloudbuild.yaml은 Docker 이미지 빌드·등록까지만 정의하며, GitHub Actions 검증, Cloud Run 배포, DB 접근 금지 경계, secret 권한, 실패 복구 경계가 저장소의 흐름으로 고정되어 있지 않다.
핵심 흐름 (core-flow)
Pull Request → GitHub Actions CI → 보호된 main 병합 → Cloud Build trigger → app image 빌드·Artifact Registry push → 트래픽 없는 Cloud Run revision smoke test → 초기 traffic 유지 → 운영자 승인 후 별도 traffic 전환 또는 이전 revision 복구. 운영 DB migration은 포함하지 않는다.
연결 구현 통제 기록
연결 구현 통제 문서 · G1-A revised design 구현 결과와 운영 연결 상태를 추적한다.
목표·범위 현재 근거 시스템 모델 결정 GCP 사전 조건 Cloud Build 단계 · 재설계 질문 실패·복구 검증 실행 계약 자기점검

1. 목표와 범위

첫 단계의 목표는 애플리케이션 코드와 배포 제어를 분리하는 것이다. GitHub Actions는 변경의 품질 게이트를 담당하고, GCP 내부의 Cloud Build가 애플리케이션 이미지와 Cloud Run 배포를 담당한다. 초기 CD는 운영 DB schema·data를 변경하지 않는다.

포함

  • PR과 main push에서 Node 24.18·pnpm 10.32.1 기반 CI 실행.
  • pnpm verify:local과 runtime Docker build로 테스트·컨테이너 산출물 검증. CI의 DB는 격리된 로컬/테스트 DB로 한정한다.
  • 보호된 main 병합을 기점으로 Cloud Build가 immutable commit artifact를 만들고 Cloud Run에 배포.
  • 운영 DB에 drizzle-kit migrate·drizzle-kit push·임의 DDL/DML을 실행하지 않음.
  • Secret Manager, 최소 권한 service account, no-traffic revision smoke test, 운영자 승인 traffic 전환과 수동 Cloud Run revision rollback.

비포함

  • 이번 단계에서 별도 staging·production 프로젝트를 새로 만드는 것.
  • Cloud SQL인지 외부 managed PostgreSQL인지 확정되지 않은 네트워크 인프라 자체의 생성.
  • Terraform 전체 도입, Binary Authorization·자동 취약점 차단, canary 비율 자동 조정.
  • 모든 운영 DB migration·backfill·schema 변경·복구. 이 작업은 별도 설계와 명시적 승인 후 다룬다.
  • 앱이 기존 schema에 대해 수행하는 정상적인 runtime read/write까지 차단하는 것. 초기 CD가 DB schema/data를 직접 변경하지 않는다는 경계와 구분한다.

2. 현재 저장소 근거와 가정

설계에 반영한 저장소 관찰
관찰설계 영향
package.json은 Node >=24.18.0 <25, pnpm >=10.32.1 <11을 요구한다.CI toolchain을 Node 24.18.0과 pnpm 10.32.1로 고정한다.
pnpm verify:local은 PostgreSQL Compose, format/lint/typecheck/build, 일반·E2E·integration test, 실제 API scenario까지 순서대로 실행한다.CI의 단일 품질 게이트로 재사용하고, 별도로 Docker image build를 추가한다.
apps/api/src/api/health/health.controller.ts의 GET /health는 DB를 주입받지 않고 { status: 'ok' }만 반환한다.운영 smoke는 GET /health 단일 호출로 제한한다. POST·PUT·DELETE나 DB를 조회하는 API 시나리오는 production smoke에 포함하지 않는다.
Dockerfile의 runtime stage는 dist와 production dependencies만 복사한다.runtime image와 CD에서 pnpm db:migrate를 실행하지 않는다. 초기 단계에는 migration 전용 target/image를 추가하지 않으며 Node base image는 검토된 digest로 고정한다.
drizzle/*.sql에는 현재 DROP TABLE/COLUMN, TRUNCATE, DELETE FROM이 없지만, 0005는 FK constraint를 제거·재생성하고 0004·0005는 legacy 단수 테이블명을 참조한다.이 migration 이력은 초기 CD에 연결하지 않는다. 향후 별도 migration 설계에서 대상 DB와의 호환성을 다시 검토한다.
현재 cloudbuild.yaml은 gcr.io/workvoys/github.com/team-mogak/mogak-core-back:$COMMIT_SHA를 build·push하고 CLOUD_LOGGING_ONLY만 설정한다.새 설계에서는 Artifact Registry pkg.dev 경로, 명시적 target preflight, builder digest pinning, digest deploy, no-traffic smoke를 사용한다.
.github/workflows는 발견되지 않았다.CI workflow를 새로 추가한다. GHA에는 GCP 장기 service-account key를 주지 않는다.
기존 문서에는 Cloud Run 서비스·trigger가 존재한다고 기록되어 있지만, 저장소 설정에는 실제 서비스명·리전이 없다.서비스명·리전·운영 DB 연결 방식은 구현 직전 GCP에서 읽기 확인하고 placeholder를 채운다.

가정

현재 GCP project는 기존 YAML에 나타난 workvoys이며, 운영 PostgreSQL은 이미 접근 가능한 endpoint를 가진다고 가정한다. Cloud SQL이면 Cloud Run service에 Cloud SQL connection을 추가하고, 외부 managed PostgreSQL이면 해당 VPC egress·allowlist만 바꾼다. 초기 CD는 이 DB에 migration이나 임의 SQL을 실행하지 않는다.

배포 순서app artifact push → Cloud Run --no-traffic revision → revision health smoke → 초기 CD 종료. traffic은 운영자 승인 후 별도 실행한다.revision 실패 시 기존 traffic을 유지한다. smoke 성공만으로 traffic을 바꾸지 않으며, CD가 schema를 바꾸지 않으므로 앱 rollback은 수동 traffic 명령으로 한정한다.

배포 승인초기 Cloud Build는 smoke 뒤 멈춘다. 운영자는 실제 service·region·IAM·approval을 확인한 뒤 별도 traffic 전환을 승인한다.현재 staging·production 리소스와 서비스명이 저장소에 없으므로 단일 환경을 바로 무인 production으로 가정하지 않는다.
rollback애플리케이션은 운영자가 이전 Cloud Run revision으로 traffic을 되돌린다. 초기 CD가 DB schema·data를 변경하지 않으므로 DB rollback 절차는 실행하지 않는다.향후 자동 traffic/rollback이나 migration을 도입할 때는 별도 설계와 승인을 거친다.

초기 단계의 DB 변경 보류 경계

Drizzle migration은 별도 후속 설계로 보류한다. 초기 CD는 애플리케이션 artifact와 Cloud Run revision만 다루며, 운영 DB에는 migration command·임의 SQL·schema introspection query를 실행하지 않는다. CI에서 사용하는 PostgreSQL은 저장소가 보장하는 격리된 _test DB로 한정한다.

Smoke safety: 현재 GET /health 구현은 정적 응답이라 운영 DB row·schema를 변경하지 않는다. smoke는 production custom domain이 아니라 새 revision의 검증 tag URL에 호출한다. 단, Cloud Run container startup 코드나 향후 health endpoint가 DB query·seed·write를 추가하면 이 보장은 사라지므로, smoke 범위를 변경할 때 별도 검토한다.

향후 migration을 다시 논의할 때의 보류 기준
항목현재 단계후속 설계에서 필요한 것
운영 DB 접근Cloud Build·CD에서 금지한다.대상 DB, 네트워크, secret, 운영 owner를 먼저 확정한다.
migration SQL생성·수정·실행하지 않는다.Git에 커밋된 SQL을 직접 review하고 additive / transform / destructive로 분류한다.
현재 이력drizzle/0004·0005를 production에 연결하지 않는다.신규 plural schema와 legacy 단수 schema 중 어느 쪽을 기준으로 삼을지 별도 결정한다.
복구·호환성이번 단계 승인 대상이 아니다.backup/PITR, staging replay, expand/contract, 앱·DB rollback을 별도 승인한다.

2026-08-30 read-only preflight 결과

project는 workvoys로 확인됐다. 기존 mogak-spring, workvoys-kanban-alarm, workvoys-web-prod는 모두 asia-northeast3에 있고, 기존 backend image repository backend-core도 asia-northeast3에 있다. asia-northeast1에서는 해당 Cloud Run service와 repository가 확인되지 않았다. 기존 main trigger는 cloudbuild.yaml을 사용하지만 기본 Compute service account를 사용하며 approvalConfig가 출력되지 않아 승인 여부가 미확정이다. 따라서 구현은 region/service/repository/runtime SA를 trigger에서 모두 명시하도록 바꾸고, Cloud Build가 build·push하기 전에 같은 region의 기존 resource를 read-only로 확인하도록 한다. 실제 GCP 값과 IAM은 여전히 운영 연결 전 확정 대상이다.

GitHub Actions CI workflow 계약

workflow 이름은 CI, required job 이름은 verify로 고정해 GitHub branch protection에서 CI / verify를 요구한다. action은 구현 시 commit SHA pinning을 적용하고, workflow에는 GCP credential·운영 secret을 넣지 않는다.

name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  verify:
    runs-on: ubuntu-24.04
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@<commit-sha>
      - uses: pnpm/action-setup@<commit-sha>
        with: { version: 10.32.1 }
      - uses: actions/setup-node@<commit-sha>
        with: { node-version: 24.18.0, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm verify:local
      - run: docker build --target runtime --tag mogak-core-back:ci .
      - if: always()
        run: docker compose down --volumes --remove-orphans

APP_IMAGE=asia-northeast1-docker.pkg.dev/workvoys/mogak/mogak-core-back:$COMMIT_SHA

7. Cloud Build CD 단계 계약

Cloud Build의 step은 target preflight에서 시작해 아래 순서를 유지한다. 같은 build 안에서는 선행 step이 실패하면 이후 step을 실행하지 않는다. target preflight는 placeholder를 거부하고 지정한 region의 기존 Artifact Registry repository·Cloud Run service·runtime service account를 read-only로 확인하므로, 대상이 없으면 build·push 전에 중단한다. 초기 CD에는 DB 접근·migration step이 없으며, 운영 DB 변경은 발생하지 않는다. 초기 build는 tag /health smoke 성공 뒤 traffic을 바꾸지 않고 종료한다. 서로 다른 CD build의 동시 실행은 기본적으로 직렬화된다고 가정하지 않으므로, 운영자는 최신 commit만 별도로 승인해 traffic을 전환한다.

  # placeholder와 target 존재/region 일치 여부를 먼저 read-only 확인
  gcloud artifacts repositories describe "$AR_REPOSITORY" --location="$REGION"
  gcloud run services describe "$SERVICE" --region="$REGION"
  gcloud iam service-accounts describe "$RUNTIME_SERVICE_ACCOUNT"

  docker push "$APP_IMAGE:$COMMIT_SHA"

gcloud run deploy "$SERVICE" \
  --image="$APP_IMAGE@$APP_DIGEST" --no-traffic \
  --tag="verify-$SHORT_SHA-$BUILD_ID_PREFIX" --region="$REGION"
# verify tag /health 성공 → revision/tag/image 값을 build log에서 handoff
# Cloud Build 종료, 기존 traffic 유지
# 명시적 운영자 승인 후 별도 실행:
gcloud run services update-traffic "$SERVICE" \
  --region="$REGION" --to-tags="$TAG=100"
# 필요 시 수동 rollback:
gcloud run services update-traffic "$SERVICE" \
  --region="$REGION" --to-revisions="$PREVIOUS_REVISION=100"

승인 후 traffic·rollback·tag cleanup의 실제 명령과 단일-100% traffic 전제는 Cloud Run app-only release runbook에 둔다. revision 삭제는 자동화하지 않는다.

동시 배포 제어

Cloud Build의 build quota는 여러 build가 실행될 수 있는 상한이지 동일 Cloud Run service 배포의 순서 보장이 아니다. 따라서 첫 구현은 production trigger approval을 켜고 운영자가 최신 commit만 승인한다. 무인 자동 배포로 전환하려면 GitHub merge queue 기반 직렬화, GHA의 Cloud Build 호출 concurrency, 또는 별도 deployment lock 중 하나를 후속 설계로 선택한다.

9. 불변식

  1. CI가 실패한 commit은 보호된 main에 병합될 수 없고, 따라서 정상 경로의 CD 대상이 되지 않는다.
  2. Cloud Run이 serving하는 image는 branch나 latest가 아니라 commit SHA와 확인된 digest로 추적된다.
  3. 초기 CD의 Cloud Build에는 운영 DB 접근, migration Job, drizzle-kit migrate, drizzle-kit push 단계가 없다.
  4. 새 revision의 smoke가 실패하면 기존 revision이 traffic을 계속 가진다. smoke가 성공해도 초기 CD는 traffic을 자동 변경하지 않으며, traffic 명령은 운영자 승인 후 별도 실행한다. 초기 CD가 DB schema·data를 변경하지 않으므로 rollback 시 DB recovery를 수행하지 않는다.
  5. 운영 secret의 원문은 GitHub, Cloud Build substitution, build log, Docker layer에 남지 않는다.
  6. Cloud Build는 placeholder target을 거부하고, 지정한 region에 기존 service·repository·runtime service account가 확인되지 않으면 build·push 전에 종료한다.
  7. 향후 migration은 현재 CD와 분리된 별도 설계·승인 없이는 생성·수정·실행하지 않는다.
  8. CI가 사용하는 DB는 전용 _test DB뿐이며, production DATABASE_URL은 CI/CD에 주입하지 않는다.

“배포를 위해 운영 DB를 같이 바꿔야 한다”는 요구가 초기 범위에 섞이는 것이 가장 큰 위험이다. 이번 단계는 DB 변경을 하지 않는 app-only CD로 고정하고, migration은 대상 DB·백업·호환성 검토가 끝난 별도 설계로 분리한다.

12. 구현 후 검증 계획

  1. GitHub Actions: PR에서 pnpm verify:local이 성공하고, runtime Docker build가 성공하는지 확인한다.
  2. Cloud Build: placeholder·target preflight가 build/push 전에 동작하고, 동일 commit의 app image가 SHA/digest로 push되며, revision·tag·smoke URL handoff가 log에 남고, DB secret·DB 접근 단계가 없는지 확인한다.
  3. Cloud Run: 새 revision이 traffic 없이 생성되고, revision tag 또는 검증 endpoint의 GET /health가 {"status":"ok"}를 반환하는지 확인한다.
  4. Traffic: tag smoke 성공 직후 기존 traffic이 유지되는지 확인하고, 운영자 승인 후 별도 명령으로 새 revision 100% 전환이 되는지 확인한다.
  5. Rollback drill: 운영 runbook에 따라 단일 100% traffic 전제, 운영자 승인 traffic 전환, 앱 revision 수동 rollback, rollback window 후 tag cleanup을 실제로 기록한다. revision 삭제는 자동화하지 않는다.
  6. IAM: GHA token에 GCP 장기 key가 없고, deployer/runtime service account가 필요한 resource만 접근하는지 확인한다. Cloud Build에는 DB 권한이 없어야 한다.

13. 결정 품질 압력 검사

결정
GHA는 검증만, Cloud Build는 GCP 내부 build·Cloud Run app rollout의 no-traffic 단계까지만 맡긴다. 초기 CD는 운영 DB를 건드리지 않는다.
권고
현재 저장소의 pnpm verify:local을 CI gate로 재사용하고, runtime image를 commit SHA/digest로 배포한다. Drizzle migration은 별도 설계·승인 전까지 연결하지 않는다.
최소안
한 Cloud Run 서비스와 한 Cloud Build trigger로 시작하되, bootstrap approval·no-traffic smoke에서 초기 CD를 끝내고 traffic 전환·수동 rollback은 운영 runbook의 별도 명령으로 유지한다.
미룰 것
staging/prod promotion, 자동 canary, deployment lock, image attestation은 실제 service/region/DB 운영 정보를 확인한 다음 별도 결정한다.
가정·확신도
workvoys project와 기존 PostgreSQL endpoint는 확인된 저장소 근거가 있으나, 실제 Cloud Run service명·region·DB provider는 미확인이다. CI/CD 순서에 대한 확신도는 높고, 네트워크 세부에 대한 확신도는 중간이다.
확인 또는 다음 행동
G1-A 범위의 workflow와 Cloud Build 설정을 구현·검증한다. 실제 GCP service·repository·service account 값은 trigger substitution과 read-only preflight로 확정하며, 운영 DB나 GCP 리소스 mutation은 이 단계에 포함하지 않는다.

14. 설계 의사결정 질문 (grilling)

진행 상태: 결정 반영 완료 · 범위: Cloud Build CD의 1차 rollout 정책과 설정 복잡도.

사용자의 ㅇㅇ과 이어진 워크트리 작업 지시를 G1-A 권고안의 구현 진행 지시로 기록한다. revised design은 image build/push → no-traffic deploy → tag /health smoke에서 초기 Cloud Build를 끝내고, traffic 전환·rollback을 별도 운영자 명령으로 분리한다.

G1 — 결정
초기 CD에서 tag /health smoke가 성공한 뒤 traffic을 자동 전환할 것인가? → G1-A 선택
왜 지금
traffic 전환은 운영 상태를 바꾸는 외부 효과이며, 이 선택에 따라 YAML의 단계 수·IAM(run.invoker)·rollback 책임·검증 범위가 달라진다.
확인된 근거
현재 저장소의 /health는 정적 응답이다. GCP preflight에서는 기존 service/repository가 asia-northeast3에 있고 Tokyo 대상은 확인되지 않았으며, 기존 trigger의 approval/IAM 계약도 확정되지 않았다.
G1-A · 권고
초기에는 build/push → no-traffic deploy → tag /health smoke에서 멈추고, 실제 GCP 값·권한·approval을 확인한 운영자만 별도 traffic 전환을 수행한다. blast radius와 자동 rollback 오판은 줄지만 완전 자동 배포는 늦어진다.
G1-B · 대안
현재처럼 자동 traffic 전환과 service smoke 실패 시 이전 revision rollback을 유지한다. 배포는 편해지지만 service/repository/IAM이 확정되고 실제 smoke·rollback drill을 통과해야 하며, 일시적 health 실패가 자동 rollback을 일으킬 수 있다.
G2 · 종속 결정
짧은 YAML을 유지한다. 초기 Cloud Build에는 build/push/no-traffic/tag smoke만 두고, 승인 후 update-traffic와 수동 rollback은 runbook 또는 후속 change로 분리한다. 별도 rollout script는 현재 추가하지 않는다.

공유 이해 요약

  1. GHA는 PR과 main의 품질 검증만 수행하고 GCP 권한을 갖지 않는다.
  2. Cloud Build는 protected main의 같은 commit을 SHA/digest artifact로 빌드·push한다.
  3. Cloud Run에는 새 revision을 --no-traffic·검증 tag로 배포하고, 현재 정적 /health만 smoke한다.
  4. smoke 성공은 초기 CD의 끝이다. 기존 traffic은 유지되며, 운영자가 최신 commit·service·region·IAM·approval을 확인한 뒤 별도 traffic 전환 또는 수동 rollback을 수행한다.
  5. Tokyo 후보·service·repository·runtime SA는 아직 운영값으로 확정하지 않았고, 지금까지 GCP와 DB mutation은 없었다.

결정 기록: G1-A 선택과 G2(짧은 YAML·별도 운영 명령)를 반영했고, 현재 워크트리에 구현 중이다. 운영 trigger 활성화와 traffic 변경은 별도 운영 확인 전까지 보류한다.

15. 설계 통제 상태

상태: 구현 진행 · 운영 연결 보류 · 강도: High-risk · 기존 승인: 2026-08-30 · 사용자 ㄱㄱ로 app-only 구현 승인

기존 승인은 app-only 안전 경계에 대한 기준으로 보존한다. G1-A와 G2를 반영한 revised design에 대해 사용자가 워크트리 작업을 지시했으므로 저장소 설정 구현을 진행한다. 실제 GCP 운영 trigger 활성화·traffic 변경·DB 접근은 별도 운영 확인 전까지 보류한다.

승인 범위: GitHub Actions CI, Artifact Registry app image, Cloud Build의 no-traffic Cloud Run revision·/health smoke. 운영자 승인 후 별도 traffic 전환·수동 앱 rollback은 runbook 명령으로만 다루며 초기 Cloud Build 파일에는 넣지 않는다. 운영 DB schema·data, migration Job, Drizzle migration, GCP 운영 리소스 mutation은 승인 범위에 없다.

브라우저에서 제출한 결과는 Codex로 자동 전달되지 않는다. 이 점검은 설계 승인이 아니라, 배포 순서·실패 경계·운영 권한을 예측할 수 있는지 확인하는 정보용 통제다.
