GitHub Actions CI와 Cloud Build·Cloud Run CD 설계

목적 (purpose)
저장소의 소스 변경을 검증하고, 승인된 커밋을 Cloud Build로 빌드·마이그레이션·Cloud Run에 안전하게 배포하는 CI/CD 운영 흐름을 정의한다.
사용자 (audience)
MOGAK 백엔드 개발자, GitHub 저장소 관리자, GCP 배포·운영 담당자.
문제 (problem)
현재 cloudbuild.yaml은 Docker 이미지 빌드·등록까지만 정의하며, GitHub Actions 검증, Cloud Run 배포, DB migration 순서, secret 권한, 실패 복구 경계가 저장소의 흐름으로 고정되어 있지 않다.
핵심 흐름 (core-flow)
Pull Request → GitHub Actions CI → 보호된 main 병합 → Cloud Build trigger → 이미지 빌드·Artifact Registry push → migration Cloud Run Job → 트래픽 없는 Cloud Run revision smoke test → 트래픽 전환 → 필요 시 이전 revision 복구.
연결 구현 통제 기록
승인 후 생성할 구현 통제 문서 · 현재는 아직 생성하지 않는다.
목표·범위 현재 근거 시스템 모델 결정 실패·복구 검증 자기점검

1. 목표와 범위

첫 단계의 목표는 애플리케이션 코드와 배포 제어를 분리하는 것이다. GitHub Actions는 변경의 품질 게이트를 담당하고, GCP 내부의 Cloud Build가 실제 이미지·migration·Cloud Run 배포를 담당한다.

포함

  • PR과 main push에서 Node 24.18·pnpm 10.32.1 기반 CI 실행.
  • pnpm verify:local과 runtime/migrator Docker build로 테스트·컨테이너 산출물 검증.
  • 보호된 main 병합을 기점으로 Cloud Build가 immutable commit artifact를 만들고 Cloud Run에 배포.
  • 운영 PostgreSQL migration을 앱 인스턴스가 아니라 단일 task Cloud Run Job에서 실행.
  • Secret Manager, 최소 권한 service account, no-traffic revision smoke test, Cloud Run traffic rollback.

비포함

  • 이번 단계에서 별도 staging·production 프로젝트를 새로 만드는 것.
  • Cloud SQL인지 외부 managed PostgreSQL인지 확정되지 않은 네트워크 인프라 자체의 생성.
  • Terraform 전체 도입, Binary Authorization·자동 취약점 차단, canary 비율 자동 조정.
  • DB migration의 자동 down/복구. 앱 revision rollback과 DB schema rollback은 다른 작업으로 남긴다.

2. 현재 저장소 근거와 가정

설계에 반영한 저장소 관찰
관찰설계 영향
package.json은 Node >=24.18.0 <25, pnpm >=10.32.1 <11을 요구한다.CI toolchain을 Node 24.18.0과 pnpm 10.32.1로 고정한다.
pnpm verify:local은 PostgreSQL Compose, format/lint/typecheck/build, 일반·E2E·integration test, 실제 API scenario까지 순서대로 실행한다.CI의 단일 품질 게이트로 재사용하고, 별도로 Docker image build를 추가한다.
Dockerfile의 runtime stage는 dist와 production dependencies만 복사한다.runtime image에서 pnpm db:migrate를 실행하지 않는다. migration 전용 target/image가 필요하다.
현재 cloudbuild.yaml은 gcr.io/workvoys/github.com/team-mogak/mogak-core-back:$COMMIT_SHA를 build·push하고 CLOUD_LOGGING_ONLY만 설정한다.현재 이미지 경로는 기준선으로 기록하되, 새 설계에서는 Artifact Registry pkg.dev 경로로 전환한다.
.github/workflows는 발견되지 않았다.CI workflow를 새로 추가한다. GHA에는 GCP 장기 service-account key를 주지 않는다.
기존 문서에는 Cloud Run 서비스·trigger가 존재한다고 기록되어 있지만, 저장소 설정에는 실제 서비스명·리전이 없다.서비스명·리전·운영 DB 연결 방식은 구현 직전 GCP에서 읽기 확인하고 placeholder를 채운다.

가정

현재 GCP project는 기존 YAML에 나타난 workvoys이며, 운영 PostgreSQL은 이미 접근 가능한 endpoint를 가진다고 가정한다. Cloud SQL이면 Cloud Run service/job에 Cloud SQL connection을 추가하고, 외부 managed PostgreSQL이면 해당 VPC egress·allowlist만 바꾼다. CI/CD의 핵심 순서와 권한 분리는 유지된다.

IAMCloud Build용 deployer SA, API runtime SA, migration job SA를 분리한다.deployer는 Artifact Registry write·Cloud Run 배포·runtime SA 사용·job invoke에만 접근하고, runtime/job SA가 secret·DB에 접근한다.
배포 승인bootstrap 기간에는 Cloud Build production trigger에 approval을 걸고, 첫 smoke·rollback 확인 후 자동화 여부를 별도로 결정한다.현재 staging·production 리소스와 서비스명이 저장소에 없으므로 단일 환경을 바로 무인 production으로 가정하지 않는다.
rollback애플리케이션은 이전 Cloud Run revision으로 traffic을 되돌린다. DB는 자동 rollback하지 않고 expand/contract migration과 수동 recovery 절차를 따른다.Cloud Run revision rollback은 schema rollback을 되돌리지 않는다.

6. 불변식

  1. CI가 실패한 commit은 보호된 main에 병합될 수 없고, 따라서 정상 경로의 CD 대상이 되지 않는다.
  2. Cloud Run이 serving하는 image는 branch나 latest가 아니라 commit SHA와 확인된 digest로 추적된다.
  3. migration Job이 성공하기 전에는 새 앱 revision에 traffic을 주지 않는다.
  4. 새 revision의 smoke가 실패하면 기존 revision이 traffic을 계속 가진다. traffic을 되돌려도 이미 적용된 DB migration은 되돌아가지 않는다.
  5. 운영 secret의 원문은 GitHub, Cloud Build substitution, build log, Docker layer에 남지 않는다.
  6. migration은 이전 revision과 호환되는 expand/contract 방식이어야 한다. 컬럼 삭제·이름 변경처럼 구 revision을 즉시 깨뜨리는 migration은 별도 승인 없이는 배포하지 않는다.
  7. migration Job은 task 1개, parallelism 1, 자동 retry 0을 기본으로 하며 실패 후 원인 확인 없이 재실행하지 않는다.

7. 실패와 복구

실패 지점별 관찰과 다음 행동
실패 지점보장되는 상태운영 행동
GHA format/lint/type/test/build 실패PR merge 차단. Cloud Run 영향 없음.GHA 로그에서 실패 command를 수정하고 같은 PR을 재검증한다.
Cloud Build Docker build/push 실패새 revision·traffic 없음. 일부 이미지가 남을 수 있으나 serving되지 않음.Cloud Build log와 commit SHA를 확인한 뒤 재실행한다.
migration Job 실패새 앱 revision traffic 없음. DB가 일부 변경됐을 가능성은 자동으로 숨기지 않음.Job execution log와 Drizzle migration 기록을 확인한다. 필요하면 DB backup/recovery 절차를 수동 수행하고, 원인 확인 전 재실행하지 않는다.
새 revision startup 또는 GET /health 실패--no-traffic이면 이전 revision이 계속 serving.secret, PORT, DB 연결, image 로그를 확인하고 새 revision만 수정·재배포한다.
traffic 전환 후 5xx·계약 오류Cloud Run revision은 immutable이며 이전 revision으로 traffic을 되돌릴 수 있음.gcloud run services update-traffic <service> --to-revisions <previous-revision>=100으로 앱만 rollback하고 schema 영향은 별도로 판정한다.
두 CD build가 겹침Cloud Build의 build quota가 deployment serialization을 보장하지 않음.bootstrap에서는 approval로 최신 commit만 승인한다. 자동 무인 배포 전에는 main merge serialization 또는 별도 deployment lock/concurrency 설계를 추가 승인한다.

가장 큰 반증

“앱은 정상인데 migration이 실패했거나, 앱 rollback 뒤에도 DB schema가 새 버전인 상태”가 이 설계를 깨뜨리는 가장 현실적인 경로다. 그래서 migration을 Cloud Run Job으로 분리하는 것만으로 충분하지 않고, 모든 production migration에 expand/contract·backup·호환성 검토를 요구한다.

8. 거부한 대안

대안과 선택하지 않은 이유
대안거부 이유
GHA에서 Docker push와 Cloud Run deploy까지 모두 수행CI와 CD credential boundary가 합쳐지고, GHA가 운영 GCP 권한을 직접 가져야 한다. WIF로 개선할 수 있지만 이번 요청의 Cloud Build CD 경계와 맞지 않는다.
Cloud Build는 image만 만들고 앱 startup에서 migrationCloud Run scale-out 인스턴스가 동시에 migration할 수 있고, revision health와 schema 변경이 한 lifecycle에 섞인다.
현재 gcr.io와 mutable latest를 계속 사용Artifact Registry가 새 이미지 저장소 기준이며, tag만으로는 정확한 배포·rollback 대상을 보장하기 어렵다.
migration 실패 시 자동 down migration데이터 손실과 비가역 DDL 위험이 있어 자동 복구로 일반화할 수 없다.

9. 구현 후 검증 계획

  1. GitHub Actions: PR에서 pnpm verify:local이 성공하고, runtime/migrator Docker build가 성공하는지 확인한다.
  2. Cloud Build: 동일 commit에서 두 image가 같은 SHA로 push되고, log가 CLOUD_LOGGING_ONLY로 남으며 secret 원문이 없는지 확인한다.
  3. Migration: staging 또는 복제 가능한 테스트 DB에서 Job이 한 번 성공하고, 재실행 시 Drizzle migration 기록에 맞게 안전하게 no-op 또는 명확한 실패를 내는지 확인한다.
  4. Cloud Run: 새 revision이 traffic 없이 생성되고, revision tag 또는 검증 endpoint의 GET /health가 {"status":"ok"}를 반환하는지 확인한다.
  5. Traffic: 성공 시 새 revision 100%, 실패 시 이전 revision 100%인지 확인한다.
  6. Rollback drill: 앱 revision rollback command와 DB schema 잔여 상태를 실제로 기록한다.
  7. IAM: GHA token에 GCP 장기 key가 없고, deployer/runtime/migrator 각 SA가 필요한 resource만 접근하는지 확인한다.
승인 기준
기준통과 조건
품질pnpm verify:local와 두 Docker target build가 성공한다.
재현성같은 commit SHA가 같은 artifact 식별자와 연결되고 lockfile이 변경되지 않은 채 재현된다.
안전한 배포migration 성공 → no-traffic revision smoke → traffic 전환 순서가 Cloud Build log에 확인된다.
복구이전 revision rollback command, 실패 시 traffic 보존, DB migration의 비자동 rollback 한계가 운영 문서에 기록된다.
비밀·권한secret 원문이 코드·workflow·build log에 없고, SA 권한이 설계 표와 일치한다.

공식 참고: Cloud Build GitHub trigger, Cloud Run image deployment/revision, Cloud Run Job execute/wait, GitHub OIDC Workload Identity Federation, Artifact Registry transition.

10. 결정 품질 압력 검사

결정
GHA는 검증만, Cloud Build는 GCP 내부 build·migration·Cloud Run rollout을 맡긴다.
권고
현재 저장소의 pnpm verify:local을 CI gate로 재사용하고, runtime과 migrator를 분리해 commit SHA/digest로 배포한다.
최소안
한 Cloud Run 서비스와 한 Cloud Build trigger로 시작하되, bootstrap approval·no-traffic smoke·수동 rollback을 유지한다.
미룰 것
staging/prod promotion, 자동 canary, deployment lock, image attestation은 실제 service/region/DB 운영 정보를 확인한 다음 별도 결정한다.
가정·확신도
workvoys project와 기존 PostgreSQL endpoint는 확인된 저장소 근거가 있으나, 실제 Cloud Run service명·region·DB provider는 미확인이다. CI/CD 순서에 대한 확신도는 높고, 네트워크 세부에 대한 확신도는 중간이다.
확인 또는 다음 행동
아래 자기점검으로 흐름을 확인한 뒤, 설계 승인 여부를 별도로 결정한다. 승인 전에는 workflow, Dockerfile, cloudbuild.yaml, GCP resource를 수정하지 않는다.

12. 별도 설계 승인

현재 상태는 설계 승인 대기다. 자기점검 답변은 설계 이해 확인이며 승인 자체가 아니다.

설계가 확정되면 대화에서 별도로 “이 설계로 구현을 시작할까?”에 답한다. 승인 전에는 구현 파일과 GCP 운영 리소스를 변경하지 않는다.
