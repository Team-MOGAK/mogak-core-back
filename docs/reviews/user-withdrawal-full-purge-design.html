회원 탈퇴: 동기 전체 삭제

설계 상태: 승인됨 · 2026-08-23

목적: 탈퇴와 동시 mutation이 경합해도 앱 코드가 관계 데이터를 안전하게 삭제한다.

HTTP 계약 · 동기 운영 기준 · 동시성 규약 · CTE 삭제 배치 · 검증 보강 · 동기 처리 한계 · ORM 삭제 전환 · 실패 처리 책임 · 설계 점검 · 리뷰

목적

회원 탈퇴 요청 안에서 회원과 회원이 소유하거나 작성한 관계 데이터를 앱 코드가 명시적으로 삭제한다. DB FK cascade는 삭제 완결성의 전제가 아니다.

HTTP 계약

POST /api/auth/withdraw → 204 No Content

응답 본문 및 isDeleted 필드는 반환하지 않는다. 성공은 삭제 완료를 뜻한다.

동기 운영 기준 — 제안

  1. 탈퇴 transaction이 대상 users 행과, 새 자식 행을 받을 수 있는 모다랏·모각·조각·실행·게시글 부모 행을 FOR UPDATE로 선점한다.
  2. 새 댓글·좋아요·이미지는 lock된 게시글 FK를, 새 실행·조각·모각은 lock된 부모 FK를, 세션·팔로우·사용자 작성 데이터는 lock된 사용자 FK를 참조하므로 FK의 KEY SHARE와 충돌해 대기한다.
  3. 대기 중 먼저 시작한 mutation이 commit했을 수 있으므로, 부모 lock 획득 후 사용자 존재와 모든 삭제 대상은 DB subquery로 다시 계산한다.
  4. 게시글 자식부터 사용자까지 명시적으로 삭제하고, 모든 DB 삭제를 하나의 transaction으로 commit 또는 rollback 한다.
  5. 일반 mutation에는 탈퇴만을 위한 advisory/user lock 호출을 추가하지 않는다. 단, FK를 거치지 않고 관계를 만드는 경로가 없는지는 감사한다.
인덱스
post_img(post_id), post_comment(post_id), post_comment(user_id), post(user_id), modarat(user_id), mogak(modarat_id), jogak(mogak_id), auth_sessions(user_id), follow(to_id)를 migration으로 추가한다. 운영 DB에서는 가능한 CREATE INDEX CONCURRENTLY 방식으로 배포한다.
시간 제한·관측
transaction/lock 대기/삭제 건수 테이블별 로그와 metric을 남기고, DB lock timeout 및 statement timeout을 둔다. timeout·오류는 rollback하며 204를 반환하지 않는다.
재시도 계약
성공만 204다. 완료 후 토큰은 함께 삭제되어 동일 사용자의 재요청은 인증 단계에서 실패한다. 별도의 DELETING 상태나 retry API는 sync 범위에 넣지 않는다.
외부 데이터
DB에 저장된 관계 행만 이 transaction으로 완결한다. 오브젝트 스토리지의 실제 파일 삭제가 요구되면 async purge의 별도 범위로 전환한다.

불변식: DB FK cascade는 탈퇴 완결성의 수단이 아니다. 마지막 users 삭제 이전에 모든 관계 행이 앱 코드의 명시적 delete로 사라져야 한다. 현재 FK가 ON DELETE CASCADE인 것은 누락을 숨길 수 있으므로, 이를 RESTRICT로 바꾸는 작업은 다른 삭제 endpoint까지 영향이 있어 별도 schema migration 범위로 검토한다.

삭제 순서

  1. 대상 사용자 transaction advisory lock 획득
  2. 대상 모각 실행과 사용자 작성 게시글을 찾고, 게시글 이미지·댓글·좋아요·게시글을 자식부터 삭제
  3. 사용자 작성 댓글·좋아요, 팔로우 양방향, 세션, 소셜 계정, 동의를 삭제
  4. 일정 요일·일정·실행·조각·모각·모다랏을 자식부터 삭제
  5. 마지막으로 users 행을 삭제

동시성 규약

탈퇴만 사용자·모다랏·모각·조각·실행·게시글 부모 행을 FOR UPDATE로 lock한다. 관계를 새로 만드는 일반 mutation은 해당 FK 참조 과정에서 KEY SHARE를 획득하므로, 탈퇴의 부모 FOR UPDATE와 충돌한다. 기존 자식 행의 변경은 이후 명시적 delete와 행 lock으로 직렬화된다. 모든 삭제 대상은 부모 lock 뒤 SQL subquery로 다시 계산한다.

대량 계정에서도 bind parameter 제한에 걸리지 않도록 탈퇴 cascade는 JavaScript ID 배열이나 IN (...ids)가 아니라 DB 서브쿼리로 수행한다.

이 lock은 DB 전체에 공유되지만 같은 사용자 key만 충돌한다. transaction commit/rollback 때 자동 해제된다.

CTE 삭제 배치 — 재승인 대상

결정 제안: 현재의 명시적 앱단 cascade와 부모 row lock은 유지하되, 삭제 SQL을 도메인별 data-modifying CTE로 묶는다. FK cascade·DB trigger·stored procedure는 도입하지 않는다.

삭제 statement 경계
순서도메인포함하는 명시 delete
1게시글post_img → post_comment → post_like → post
2모각 트리jogak_schedule_weekdays → jogak_schedules → daily_jogak → jogak → mogak → modarat

가장 강한 반증: data-modifying CTE는 같은 행을 두 번 수정하거나 FK 삭제 순서를 암묵적으로 기대하면 예측할 수 없다. 각 하위 delete는 상위 CTE의 RETURNING을 참조해 순서를 강제하고, 세 도메인을 하나의 거대 query로 합치지 않는다.

미룬 범위: lock 조회 자체를 조인 하나로 합치거나, async purge worker·DB stored procedure로 전환하는 것은 포함하지 않는다.

탈퇴 검증 보강 — 재승인 대상

변경 범위: 런타임 코드와 HTTP 계약은 바꾸지 않는다. PostgreSQL 통합 테스트와 AuthService 단위 테스트만 보강해 앱단 cascade·재시도·실제 경합의 불변식을 증명한다.

추가할 검증
범주증명할 결과
전체 관계 삭제탈퇴 사용자와 그 모다랏·모각·조각·일정·요일·실행·게시글·이미지·댓글·좋아요·팔로우·세션·소셜 계정·동의가 모두 사라진다. 다른 사용자의 고유 데이터는 보존한다.
빈 계정·없는 사용자관계가 없는 계정도 삭제되고, 없는 사용자는 repository에서 false, service에서 USER_NOT_FOUND가 된다. 성공 뒤 같은 토큰은 세션 삭제 때문에 인증 단계의 LOGOUT_TOKEN이 된다.
실제 경합deleteUser()가 확보한 post/users lock과 동시에 댓글·좋아요·팔로우 insert를 시작하면 insert가 대기하고, 탈퇴 commit 뒤 부모 부재로 실패한다.

한계: 현 DB FK의 ON DELETE CASCADE가 누락된 명시 delete를 가릴 수 있다. 이번 테스트는 실제 삭제 범위와 lock 결과를 증명하지만, DB cascade 자체를 제거하지는 않는다. FK 정책 변경은 별도 schema 범위다.

동기 처리 한계 — 측정 기반 제안

결정 제안: 초기 동기 탈퇴는 작은 계정에 한정한 임시 운영 방식으로만 둔다. 현재의 무제한 fan-out과 “관계 사용자 전부 advisory lock”을 그대로 둔 채로는 운영 상한을 보장할 수 없다.

동기로 감수 가능한 전제
외부 파일/검색/알림 삭제는 포함하지 않고, 삭제 transaction의 p95가 1초 이하·p99가 3초 이하임을 운영 규모 데이터에서 확인하며, 관계 사용자 lock fan-out이 작은 계정에 한정한다.
동기 방식의 중단선
한 요청이 3초를 자주 넘기거나, 대기 lock이 생기거나, 게시글·댓글·좋아요·팔로우 어느 하나가 무제한으로 자랄 수 있으면 async purge job으로 전환한다.
미룬 범위
DELETING 상태를 먼저 commit하고 새 command를 즉시 거절하는 구조, 재시도·recovery worker, 외부 오브젝트 삭제는 async 설계에서 함께 결정한다.

검증 전제: 위 수치는 비어 있는 로컬 DB에서 만든 단일 계정 fixture의 경계 증거이며, 운영 성능 예측값은 아니다. 실제 배포 후보 데이터 분포와 DB 네트워크 지연에서 EXPLAIN (ANALYZE, BUFFERS) 및 p95/p99를 다시 확인해야 한다.

ORM 삭제 전환 — 재승인 대상

변경 제안: 테이블명 문자열 raw SQL과 DELETE USING을 없앤다. 탈퇴 persistence 경로에서 Drizzle table 정의와 query builder를 사용한다. 관련 사용자 lock 대상 조회는 Drizzle typed CTE target_posts를 한 SQL 안에서 재사용하고, 삭제는 서브쿼리로 조합한다.

  1. 조회한 관련 사용자 ID는 기존처럼 정렬·중복 제거해 advisory lock에만 사용한다.
  2. 삭제는 tx.delete(table).where(inArray(column, subquery))로 수행한다. 자식부터 부모로의 순서는 유지한다.
  3. 삭제용 subquery는 lock 획득 뒤 다시 평가한다. 삭제 조건에 JavaScript ID 배열을 바인딩하지 않는다.

동시 개선 범위: lock 전에 owner를 찾기 위한 join은 유지한다. 그러나 lock 후에는 해당 owner의 탈퇴가 같은 lock 없이 진행될 수 없으므로, 실행·조각·모각·게시글의 존재 재확인은 각 PK 또는 직접 FK만 조회한다. 같은 소유권 join을 두 번째 수행하지 않는다.

  • updateExecutionStatus: 3-join 재확인 → daily_jogak_id PK 재확인
  • insertExecution, createJogakWithSchedule: owner join 재수행 → jogak_id/mogak_id PK 재확인
  • createForOccurrence: 2-join 재확인 → jogak_id PK 재확인
  • toggleLike, createComment: lock 대상 수집용 hierarchy join은 유지하고, lock 후 존재 확인은 post_id PK 재확인

실패 처리 책임 — 재승인 대상

변경 제안: lock 획득 뒤 사용자·게시글·조각 등 필수 리소스가 사라진 경우, repository가 기존 DomainException 코드(USER_NOT_FOUND, POST_NOT_FOUND, JOGAK_NOT_FOUND)를 직접 던진다. service의 try/catch, instanceof, 컨텍스트별 *AfterLockException은 제거한다.

HTTP 상태와 오류 코드는 바뀌지 않는다. 예상하지 못한 DB 오류는 기존 persistence 오류로 유지하며, 전역 FK 23503 변환은 도입하지 않는다.

설계 점검

design-control-state: 미실시 · 질문 ID: WD-CTE-01 · 2026-08-23 사용자 승인: 도메인별 CTE 삭제 배치로 왕복을 줄이되 기존 parent row lock과 앱단 명시 delete를 유지한다.

WD-CTE-01 — CTE로 삭제 왕복을 줄일 때도 앱단 cascade를 유지하려면 무엇이 반드시 필요한가?


정답: B. CTE는 왕복 절감 수단일 뿐이다. 앱단 cascade를 지키려면 자식부터 부모로의 명시 delete 의존성과 기존 lock/re-evaluation 경계를 그대로 유지해야 한다.
WD-VERIFY-01 — 탈퇴가 post/users를 FOR UPDATE로 선점한 뒤 다른 사용자가 댓글·좋아요·팔로우 insert를 시작하면, 탈퇴가 commit된 후 그 insert의 기대 결과는?


정답: B. comment·like는 post FK를, follow는 users FK를 참조한다. 탈퇴 transaction의 부모 FOR UPDATE와 FK의 KEY SHARE가 충돌하므로 insert는 대기하고, commit 뒤 부모 부재를 다시 확인해 실패한다.
WD-SYNC-04 — 게시글 10,000건의 삭제 시간이 3초를 넘는다면 어떤 판단이 맞나?


정답: B. 자식 테이블 FK 재확인도 인덱스를 필요로 하며, 현재 순차 advisory lock 비용은 관계 사용자 수에 따라 별도로 증가한다.
WD-SYNC-05 — 탈퇴가 대상 사용자만 lock할 때, 댓글·좋아요·팔로우의 동시 쓰기를 막는 조건은?


정답: B. 새 comment/like/image는 post FK를, 새 follow/session/modarat는 users FK를 참조한다. 탈퇴가 이 부모를 FOR UPDATE로 선점하면 FK의 KEY SHARE와 충돌한다.
WD-ORM-01 — 대량 계정에서 bind parameter 제한을 피하면서 lock 이후 최신 삭제 범위를 적용하려면?


정답: B. lock 대상은 애플리케이션이 정렬해 획득하되, 대량 삭제 범위는 DB subquery로 재평가한다.
WD-LOCK-02 — owner lock을 획득한 뒤 execution이 남아 있는지 다시 확인할 때 필요한 쿼리는?


정답: B. lock 전에 기다리던 탈퇴가 끝났을 수 있으므로 존재 재확인은 필요하지만, lock 획득 뒤에는 PK 재확인으로 충분하다.
WD-ERR-01 — lock 대기 후 사용자가 삭제된 경우 repository는 무엇을 반환/던져야 하나?


정답: B. 경합으로 사라진 리소스는 정상적인 not-found 계약으로 처리하되, 다른 DB 결함을 USER_NOT_FOUND로 오분류하지 않는다.
