Spring 운영 DB 배포 안정화 설계

현재 상태: G10/G13-A와 G14-A 구현 완료; 운영 제어 보류. 기존 Spring 운영 DB에 Nest API를 연결할 때 확인된 데이터 손실·프로세스 종료·자원 고갈·동시성·로그 개인정보 위험과 중첩된 PostgreSQL 오류 매핑 문제를 한 기준선으로 관리한다. Multer 전이 취약점은 상위 Nest 버전만으로 해소되지 않아 루트 override, 업로드 인덱스 상한과 안전한 400 매핑을 적용했고, audit·전체 회귀·이미지 빌드까지 통과했다. migration·세션 정책·readiness·Cloud Run CD는 계속 별도 작업으로 보류한다.

목적 (purpose)
기존 Spring 운영 DB를 사용하는 Nest API 배포가 데이터 의미를 보존하고, 예상 가능한 장애·남용·인증 오설정을 안전하게 거부하도록 만든다.
사용자 (audience)
MOGAK 백엔드 개발자, 운영 배포 담당자, 장애 대응 담당자
문제 (problem)
반복 요일 백필 손실, 끊긴 DB 연결에 의한 프로세스 종료, 무제한 날짜·페이지 조회, 최초 소셜 로그인 경쟁 실패, DB 오류 로그의 원문 노출, 약한 JWT·세션 누적, 운영 의존성 보안 권고

운영 DB 사전검사 → 안전한 레거시 백필/복구 → API 기동 검증 → 인증·조회·DB 장애 경계 → 관측·복구 증거 확인

확인된 근거

  • 고정 의존성 설치 후 pnpm format:check, pnpm lint, pnpm typecheck, pnpm build, 비DB Jest 274개는 통과했다.
  • 별도 PostgreSQL 17에서 DB 통합 24개 중 23개 통과, 동일 소셜 identity 동시 로그인 1개 실패.
  • 레거시 SQL의 현재 백필 문장을 합성 표본에 실행해 월·수 원본이 월요일 하나로 축소됨을 확인했다.
  • 성공 조회 뒤 해당 API Pool의 idle backend를 종료하자 Unhandled 'error' event와 프로세스 exit 1이 발생했다.
  • 0001-01-01 … 9999-12-31 날짜 범위와 size=1000000000이 요청 검증을 통과했다. 1,000년 배열 생성은 약 219ms의 동기 작업이었다.
  • 합성 DB 오류 파라미터가 현재 예외 로그의 message/stack에 남는 것을 확인했다. 1글자 JWT secret도 발급·검증됐다.
  • 빈 PostgreSQL에서 신규 pnpm db:migrate가 0004의 follow 테이블 참조로 실패했고, 프로덕션 의존성 감사에서 qs 6.15.3 moderate 권고 2건이 확인됐다.
  • pnpm audit --prod가 @nestjs/platform-express@11.1.28 → multer@2.2.0 경로에서 high 3건·low 1건으로 실패했다. 레지스트리 확인 결과 Nest 11 최신 11.2.3과 Nest 12.0.1도 multer 2.2.0을 exact dependency로 선언한다.
  • G14-A 구현 후 루트 override·lockfile은 multer@2.3.0 단일 트리를 가리키고, 두 이미지 업로드 정책은 fieldArrayIndexLimit: 0을 사용한다. pnpm audit --prod는 No known vulnerabilities found를 반환했고, 실제 과대 배열 인덱스 multipart 요청은 400으로 거부됐다.

시스템 모델과 경계

  1. 읽기 전용 카탈로그·데이터 사전검사를 통과시킨다.
  2. 백업·복구 지점을 확보하고, 호환 SQL을 작은 트랜잭션 단위로 실행한다.
  3. API는 강한 환경값과 DB 연결 설정으로 기동하며 readiness smoke를 통과해야 트래픽을 받는다.
  4. 요청 경계에서 비용을 제한하고, 저장소는 실패·경쟁 조건을 의미 있는 결과로 복구한다.
  5. 로그·메트릭으로 남은 장애를 탐지하고 재현 가능한 rollback/runbook을 사용한다.

설계 의사결정 초안

아래 권고는 현재 증거에 기반한 제안이다. 선택지는 사용자가 결정하며, 답변이 들어오면 이 기준선에 결정과 이유를 기록한다.

G1 · 레거시 요일 원본과 충돌 처리

현재 SQL은 시작일 요일을 추론한다. 문서와 Spring 관계 모델은 jogak_period → period.days 전체 집합을 정본으로 설명한다.

권고 A: 원본 관계에서 DISTINCT 요일을 복사하고, 고아·잘못된 요일·빈 WEEKLY·기존 대상 충돌을 사전검사에서 발견하면 쓰기 전 중단한다. 이미 잘못 이관된 행은 별도 승인된 repair 모드로만 교체한다. 자동 덮어쓰기의 편의는 포기하지만 기존 Nest 편집 손실을 막는다.

대안 B는 원본으로 기존 대상까지 자동 덮어쓰는 방식이며, 빠르지만 의미 충돌과 데이터 손실을 복구하기 어렵다.

G2 · 날짜·페이지 비용 상한

현재 API 계약은 양의 안전 정수와 날짜 형식만 검사한다.

권고 A: 날짜 범위 최대 366일, 피드·게시글 size 최대 100, page/cursor 곱셈이 안전 정수 범위를 넘지 않도록 거부한다. 초과는 기존 validation error envelope으로 반환한다. 네트워크 요약은 댓글 행을 조회하지 않는다.

대안 B는 31일/50개로 더 강하게 제한하는 방식이며 메모리 보호는 좋지만 기존 달력·피드 사용 계약을 깨뜨릴 수 있다.

G3 · DB 장애와 readiness

현재 Pool은 error 이벤트 처리기가 없고 /health는 DB를 조회하지 않는 상수 200이다.

권고 A: Pool에 안전한 error handler와 연결·쿼리 대기 timeout을 설정하고, GET /health/ready는 가벼운 DB SELECT 1 성공에만 200, 실패는 503을 반환한다. 기존 /health 계약은 유지한다. readiness에 개인정보·DB 오류·인증을 노출하지 않는다.

대안 B는 Pool handler만 추가하고 readiness를 운영 probe에서 다루지 않는 방식이며 API 계약 변화는 적지만 health false positive가 남는다.

G4 · 세션 보존

로그인마다 새 auth_sessions 행이 생기고 자연 만료 정리·사용자별 상한이 없다.

권고 A: 세션 생성 transaction에서 만료 행을 정리하고, 사용자별 활성 세션을 10개로 제한해 가장 오래된 세션부터 폐기한다. expires_at 인덱스와 운영 cleanup 명령/주기를 추가한다. 이로써 무제한 누적을 막지만 오래된 기기 로그인이 종료될 수 있다.

대안 B는 cleanup과 인덱스만 두고 세션 상한을 두지 않는 방식이며 사용자 경험은 보존하지만 계정별 무제한 누적을 남긴다.

G5 · JWT secret 오설정

README는 32자 이상을 요구하지만 런타임은 길이를 검사하지 않는다.

권고 A: 유효 secret을 UTF-8 기준 최소 32바이트로 검증하고, 누락·짧은 값·개발용 fallback이면 기동을 실패시킨다. 기존 운영 secret이 조건을 충족하는지 배포 전 별도 확인한다. 경고만 남기고 기동하는 대안은 인증 위조 위험을 남기므로 권고하지 않는다.

G6 · 오류 로그 개인정보

현재 Drizzle 오류의 message/stack에 SQL 파라미터가 들어갈 수 있다.

권고 A: DB/쿼리 오류는 오류 종류와 SQLSTATE·constraint·table 같은 allowlist만 기록하고 raw message/stack/params는 기록하지 않는다. 일반 애플리케이션 오류도 입력 원문이 포함되지 않는 안전한 snapshot만 남긴다. 진단 상세는 운영 접근 제한 DB error metric으로 대체한다.

G7 · 동시 로그인 복구

기존 설계는 exact provider identity 재조회 후 세션 발급을 승인했지만 현재 Drizzle wrapped cause를 놓친다.

권고 A: cause까지 PostgreSQL unique constraint를 판별하고 한 번만 exact identity를 재조회한다. 찾으면 RESUME 세션, 못 찾으면 원래 persistence 오류를 유지한다. 이메일만 같은 계정은 연결하지 않는다.

G8 · 신규 DB 마이그레이션 경로

빈 PostgreSQL에서 0004_withdrawal_purge_indexes.sql가 존재하지 않는 follow 테이블을 참조한다. 이번 대상은 이미 운영 중인 Spring DB다.

권고 B: 이번 배포에서는 Spring 호환 경로만 고치고, 신규 DB 경로는 별도 마이그레이션 기준선 작업으로 분리한다. 적용 이력이 있는 파일을 함께 수정하지 않는다. 신규 설치·복구도 이번 릴리스의 지원 범위라면 권고 A로 전환해 후속 migration과 빈 DB 재구축 검증까지 포함한다.

G9 · 운영 의존성 보안 패치

프로덕션 의존성 감사에서 qs 6.15.3의 moderate 권고 2건이 확인됐고 수정 버전은 6.16.0이다. 현재 Express의 simple parser 경로에서 악용 가능성은 확정되지 않았다.

권고 A: 잠금 파일을 qs >=6.16.0으로 갱신하고 audit·빌드·회귀 테스트를 다시 실행한다. 패치 후에도 실제 도달 경로가 없는지 확인한다. 대안 B는 현 버전을 유지하고 외부 WAF·모니터링으로만 완화하는 방식이며 취약 권고를 계속 남긴다.

G10 · 중첩 PostgreSQL unique 오류 매핑

UserRepository는 23505/users_nickname_unique를 오류 객체의 최상위에서만 확인한다. Drizzle이 PostgreSQL 오류를 cause에 감싸면 같은 사용자 입력 경쟁이 내부 오류로 노출될 수 있다.

권고 A: 순환 참조를 막는 cause 순회로 허용된 constraint만 판별하고, 중복 닉네임은 기존 DuplicateNicknameException 계약으로 변환한다. 다른 unique 오류와 원인 미확인은 persistence 오류로 남긴다. 데이터베이스의 고유 제약은 계속 최종 방어선으로 둔다.

G11 · 배포 설정의 외부 효과 경계

현재 Cloud Build YAML은 이미지 build/push만 수행하며 실제 서비스명·리전·service account·DB 네트워크는 저장소에 없다.

권고 A: Cloud Build에 commit SHA/digest, 단일 migration Job, no-traffic revision, readiness smoke, traffic 전환을 parameter로 선언하되 필수 substitution이 없으면 즉시 실패하게 한다. 실제 GCP 리소스 생성·secret 연결·traffic 전환은 구현하지 않고 별도 운영 승인 단계로 남긴다. 대안 B는 저장소에 현재 값을 하드코딩하는 방식이며 잘못된 프로젝트나 서비스로 배포할 위험이 있다.

G12 · 레거시 요일 충돌 복구 경계

대상에 이미 존재하는 일정이 원본 Spring 요일 집합과 다르면 자동으로 어떤 쪽이 최신인지 결정할 수 없다.

권고 A: 기본 migration은 원본 관계의 전체 요일을 신규 대상에만 복사하고, 기존 대상 불일치·고아·잘못된 값은 보고 후 전체 rollback한다. 과거 오이관 복구는 백업·대상 ID·전후 집합 보고가 확인된 별도 명령으로 분리한다. 운영 DB에서 자동 덮어쓰기나 무조건 재실행은 금지한다.

G13 · 이번 릴리스의 최소 구현 범위

전체 하드닝을 한 번에 구현하면 운영 DB와 Cloud Run 정책을 추측하게 되고, 검증 표면이 과도하게 넓어진다.

선택 A: 중첩 unique 매핑, JWT 최소 길이, Pool error/timeout, DB 오류 로그 정제, qs 잠금 파일만 이번 변경으로 구현하고, migration·세션 보존·readiness·Cloud Run CD는 별도 승인된 작업으로 보류한다. 선택 B는 전체 하드닝을 한 번에 구현하는 방식이며 대상 환경 확인과 rollback 증거가 없는 상태에서 위험하다.

G14 · Multer 전이 취약점 처리

@nestjs/platform-express@11.1.28이 multer 2.2.0을 exact dependency로 고정한다. 현재 사용하는 Nest 11 최신 11.2.3과 Nest 12.0.1도 같은 버전을 선언하므로 Nest만 올리는 방식은 감사 blocker를 해소하지 않는다. 애플리케이션은 FileInterceptor/FilesInterceptor와 고정 필드 multipartFile만 사용하고, 배열 인덱스가 필요한 multipart 필드는 없다.

결정 A · 사용자 선택 2026-09-12: 루트 pnpm.overrides.multer를 정확히 2.3.0으로 고정하고, 두 이미지 업로드 정책의 limits.fieldArrayIndexLimit을 0으로 설정한다. Multer 2.3.0의 네 감사 권고 수정과 배열 인덱스 상한을 함께 적용하고, 타입 호환용 로컬 limits 타입·업로드 정책 회귀 테스트·전체 audit/빌드/회귀 검증을 추가한다. 현재 Node 24 런타임은 Multer의 최소 Node 요구를 충족한다.

대안 B(보류)는 Nest가 패치 dependency를 제공할 때까지 2.2.0을 유지하거나 Nest 의존성을 포크하는 방식이며, high 3건·low 1건을 계속 남기거나 유지보수 부담을 만든다.

업로드multipart 런타임은 Multer 2.3.0 이상이고 배열 인덱스 상한은 이 API의 최소 요구값(0)설치·감사·업로드 정책 테스트를 통과하지 못하면 릴리스 차단

실패·복구와 운영 절차

  1. 배포 전 운영 DB read-only preflight에서 테이블/컬럼/제약/고아/요일 충돌을 출력한다. 하나라도 차이가 있으면 쓰기 단계를 실행하지 않는다.
  2. 백업 확인 후 호환 SQL을 실행하고, 커밋 전 요일 집합·행 수·제약을 다시 비교한다. 실패하면 전체 transaction을 rollback한다.
  3. 새 revision은 readiness DB probe와 인증·조회 smoke가 모두 성공한 뒤 트래픽에 연결한다. 기존 health는 liveness로만 사용한다.
  4. Pool error, DB timeout, 5xx, 429, readiness 503, session cleanup 건수, migration 차이를 구조화 metric/log로 관측한다.
  5. 전환 후 요일 차이가 발견되면 원본·대상 집합을 보존한 별도 repair report를 만들고 승인된 ID만 원자적으로 복구한다. 원본을 직접 수정하거나 무조건 재실행하지 않는다.
금지: 운영 DB에서 현재 SQL을 그대로 재실행하거나, 실제 운영 URL로 통합 테스트를 실행하거나, 충돌 행을 원본 기준으로 자동 삭제·덮어쓰기하지 않는다.
