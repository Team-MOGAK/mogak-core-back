2. 변경 원칙과 범위

모든 브랜치 push와 모든 PR 대상에서 Prettier, lint, typecheck, DB가 필요 없는 테스트 전체, 애플리케이션 빌드를 수행한다. 초기에는 경로 필터나 브랜치별 검사 축소를 두지 않는다.

CI YAML의 문법·표현식 검사와 runtime 이미지 조립 검증도 같은 이벤트에서 수행하는 것을 권고한다. 문서만 변경한 push와 draft PR도 동일하게 검사한다.

유지할 불변식: DB 서비스·실제 DB 접속·마이그레이션·배포는 실행하지 않는다. 일반 Jest에 포함된 schema 정의 테스트나 가짜 저장소 테스트는 실행할 수 있다. 운영 자격증명을 runner에 전달하지 않는다.

이번 설계의 완료는 CI 정책 확정이다. Cloud Build/Cloud Run 변경, 이미지 업로드, 컨테이너 서비스 기동, DB 테스트 도입은 별도 범위다. CI 성공은 배포 환경·DB 호환성 검증 성공을 뜻하지 않는다.

3. 언제, 무엇을 검사하는가

이벤트별로 검사 내용은 같고 검사하는 Git 상태가 다르다
계기검사 대상검사 범위최종 체크 이름 제안
모든 브랜치 pushpush된 브랜치의 마지막 커밋전체 검사CI Push
모든 대상 브랜치의 PRPR head와 base를 합친 GitHub test merge commit전체 검사CI Required
main에 병합되어 발생한 push실제로 main에 반영된 커밋전체 검사CI Push
수동 실행선택한 ref전체 검사CI Manual
merge_group / checks_requested병합 대기열의 test merge commit전체 검사CI Required

push.branches: ['**'], PR에는 브랜치 필터를 두지 않는다. PR은 opened, synchronize, reopened, edited, ready_for_review를 받는다. edited는 대상 브랜치 변경을 포함하기 위한 선택이며 제목·본문 수정에도 재실행되는 비용을 우선 수용한다. 태그 push는 자동 실행 대상이 아니다.

같은 push에서 push run과 PR run이 생기는 것은 별개의 Git 상태를 검사하기 때문이다. 중복이라는 이유만으로 둘 중 하나를 취소하지 않는다. 실행별로 event, head SHA, base SHA, 실제 checkout SHA를 요약에 남긴다.

동시 실행 그룹은 고정된 CI 식별자 + event + PR 번호 또는 ref + 검사 SHA로 구분한다. 서로 다른 SHA는 끝까지 검사하고, 같은 이벤트·ref·SHA의 중복 실행만 대체한다. 과거 SHA의 재실행이 새 SHA 검사를 취소하지 않도록 한다. GitHub의 실행 순서는 커밋 시간순으로 보장되지 않으므로 단순 ref 단위 취소를 “최신 커밋 보장”이라고 부르지 않는다.

플랫폼 예외: 커밋 메시지의 [skip ci] 등 GitHub skip 지시문은 workflow 자체를 시작하지 않게 한다. 팀 운영에서는 사용하지 않는 정책을 명시하고, 보호된 PR은 CI Required가 없으면 병합하지 못하도록 한다. 이 workflow 하나로 보호되지 않은 개인 브랜치의 skip 지시문까지 강제로 무력화할 수 있다고 보장하지 않는다.

PR 충돌이나 GitHub의 외부 기여자 실행 승인 대기는 통과가 아니다. base 갱신으로 기존 검증이 낡았으면 branch update 또는 merge queue 검증이 필요하다. merge_group 이벤트 지원은 준비하되 merge queue 자체는 이번에 활성화하지 않는다.

고정된 8개 검사는 format, lint, typecheck, test, scripts, build, workflow-lint, image라는 명시적 독립 job으로 구성한다. 하나의 검사 실패 때문에 다른 job을 취소하지 않으며, 실패를 성공으로 취급하는 continue-on-error는 두지 않는다. 현재는 버전 조합이 없으므로 matrix를 도입하지 않고 각 결과를 직접 합산한다.

Node/pnpm 설치 단계는 저장소 내부 composite action 등 한곳에 모은다. 각 runner에서 frozen lockfile 설치를 하고 pnpm store 캐시만 재사용한다. runner 간 node_modules 공유나 별도 설치 산출물 업로드는 도입하지 않는다. 병렬화는 runner 사용 시간·설치 횟수를 늘리므로 실행 시간과 대기 시간을 함께 관찰한다.

5. 성공 표시와 병합 강제를 연결한다

최종 합산 job은 8개 검사 모두를 needs에 명시하고 job 조건에는 if: always()만 둔다. 모든 결과가 정확히 success인지 job 내부 step에서 검사해 하나라도 다르면 exit 1이다. 성공 조건을 job의 if에 붙여 실패 시 합산 자체가 skipped가 되는 구현은 금지한다. 실패·취소·누락·skip은 성공으로 합산하지 않는다. 전체 workflow 취소나 runner 장애로 합산 자체가 완료되지 않은 경우도 병합 허용 근거가 될 수 없다.

합산 job은 하나이며 이벤트에 따라 표시 이름을 선택한다. PR/merge_group에서는 CI Required, push에서는 CI Push, 수동에서는 CI Manual이다. push에 이름만 같은 skipped CI Required job을 만들지 않는다.

현재 main 보호가 없으므로 운영 적용에는 GitHub ruleset이 필요하다: PR 경유, GitHub Actions의 CI Required 필수, base 최신 상태 요구, 일반 우회 비허용. 장기 통합 브랜치가 추가되면 해당 대상에도 같은 병합 규칙을 적용하고 개인 작업 브랜치 push는 허용한다.

체크 이름과 GitHub Actions App 지정은 특정 workflow를 잠그는 장치가 아니다. .github/ 전체(다른 workflow·공통 action·CODEOWNERS 자체 포함)와 검사 실행 계약을 바꾸는 파일에는 실제 관리자를 CODEOWNERS로 지정하고 보호 대상에서 해당 소유자 승인 및 오래된 승인 무효화를 요구하는 것을 권고한다. 관리자 계정/team을 임의로 만들지 않으며 설정 적용 전에 지정한다. 이는 신뢰 가능한 리뷰 경계이고, 같은 저장소의 기여자가 변경 가능한 검사 코드 전체를 암호학적으로 보장하는 장치는 아니다.

CI 실행 대상을 모든 브랜치로 만드는 것과 모든 개인 브랜치의 직접 push를 금지하는 것은 별개다. 모든 PR은 검사하되, 병합 강제 정책은 main 및 실제 공유 통합 대상에 적용한다.

GitHub는 skipped job을 병합 가능한 결과로 볼 수 있으므로 단순히 job을 required로 등록하는 것만으로 검증 완료를 보장하지 못한다. GitHub 필수 체크 문서에 따라 합산 job의 실패 경로와 실제 병합 차단을 확인한다.

6. 이미지 빌드는 모든 이벤트에 포함하는 것을 권고

이 저장소는 Dockerfile로 production dependency만 설치한 runtime을 조립한다. 일반 빌드 성공만으로 해당 설치·파일 복사 과정이 성공한다고 보장할 수 없다. 기존 PR 실행에서 Docker build step은 약 32초, 일반 Jest는 약 163초였다. 단일 과거 표본이므로 성능 보장은 아니지만, 현재 병렬 검사에 포함할 근거는 충분하다.

권고안: 모든 브랜치 push·모든 PR·수동 실행에서 이미지 빌드도 필수 검사로 둔다. 이미지 검사에 main 조건이나 변경 경로 필터를 두지 않는다. 업로드·배포·서비스 기동은 포함하지 않는다.

대안은 이미지 전용 workflow를 따로 두거나 Docker 관련 파일이 바뀔 때만 실행하는 것이다. 비용은 줄지만 source, lockfile, runtime file layout 변경을 빠뜨리지 않도록 경로 정책을 계속 관리해야 한다. 지금은 이 복잡성을 도입하지 않는다.

이 결론이 실패한다면: 향후 cold build·다운로드 지연으로 runner 비용과 대기열이 크게 늘어날 수 있다. 누적 실행시간을 본 뒤 BuildKit cache를 먼저 검토하고, 그 후에도 문제가 있으면 별도 정책으로 재검토한다. 현재 cache 구조를 과도하게 확장하지 않는다.

7. 권한·재현성·실패 운영

기본 권한은 contents: read, checkout은 persist-credentials: false다. PR 코드를 운영 자격증명과 함께 실행하지 않도록 GitHub-hosted runner와 pull_request 이벤트를 사용한다. 외부 fork PR은 GitHub의 실행 승인 정책을 그대로 따른다.

Node/pnpm은 현재 package 계약과 맞추고 lockfile 고정 설치를 유지한다. 외부 action은 검증한 SHA로 고정한다. Dockerfile의 Node runtime base는 실제 확인한 manifest digest sha256:a0b9bf06e4e6193cf7a0f58816cc935ff8c2a908f81e6f1a95432d679c54fbfd로 고정한다. 기존 버전 숫자를 최신 main과 대조하지 않고 복사하지 않는다.

각 검사에는 timeout을 둔다(일반 검사 10분, 테스트 15분, 이미지 15분, 합산 2분을 초기값으로 제안). 설치 실패는 해당 검사 실패, 테스트 실패는 다른 검사 계속, 네트워크 장애도 실패로 표시한다. 무제한 재시도·강제 성공·실패 테스트 생략을 넣지 않는다. 원인 수정 또는 일시 장애 확인 후 해당 run을 재실행한다.

run 이름과 Step Summary에 이벤트, 대상/base 브랜치, 실제 검사 SHA, 검사별 결과와 로그 링크를 기록한다. 브랜치명·PR 제목을 shell 코드에 직접 삽입하지 않고 환경변수로 전달해 인용 처리한다. 테스트 결과 JSON/TAP 등은 필요시 7일 보관하고 실행 실패 시에도 업로드를 시도한다. 파일이 생성되기 전 실패했다면 원래 실패를 보존하고 산출물이 없다고 명시한다. secret·환경변수 전체 dump는 남기지 않는다.

테스트·이미지·설정 검사 각각 실패 또는 예기치 않은 skip각 실패가 합산을 실패시킨다. dependency skip을 성공으로 해석하지 않는다.
PR에 연속 push / 대상 브랜치 변경 / 과거 SHA 재실행각 검사 SHA를 유지하며 과거 실행이 최신 SHA를 취소하지 않는다. 동일 이벤트·ref·SHA 중복만 대체한다.
skip 지시문 / 가짜 CI Required 추가 시도필수 체크 누락은 보호 대상 병합 차단. 검사 계약 변경은 CODEOWNERS 승인으로 통제한다.
push 성공, PR 실패 또는 수동 실행만 성공CI Required를 대체하지 못하므로 보호 대상 병합이 막힌다.
운영 secret·DB 서비스가 없는 runner지원하는 모든 검사가 통과. DB 마이그레이션 실행 흔적 없음.
main 병합 후 push / 수동 실행 / 향후 queue해당 상태의 전체 검사. queue 채택 전 merge_group 실제 실행을 별도 검증한다.
  1. 최신 main을 작업 브랜치에 반영하고 테스트 목록·명령·Dockerfile 계약을 재확인한다. 기존 앱 변경은 CI 작업과 분리한다.
  2. workflow, 공통 setup, 검사 명령 범위, 결과 요약을 구현하고 정적 검사를 수행한다. 실패 시나리오는 검증용 checkout/ref에서만 시험하고 의도된 실패 코드를 최종 변경에 남기지 않는다.
  3. PR #15에서 새 check 이름과 전체 성공을 확인한다. 저장소 보호 설정과 PR 병합은 실제 적용 단계로 구분한다.
  4. main 보호에 새 CI Required와 관리자가 지정된 CODEOWNERS 승인 정책을 등록하고 실패/누락 상태의 병합 차단을 확인한다. 부트스트랩 순서를 사전에 정해 체크 이름 변경으로 인한 영구 대기를 방지한다.
  5. PR 병합 후 main push를 확인한다. 기존 장기 작업 브랜치는 workflow 변경을 merge/rebase로 받아야 push 정책이 적용된다. 새 main에서 분기한 브랜치는 해당 설정을 상속한다.

수동 실행의 Actions UI는 기본 브랜치에 workflow가 존재하는 것이 전제다. workflow 파일 하나를 PR에 올렸다고 과거 브랜치들에 소급 적용됐다고 보고하지 않는다.
