모바일-서버 헬스 핑 프로토콜

목적
Cloud Run scale-to-zero 환경에서 모바일 앱이 기존 health ping으로 서버 기동을 기다린 뒤, 초기 데이터를 안전하게 요청한다. DB readiness 보장은 관측 후 필요할 때만 추가한다.
사용자
모바일 앱 사용자 및 API/프런트엔드 구현 담당자
문제
6~7초가 걸리는 콜드스타트 동안 첫 업무 API가 실패·중복 호출되거나 무한 로딩으로 보이는 문제
핵심 흐름
앱 셸 표시 → readiness ping → 준비 확인 → 초기 데이터 호출 → 성공 또는 제한된 복구 UI
추적
Codex task `/root` · 생성/갱신: 2026-08-24

목표와 비목표

목표: 최초 화면에서 서버 준비 여부를 먼저 판정하고, 준비된 경우에만 초기 업무 API를 호출한다. 준비에 실패하면 제한된 시간 안에 명확한 재시도 UI로 전환한다.

비목표: 모든 API의 자동 재시도, 업무 API의 성공 보장, max instances=3에서의 용량 부족 해결, 장기 장애를 로딩 화면으로 은폐하는 것은 범위 밖이다.

시스템 모델과 런타임 순서

  1. 앱은 즉시 셸/스켈레톤과 “서비스 준비 중” 상태를 표시한다.
  2. 초기 화면 단일 조정자가 기존 GET /health를 호출한다. 같은 화면·앱 세션에서는 동시에 하나만 실행한다.
  3. 200 OK를 받으면 초기 읽기 API(bootstrap 또는 기존 초기 조회 묶음)를 시작한다.
  4. 허용된 일시 오류면 한정 재시도하고, 시간 예산을 넘기면 재시도 버튼이 있는 복구 화면으로 바꾼다.

단계별 API 계약

1단계(MVP): 기존 GET /health를 그대로 모바일 wake-up ping으로 사용한다. 응답·controller·서버 로직을 바꾸지 않는다. 2단계(필요 시): health 200 뒤 초기 업무 API의 DB 장애가 실제로 관측될 때만 GET /health/ready를 별도 추가한다.

헬스 endpoint의 책임 분리
endpoint성공실패사용처
GET /health200 {"status":"ok"}: 프로세스가 HTTP를 응답할 수 있음프로세스 자체 응답 불가1단계 모바일 wake-up ping·liveness·기존 운영 호환
GET /health/ready (선택)200 {"status":"ready"}: 앱과 첫 화면에 필수인 DB 연결/가벼운 query가 가능503 {"status":"unavailable"}: 필수 의존성이 불가2단계의 실제 DB readiness 보장

1단계에는 기존 /health 응답과 header를 변경하지 않는다. 2단계가 필요해지면 readiness 응답은 Cache-Control: no-store로 하며, 인증·사용자 데이터·내부 인스턴스 식별자·상세 오류는 응답하지 않는다. 프런트는 status와 자체 retry budget으로 재시도 여부를 결정한다. 서버가 rate limit·과부하 때문에 특정 대기 시간을 강제해야 할 때만 선택적으로 표준 Retry-After header를 보낸다.

0–3 인스턴스 보완: 공개 HTTP 응답은 cache하지 않지만, 서버 내부 readiness 검사는 인스턴스별 1초 결과 캐시와 in-flight 공유를 사용한다. 같은 인스턴스에 동시에 100개의 ping이 도착해도 DB SELECT 1은 한 번만 실행하고 결과를 공유한다.

Cloud Run startup probe와 콜드스타트 단축

관측된 현재 설정: TCP port 3000, initialDelaySeconds=5, periodSeconds=5, timeoutSeconds=2, failureThreshold=12. Nest가 5초 이전에 포트를 열어도 첫 probe는 5초까지 실행되지 않는다. 이후 포트가 열린 직후에도 다음 5초 주기까지 기다릴 수 있으므로, 이 설정은 traffic 허용에 0~5초(평균 약 2.5초)의 추가 지연을 만들 수 있다.

probe의 시간 값을 낮추는 것만으로 NestJS 프로세스 자체가 빨라지지는 않는다. 다만 현재처럼 고정 초기 지연과 긴 주기가 있으면 이미 준비된 컨테이너를 traffic에 늦게 연결할 수 있다. 너무 짧은 실패 한도는 느린 기동을 장애로 오판해 재기동 루프를 만들 수 있다.

현재 저장소에는 Cloud Run 배포 YAML/Terraform 설정이 없어 적용 중인 probe 값과 CPU boost 활성화 여부를 확인할 수 없다. 따라서 이 표는 변경안이지 현재 상태 진단 결과가 아니다.

  1. 먼저 프로세스 시작, Nest app module 생성 완료, listen, 첫 DB readiness 성공에 각각 timestamp를 기록한다.
  2. Cloud Run startup duration p50/p95/p99와 맞춰 이미지 pull·Node/Nest bootstrap·DB readiness 중 병목을 분리한다.
  3. CPU boost를 켠 revision을 canary로 비교한다. 그 뒤 image/dependency/import graph를 최적화한다.
  4. 마지막에만 failureThreshold를 관측된 p99보다 넉넉하게 조정한다. probe를 짧게 해서 startup을 강제하지 않는다.

프런트엔드 원인 분류: 확정이 아닌 안전한 추론

Cloud Run 인스턴스가 0개인 동안에는 서버가 응답 본문을 보낼 수 없다. 따라서 모바일 앱은 timeout·edge 5xx만으로 콜드스타트를 확정하면 안 된다. 앱은 사용자에게 안전한 실패 상태를 보이고, cold-start 추정은 이후 서버/Cloud Run 지표와 상관 분석해 확정한다.

baseMs = retryAfterMs ?? 0
jitterMs = random(0, min(3_000, 1_500 * 2^(attempt - 1)))

운영·관측

  • 서버: health_ready_latency, ready/not-ready 응답 수, DB probe 실패 원인 분류, 503·429 비율
  • 모바일: cold/warm 추정별 ping 완료 시간, retry 횟수, 25초 내 준비 성공률, 복구 화면 도달률·이탈률
  • Cloud Run: startup duration, 요청 지연·상태 코드, 인스턴스 수·concurrency, max=3 도달 시점

로그에는 요청 correlation ID와 결과 분류만 남기고, 기기 식별자·토큰·사용자 정보는 health ping에 추가하지 않는다.

수용 기준과 검증 계획

  • /health의 기존 200 계약과 rate-limit 제외가 유지되며, 1단계에서는 서버 코드 변경이 없다.
  • 2단계로 전환할 경우에만 DB가 사용 가능할 때 /health/ready가 200 ready를 반환하고, 불가 시 503·Retry-After: 2만 반환한다. raw DB 오류는 노출하지 않는다.
  • 모바일은 ping 성공 전 초기 업무 API를 호출하지 않고, 허용 오류 외에는 재시도하지 않는다.
  • 모바일은 원인 분류를 terminal state와 함께 기록하되, timeout/edge 오류만으로 콜드스타트를 확정·표시하지 않는다.
  • 동시 앱 진입·화면 재렌더링에도 앱 세션별 ping 중복이 없고, 동일 인스턴스의 readiness DB probe는 1초 결과 캐시/in-flight 공유로 합쳐져 DB pool에 오래 머물지 않는다.
  • 동시 503/429 및 slow-ready 시나리오에서 foreground 1회당 ping은 최대 3회이며, Retry-After와 jitter 이후에만 재개된다.
  • scale-to-zero, DB 불가, 네트워크 단절, 429/503, 화면 이탈을 포함한 통합 검증을 수행한다.

구현 전 확인할 미해결값: 모바일 네트워크 라이브러리의 cancellation/timeout 방식, 목표 최초 진입 SLO. Cloud Run probe에 동일 endpoint를 쓸지는 앱 handshake와 실패 의미가 달라 별도 운영 결정으로 남긴다. 2단계로 전환할 때만 DB 외 필수 의존성과 Retry-After 사용 여부를 확정한다.
