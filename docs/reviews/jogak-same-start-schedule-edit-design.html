목표와 비목표

PUT /api/jogaks/:jogakId을 PATCH /api/jogaks/:jogakId로 전환하고, UI가 실제로 수정하는 요일·종료일만 PATCH 요청으로 받는다. 시작일은 UI 입력도 PATCH 변경 필드도 아니다.

비목표: 시작일 변경 UI·새 일정 이력 생성·실행 기록 재작성은 포함하지 않는다.

변경 모델

일정 이력 경계

현재 일정 뒤에 이미 시작하는 일정이 있으면, 현재 일정의 종료일은 그 후속 일정 전날을 넘을 수 없다. PATCH에서 종료일을 생략해도 이 경계는 유지한다. 즉, 현재 일정의 요일·종료일을 고쳐도 같은 날짜에 같은 조각이 두 번 발생하지 않는다.

결정 기록

PATCH 대상 식별 방식
결정선택한 방식근거
조각 수정 안에 일정 수정 포함PATCH /api/jogaks/:jogakId에서 KST 오늘 적용 중인 schedule을 서버가 선택한다.모바일 UI가 조각을 편집하며, 사용자가 schedule ID나 시작일을 선택하지 않는다.
별도 schedule 경로이번에는 사용하지 않는다.조각 편집 흐름을 둘로 나누고 UI가 없는 대상 선택 정보를 요구하게 된다.

편집할 때 지키는 규칙

사용자가 일정을 수정했을 때의 처리
수정 상황서버가 하는 일사용자에게 보장되는 결과
요일이나 종료일 변경현재 일정을 새로 만들지 않고 그 자리에서 수정한다.“이미 같은 날 일정이 있다”는 오류 없이 변경한 요일이 반영된다.
시작일기존 값을 그대로 유지한다.수정 화면에서 의도하지 않은 시작일 변경이 일어나지 않는다.
반복 일정에서 한 번만 하는 일정으로 변경일정 설정에 있는 반복 요일과 종료일만 지운다. dailyJogak 등 이미 남은 실행 기록은 건드리지 않는다.앞으로는 반복 요일에 표시되지 않으며, 이전에 수행한 기록은 그대로 남는다.
이미 완료·실패 등으로 기록된 실행이 있음이미 남은 실행 기록은 건드리지 않는다.과거 실행 상태와 당시 제목이 사라지거나 바뀌지 않는다.
중요한 선택: 시작일이 지난 일정도 수정할 수 있지만, 시작일 자체는 바꾸지 않는다. 이미 기록된 실행은 “그날 실제로 남긴 기록”으로 보고 그대로 둔다. 새 요일이나 기간에 맞춰 과거 기록을 지우거나 다시 만들지는 않는다.

실패 처리와 관측

날짜·요일 규칙 위반의 J009/J013 처리는 유지한다. 제거하는 것은 오직 “현재 일정과 같은 시작일이 이미 있다”는 거부다.

배포 후 J009이 발생하면 요청의 날짜 형식, 종료일 순서, 요일의 빈 값·중복·지원하지 않는 값을 확인한다.

검증 계획

  1. UI가 보존한 기존 시작일로 PUT 수정 뒤 schedule 행 수와 ID, 시작일은 그대로이고 요일 집합·종료일만 요청값으로 바뀌는지 통합 테스트한다.
  2. WEEKLY→ONCE 전환 뒤 요일 행 0개·종료일 null을 확인하고, 기존 dailyJogak/실행 기록의 상태·제목 스냅샷이 그대로인지 확인한다.
  3. 시작일이 다른 요청의 현행 동작은 변경되지 않는지 회귀 테스트한다.
  4. 관련 Jest·typecheck·lint를 실행한다.

후속 개선: 수정 API 공통 RFC

현재 PUT /api/jogaks/:jogakId은 제목만 또는 schedule을 포함한 일부 필드만 받으므로 부분 수정 성격이다. 이번에는 모바일 호환을 위해 엔드포인트와 요청 형식을 유지한다. 이후 RFC: 수정 API의 JSON Merge Patch 계약을 정립한다에서 Jogak에 한정하지 않고 모든 수정 API의 JSON Merge Patch(RFC 7396) 적용 기준, null·배열·불변 필드 규칙, PUT/PATCH 전환 및 모바일 버전 호환 정책을 함께 결정한다.
