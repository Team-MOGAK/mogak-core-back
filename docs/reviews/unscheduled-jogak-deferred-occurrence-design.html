제안 모델

isRoutine: false이고 날짜 또는 명시 schedule이 없으면 Jogak 행만 생성하고 일정 행은 만들지 않는다. 이 조각은 발생 조회, 실행 상태 변경, 날짜별 목록에 나타나지 않는다. 명시 일정 요청은 현재와 같이 일정과 함께 생성한다. 루틴은 계속 시작일과 요일을 필요로 한다.

현재 DB의 jogak_schedules.jogak_id은 Jogak을 참조하지만, Jogak 하나에 일정이 반드시 있어야 한다는 DB 제약은 없다. 다만 repository·application·응답은 “생성과 동시에 일정 1개”를 전제로 하므로 이를 분리해야 한다.

실행·목록 경계

현재 제약: 기존 PUT /api/jogaks/:jogakId는 제목을 필수로 받으며 일정 이력을 추가할 수 있지만, ‘일일 조각 추가’ 전용 API는 없다. 과거 daily_jogak 경로는 제거·거부되고 실행 API는 유효한 일정 발생에만 동작한다.

API 경계 결정

선택: 기존 POST /api/jogaks/:jogakId/executions/:executionDate/start를 확장한다. 이 요청은 일정이 있으면 기존 발생을 시작하고, 일정이 전혀 없으면 지정 날짜의 독립 실행을 만들어 일일 조각을 추가한다. 제목 변경이나 별도 schedule API는 필요 없다.

이 선택은 실행을 만들기 전 일정 발생을 요구하던 기존 계약을 바꾼다. 따라서 독립 실행을 날짜별 조회와 게시글의 발생 검증에서도 일관되게 유효한 발생으로 해석해야 한다.

확정 제안: execution start로 일회성 발생 생성

무일정 조각에 POST /api/jogaks/:jogakId/executions/:executionDate/start를 호출하면, 해당 날짜의 실행 행을 IN_PROGRESS로 생성한다. 이 실행 행이 곧 사용자가 추가한 일일 조각(일회성 발생)이다. 별도 일정 행은 만들지 않는다.

현재 구현은 이 요청 전에 occursOn(schedule, executionDate)를 확인하고, 일정이 없으면 INVALID_TARGET_DATE를 반환한다. 변경 후에는 일정에서 발생한 날짜는 기존대로 처리하고, 일정이 전혀 없는 소유 조각에만 실행 행 직접 생성을 허용한다. WEEKLY·ONCE 일정은 임의 날짜 실행을 계속 거부한다.

불변식과 실패 처리

  • 무일정은 오직 명시적으로 isRoutine: false인 legacy 요청에만 허용한다. isRoutine 생략·루틴의 시작일 누락은 계속 거부한다.
  • 무일정 조각은 모각의 ‘현재 또는 미래 일정이 있는 조각 8개’ 제한에 포함하지 않는다.
  • 일정이 있는 조각은 기존 ONCE·WEEKLY 발생 규칙을 유지한다. 일정이 전혀 없는 조각만 executionDate start로 독립 실행을 만들 수 있다.
  • 잘못된 날짜나 권한 없는 조각에는 실행을 만들지 않는다. 실행 insert가 실패하면 무일정 조각은 그대로 남고, 부분 일정이나 실행 기록은 만들지 않는다.

검증 계획

  • 무일정 legacy 생성이 Jogak만 저장하고 응답에서 일정이 없음을 표현하는지 확인한다.
  • 무일정 조각이 실행 전에는 날짜별 목록에 없고 8개 일정 제한을 소비하지 않는지 확인한다.
  • executionDate start가 무일정 조각의 독립 실행을 만들고, 날짜별 목록·게시글의 발생 검증에서 이를 찾는지 확인한다.
  • 일정이 있는 조각의 임의 날짜 start, 날짜·소유권 오류는 기존처럼 원자적으로 거부되는지 확인한다.
  • 명시 일정 생성과 루틴 검증의 기존 계약 회귀 테스트를 실행한다.
