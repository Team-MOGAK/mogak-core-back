목표와 범위

리뷰가 달린 행뿐 아니라 API producer, alerting의 모든 계층, 운영 도구, 테스트·빌드 연결에서 중복 정의와 불필요한 자체 구현을 정리한다. 기존 구조와 정의를 먼저 재사용하고 독립 배포·오류 전달의 안전성은 유지한다.

현재 명시 승인된 경계는 alerting 기능 모듈 / domain 계층 없음이다. 2026-10-16 승인안의 shared 추출 제외·production 고정·수동 route 목록은 리뷰 수정안에서 달라졌고 사용자가 ㄱㄱ로 승인했다. 이후 PostgreSQL 대체안을 검토했으나 사용자가 공유 상태 보장은 아직 필요 없다고 명확히 했다. 저장소 없는 전달 축소안은 2026-10-17 명시 승인됐다. 이전 승인 기준을 기록으로 보존한다.

전체 재리뷰 AR1–AR6 · 이번 승인 범위

같은 목적·사용자·문제·전달 흐름의 후속 수정이다. 이전 저장소 없는 전달 승인은 이력으로 보존한다. 요청 제한·시작 준비·입력 계약·검증 방식의 이번 변경은 별도 승인 질문에 대한 사용자의 “ㄱㄱ”로 승인됐다(2026-10-17). 아래 수정안을 구현 기준으로 삼는다.

재확인한 원인과 최소 수정
항목 수정할 동작·구조 재사용·삭제 경계
AR1 · 요청·격리 제한 시간 내부 요청 예산 12초, Cloud Run 설정은 정확히 15초로 고정한다. 두 격리 경로에 deadline을 전달한다. 격리는 남은 시간과 2초 중 작은 값으로 RPC timeout을 정하고 SDK 재시도는 끈다. 남은 시간이 없거나 연결이 종료되면 다음 외부 호출을 시작하지 않는다. Discord fetch에는 취소 signal을 전달한다. 기존 SDK의 v1.PublisherClient로 단일 메시지를 직접 publish한다. Topic의 배치 큐를 거치지 않는다. 인증·stub 초기화는 RPC timeout 밖에 있으므로 initialize() 완료 후 HTTP listen을 시작한다. 새 SDK·범용 실행 래퍼는 없다.
AR2 · 429 응답 크기 성공·429 응답에 같은 64KiB 제한 reader를 적용한다. 초과·손상된 본문은 무시하고 유효한 Retry-After header 또는 기존 fallback 대기를 적용한다. 429는 non-ACK다. DiscordClient 내부의 기존 읽기 함수를 재사용한다. 별도 util 패키지는 없다.
AR3 · 검사 경로 scanner의 sourceRoot와 projectRoot를 구분하고 프로젝트 상대 경로 libs/shared/src와 apps/alerting/src/application으로 판정한다. 상대 import 대상도 실제 shared 루트 내부인지 확인한다. 기존 architecture scanner와 실제 모양의 fixture를 사용한다.
AR4 · API 빌드 API/Jest는 기존 방식대로 @mogak/shared source alias를 소비한다. 루트의 runtime workspace 의존성·선행 shared 빌드·별도 watcher·webpack externals 재정의·API runtime shared 산출물 복사를 제거한다. ESM alerting의 CJS shared 패키지와 의존 빌드는 유지한다. 공식 정의는 하나다.
AR5 · 로그 계약 검사 새 errorAlert.contract.spec.ts AST scanner를 삭제한다. 모든 .error()를 로그로 취급하거나 저장소 전체 이름으로 helper를 찾는 검증은 중단한다. 실제 exception filter·DB pool·Pino 옵션·Nest/Pino 통합 테스트로 metadata와 중복 억제를 확인한다. 기존 producer 테스트를 보강한다. 새 scanner·logger wrapper·전역 타입 체계는 만들지 않는다. 모든 미래 .error()를 자동 탐지한다는 보장은 하지 않는다.
AR6 · 불필요한 계약 sender는 AlertSummary만 받는다. raw payload overload·미사용 retryAfterMs export·application에서 소비하지 않는 결과 필드는 제거한다. parsePushEnvelope의 expectedSubscription은 필수 문자열 하나로 통일한다. 테스트도 production 계약을 사용한다. 내부 cooldown과 안전한 payload 투영은 유지한다.
공개 PublisherClient API는 진행 중 RPC의 AbortSignal/cancel을 지원하지 않는다. 시작 전 취소·남은 시간 검사는 적용하지만 이미 시작한 RPC는 최대 2초 deadline까지 진행할 수 있다. 로컬 timeout은 원격 미발행을 증명하지 않는다. 발행 실패는 non-ACK이며 격리 중복 가능성은 유지한다. 단순 Promise.race로 SDK 재시도를 남기는 방식은 쓰지 않는다.

범위 밖

새 domain/notification 프레임워크, provider 추가, alerting의 전면 Nest/CJS 전환, 운영 DB 마이그레이션 적용·배포/IAM 변경/웹훅 발송, 기존 Firestore 데이터 자동 이관·삭제, 브랜치 전략 변경은 포함하지 않는다. 특정 PostgreSQL 호스팅 제공자나 신규 Cloud SQL 도입을 가정하지 않는다.

환경 고정·중복 DTO production literal이 Alert/요약/입력/quarantine/deploy에 분산 SOURCE_ENVIRONMENT(development|production)를 필수 주입한다. worker NODE_ENV와 구분한다. 안전한 Alert를 한 번 확정하고 같은 필드를 다시 선언·투영하는 Summary/Classified 타입은 파생하거나 제거한다.

정책·검증 중복 기존 *.policy.ts 관례, application/infra의 중복 cooldown 값, 두 URL validator 책임별 policy에 유일하게 정의한다. 고정 제한과 실행 환경 설정을 분리하고 URL 검증도 한 구현을 재사용한다. 숫자가 같다는 이유로 관계없는 정책을 전역 집합으로 묶지 않는다.
새 인터페이스·래퍼 남발 기존 application/{service,port,type} 및 순수 class+constructor port 관례 새 domain 없이 기존 service/port/type/policy 명명·배치를 따른다. 의미 없는 재-export alias, 일회용 wrapper, 테스트를 위해 만든 생산 코드 FirestoreLike와 main의 이중 캐스팅을 제거한다. 실제 반복되는 검증 불변식은 유지한다.
병렬 검사 체계 기존 layerBoundaries 검사, verify-local/CI 새 경계 검사기를 추가하지 않고 기존 검사 범위를 alerting/shared까지 확장한다. 테스트는 기존 runner를 재사용하고 명령을 test:alerting / test:alerting:ops로 명확히 하며 CI/local gate 참조를 함께 갱신한다.

의존·빌드·전달 모델

API CJS/Nest는 기존 TypeScript/Jest source alias로 libs/shared/src를 직접 소비하고 기존 Nest bundle/watch를 사용한다. API에는 shared 선행 빌드나 runtime package link가 필요하지 않다. alerting Node ESM은 CJS로 빌드한 private shared package의 exports/types를 사용한다. 이 소비 경로에만 shared 선행 빌드·production workspace link를 유지한다. ESM 소비에서는 default import를 사용해 CJS synthetic named export 추론에 기대지 않는다. 라이브러리 TS를 alerting에서 직접 상대 import하는 우회는 쓰지 않는다.

API runtime에 Google SDK가 추가되지 않아야 하며 shared도 Nest/Google SDK/DB 의존성을 갖지 않는다. 기존 libs/core와 libs/modules를 새 pnpm package로 전환하지 않는다.

저장소 없는 전달 — 현재 제안

Firestore는 요청 없이 이번 기능에서 새로 도입했다. 이를 합의된 전제로 취급한 기록을 바로잡는다. PostgreSQL 대체안도 공유 상태 보장을 전제했으므로 철회한다. 사용자는 그 보장이 아직 필요 없다고 명확히 했다.

  • Firestore SDK·상태 adapter·환경변수·API/IAM/preflight·channel 운영 명령을 제거한다. PostgreSQL 테이블·migration·접속 설정은 추가하지 않는다.
  • ChannelStatePort·lease·fence·secret version 비교·영속 disabled를 삭제한다. 같은 인터페이스의 메모리 구현이나 새 상태 관리 모듈로 대체하지 않는다.
  • 검증된 ERROR 로그 → 안전한 고정 메타데이터 → Discord 전송 → 응답별 ACK/재시도/격리. 유효한 성공 응답과 message ID 확인 후 204를 반환한다.
  • 네트워크·timeout·5xx·손상된 성공 응답·기한 만료·429는 503으로 Pub/Sub 재시도. 요청 안에서 재시도 루프나 긴 sleep은 하지 않는다.
  • 429의 검증된 대기 시간만 DiscordClient 내부 nextAllowedAt 숫자로 기억한다. 대기 중 fetch 없이 503, 만료 후 전송. 기존 60초 fallback/24시간 상한 유지. 재시작 시 사라지고 다른 실행체와 공유되지 않는다.
  • 영구 4xx는 격리 publish 성공 후 ACK, publish 실패는 503. 401/403/404는 discord_webhook_rejected로 구분하고 안전한 error 로그를 남기며 채널을 영속 차단하지 않는다. 나머지는 discord_payload_rejected다. webhook 수정/중단은 기존 배포 설정과 운영 절차를 사용한다.
  • 기존 concurrency=1/minInstances=0/maxInstances=3 유지. 실행체 간 요청 제한 공유·중복 방지·재시작 후 상태 복원은 보장하지 않는다. 응답 유실·재전달로 알림이 중복될 수 있다.
  • 배포용 Secret Manager 숫자 버전 pin은 webhook 비밀 주입 책임이므로 유지한다. runtime DISCORD_SECRET_VERSION과 상태 비교만 제거한다. 실제 배포·리소스 삭제·웹훅 호출은 하지 않는다.

보존할 동작과 의도한 계약 변화

  • ERROR/50 및 alertEligible=true, source project/service/log/resource 검증, 대표 오류 소유권, warn/error 구분을 유지한다. consumer도 기존 producer 식별자를 검증한다.
  • 기존 v1 code/appCode/event를 소비하고 공식 registry의 고정 문구만 사용한다. raw message/stack/cause/request/SQL/실제 path/query/webhook URL은 Discord나 quarantine에 추가하지 않는다.
  • 기존 code alias와 HTTP 응답을 보존한다. 미등록 코드가 있어도 원문 문구를 fallback으로 사용하지 않으며 오류 자체의 전달을 누락시키지 않는다.
  • 새 routeTemplate은 producer의 router metadata만을 뜻한다. 문법 검사·길이 제한은 보조 guard이며 raw URL이 template임을 증명해 주지는 않는다. legacy route 필드는 화면에서 생략한다.
  • timestamp 손상/누락은 invalid_log_entry 격리, 현재 시각 위조 없음. revision은 제거. statusCode는 비HTTP 이벤트 때문에 optional 유지.
  • source 기대 환경은 explicit 설정과 sink·consumer·quarantine·표시 전체에 적용한다. development/production은 구독과 실제 webhook 설정을 분리한다. 공유 상태는 저장하지 않는다. NODE_ENV에서 감시 대상을 추측하지 않는다.
  • 공유 상태 없이 Discord 성공 확인 후 ACK한다. 실패 non-ACK·격리 순서는 유지하고 429 대기는 프로세스 메모리에만 둔다. DB 의존은 추가하지 않는다.
  • 원격 GCP ID와 운영 상태를 자동 재생성·삭제하지 않는다. 이번에는 실제 cloud apply/deploy/webhook 호출을 수행하지 않는다.

설계 의사결정 기록

진행 상태: 완료. 기존 저장소 없는 전달 결정은 유지한다. AR1–AR6은 코드·설치 SDK의 공개 API·기존 producer 테스트를 재확인했다. 이번 수정안은 “ㄱㄱ”로 승인됐다. 기술적으로 확인할 수 있는 사항을 사용자 선택 질문으로 넘기지 않았다.

shared registry vs producer가 메시지 문자열을 wire에 추가
shared registry 권고. 빌드 노드가 하나 늘지만 수신기가 공식 고정 문구를 자체 검증할 수 있고 기존 v1 code/event를 유지한다. 새로운 payload.message 신뢰 경계를 만들지 않는다.
단일 CJS vs dual build
ESM consumer용 shared는 단일 CJS 빌드를 유지한다. API는 기존 source alias로 같은 원본을 사용한다. 두 consumer가 반드시 같은 artifact를 사용해야 한다는 이전 결정을 수정하여 API 선행 빌드·watch 연결을 제거한다.
공유 상태 저장 여부
사용자가 아직 필요 없다고 결정했다. Firestore 신규 도입과 PostgreSQL 테이블 안을 모두 철회한다. 메모리 대기와 Pub/Sub 재시도로 범위를 축소하며 분산 전송 제어·중복 방지는 보장하지 않는다.
helper 분리
실제로 반복되는 불변식 검증은 유지하되 삭제하는 상태 모델만을 위한 검증은 함께 제거한다. 획일적으로 inline하거나 공용 util로 승격하지 않는다.
현 frontier
사용자 소유의 미해결 선택 없음. 기존 저장소 없는 전달·15초 배포 정책 안에서 가장 작은 수정안을 선택했다. Topic 전역 옵션·Promise.race는 요청별 RPC 제한을 충족하지 못해 제외했다. 진행 중 publish 취소와 exactly-once는 제공하지 않는다.
