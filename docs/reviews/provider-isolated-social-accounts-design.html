목적 (purpose)
서로 다른 소셜 provider의 계정을 독립 사용자 계정으로 생성·로그인한다.
사용자 (audience)
Apple·Kakao·Google 소셜 로그인 사용자와 API·DB 운영 담당자.
문제 (problem)
현재 이메일 유니크 제약과 이메일 중복 차단 때문에 같은 이메일의 다른 provider 사용자가 가입하지 못한다.
핵심 흐름 (core-flow)
provider 토큰 검증 → (provider, providerUserId) 조회 → 기존 identity 로그인 또는 새 users·social_account 생성 → 세션 발급.

provider별 독립 소셜 계정

같은 이메일이라도 provider가 다르면 서로 다른 사용자로 취급한다. 계정의 유일 식별자는 (provider, providerUserId)이며, 이메일은 연락·프로필 속성일 뿐 계정 병합 키가 아니다.

비목표

  • 이메일 기반 자동 계정 연결·병합
  • provider 간 로그인 세션 공유
  • 기존 사용자 데이터 병합·이관
  • 이메일 중복을 이유로 한 U012 차단

경계와 상태 전이

  1. 외부 provider를 검증하고 요청 provider와 identity provider가 일치하는지 확인한다.
  2. social_account(provider, provider_user_id)로 조회한다.
  3. 조회되면 그 user_id에 세션을 발급한다.
  4. 조회되지 않으면 이메일 중복 여부와 무관하게 users와 social_account를 하나의 transaction으로 생성한다.
  5. 동시 생성 충돌은 같은 exact identity 재조회로 복구하고, 이메일 충돌은 더 이상 분기하지 않는다.

동일 identity 동시 로그인과 가입 상태

PENDING은 “계정 생성 중” 플래그가 아니라 사용자 행과 소셜 identity는 이미 생성됐지만 가입 정보가 아직 완료되지 않은 상태다. 단, A와 B의 provider가 다르면 같은 이메일이어도 exact identity가 다르므로 각각 사용자 1명씩, 총 2명의 PENDING 계정이 생긴다. 아래 동시성 복구는 같은 provider·같은 subject의 중복 요청에만 적용된다.

동시 요청의 저장·응답 상태
요청 DB 결과 응답
A: 생성 transaction 선점 users 1건 + social_account 1건 + A 세션 1건 NEW, PENDING 가입 화면
B: unique 충돌 후 exact identity 재조회 새 사용자는 만들지 않음 + B 세션 1건 추가 RESUME, 같은 userId의 PENDING 가입 화면
다른 provider, 같은 이메일 이메일과 무관하게 별도 users·social_account·세션 생성 각 요청이 NEW, 각자 다른 userId의 PENDING 가입 화면

같은 exact identity의 경우 서버에는 세션 2개가 생길 수 있지만 계정 생성 상태가 2개 생기는 것은 아니다. 이는 기기별 동시 로그인을 허용하는 현재 세션 모델과 일치한다. 동일 브라우저에서는 프런트가 auth context별 join 요청을 single-flight로 직렬화해 중복 제출을 억제한다. 예외적으로 중복 요청이 서버에 도달하면 stale 요청의 T005를 같은 joinAttemptId와 authGeneration의 결과 확인으로 흡수한다. 서로 다른 기기라면 두 세션 모두 같은 사용자의 가입 화면을 가리킨다. 반대로 다른 provider의 같은 이메일은 의도적으로 서로 다른 사용자·세션·가입 화면이다.

가입 완료 race: 두 세션이 동시에 POST /api/users/join을 제출하면 현재 role = 'PENDING' 조건부 update를 먼저 통과한 한 요청만 USER가 된다. 서로 다른 세션의 후속 요청은 기존 가입 결과와 자기 세션의 최신 USER token을 받아 멱등 복구한다. 같은 currentSessionId의 후속 요청은 앞선 요청이 세션을 이미 교체했으므로 도착 시점에 따라 일반적인 stale 세션 오류인 403/T005로 종료될 수 있다. 프런트는 auth context별 joinAttemptId를 single-flight로 직렬화하고, 같은 시도의 결과와 최신 공용 token pair만 확인한다.

가입 전 token의 의미

PENDING 사용자에게도 access/refresh token을 발급하는 것은 provider 인증을 통과한 사용자가 가입 완료 API를 호출할 수 있게 하기 위한 것이다. 이 token은 가입 진행용 인증 세션이며, 가입 완료 사용자와 같은 권한을 의미하지 않는다.

가입 전·후 token 권한 경계
상태 허용 흐름 차단 흐름
PENDING POST /api/users/join — AccessTokenGuard만 적용 프로필·게시글·모각 등 RegisteredUserGuard 경로
USER 가입 완료 사용자용 전체 인증 경로 유효하지 않은 세션·token

가입 전 token 자체를 발급하지 않으려면 별도의 onboarding token과 전용 guard/계약이 필요하다. 현재 API는 /api/users/join에 access token을 사용하므로, 이번 범위에서는 PENDING token을 유지하고 권한 경계를 테스트한다.

동시 가입 개선안 (제안)

  1. PENDING token 유지: provider 인증 직후 가입 API를 호출하는 데 필요하므로 access/refresh token은 계속 발급한다. 등록 완료 권한은 여전히 RegisteredUserGuard로 제한한다.
  2. 기존 승인안 — 재검토 대상: access token의 role이 PENDING이면 인증 시 현재 user row를 확인한다. DB role이 이미 USER라면 현재 요청 principal을 USER로 승격하고, refresh에서는 최신 role이 담긴 새 access token을 발급한다. DB role이 여전히 PENDING이면 그대로 둔다.
  3. 가입 완료 원자성: UPDATE users ... WHERE role = 'PENDING'에서 먼저 성공한 요청만 닉네임·직업·주소·동의를 확정한다. 뒤 요청은 기존 USER 상태를 재확인해 기존 가입 결과와 서로 다른 세션이면 새 USER 세션을 반환하며, generic persistence 오류를 내지 않는다. 동일 currentSessionId의 후속 요청은 세션이 이미 비활성화되었으므로 LOGOUT_TOKEN(HTTP 403/T005)으로 종료할 수 있다. 어느 경우에도 뒤 요청의 입력으로 기존 가입 정보를 덮어쓰지 않는다.
  4. 세션 모델: A/B 로그인 세션을 하나로 합치거나 강제 로그아웃하지 않는다. 두 세션은 같은 userId를 가리킬 수 있고, role 최신화·가입 완료 결과로 일관된 상태를 얻는다.

대안으로 보류: 가입 전 token을 별도 onboarding token으로 분리하거나, 가입 완료 시 다른 세션을 모두 폐기하는 방식은 API 계약·다중 기기 UX를 크게 바꾸므로 이번 범위에서 제외한다.

role 최신화 재검토 (승인된 설계)

결정: registrationContinuation 같은 내부 표식을 제거하고, access token의 PENDING role은 refresh 전까지 그대로 유지한다. 이 표식은 JWT·DB에 저장되지는 않지만, “일반 USER token”과 “가입 완료 뒤 남은 PENDING token”을 구분하기 위한 요청 전용 예외 상태라 표준 도메인 모델로 보기 어렵다.

결정
가입 완료의 정확성과 세션 교체에는 표식이 필요하지 않다. 가입 응답의 새 token을 저장하고, 다른 탭의 오래된 token은 공통 HTTP client가 refresh 1회 후 원 요청을 1회만 재시도한다.
근거·가정
수동으로 각 화면이 retry하지 않고 인증 계층에서 single-flight refresh를 수행하며, 현재 refresh API가 DB의 최신 role로 access token을 발급한다는 전제다.
가장 강한 반증 또는 완화
일반 403 FORBIDDEN을 무조건 refresh 대상으로 삼으면 권한 부족 요청을 반복할 수 있다. 가입 완료 직후 proactive refresh를 우선하고, stale token을 구분해야 한다면 명시적인 오류 신호와 1회 재시도·무한 루프 방지 규칙을 프런트 공통 계층에 둔다.
미룬 범위·재검토 조건
공통 token interceptor를 제공할 수 없는 클라이언트가 있거나 refresh 없이 즉시 USER 전용 API가 반드시 동작해야 한다면, effectiveRole을 명시하는 대안을 별도 승인한다. 화면별 retry 구현은 채택하지 않는다.
기존 승인안과 승인된 변경의 경계
경계 기존 승인안 재검토 제안
access 인증 PENDING token이면 DB role을 읽어 principal을 USER로 승격 서명된 token role을 유지하고 세션 활성 여부만 확인
가입 API 승격된 principal의 registrationContinuation으로 재발급 허용 persisted USER이면서 current.role === 'PENDING'인 경우에만 재발급
refresh DB의 현재 role을 읽어 USER token을 발급
USER 전용 API DB role을 확인한 해당 요청은 즉시 통과 가능 오래된 PENDING token은 refresh 전까지 RegisteredUserGuard에서 차단
  1. authenticateAccessToken은 JWT 검증과 활성 세션 확인만 수행하고 principal의 role을 바꾸지 않는다. 따라서 일반 요청마다 DB role을 재조회하지 않는다.
  2. POST /api/users/join은 이미 persisted USER이면 current.role === 'PENDING'일 때만 기존 가입 결과와 최신 USER 세션을 반환한다. 일반 USER token은 USER_ALREADY_EXISTS로 거부한다.
  3. 클라이언트가 가입 완료 뒤 USER 전용 API를 호출하려면 refresh token으로 최신 access token을 먼저 교체한다. 이는 정상적인 stale PENDING 경로이며, 별도 onboarding token이나 provider 재조회는 추가하지 않는다. 단, 동일 currentSessionId 중복 /join에서 T005가 오면 stale 요청으로 간주하되, 같은 authGeneration의 진행 중 가입 결과와 그 결과가 저장한 최신 공용 pair만 확인한다. 다른 계정의 pair는 채택하지 않는다. pair가 없으면 오래된 token으로 refresh나 provider 자동 로그인을 시도하지 않고 로그인 화면으로 이동한다.
이 결론이 실패한다면: 클라이언트가 가입 완료 직후 오래된 access token만으로 USER 전용 API가 계속 동작한다고 가정할 수 있다. 이 경우 refresh를 명시적으로 수행하게 하거나, 즉시 승격이 제품 요구사항인지 별도로 승인해야 한다.
승인된 서버 계약: RegisteredUserGuard는 현재 request.user.role만 보고 FORBIDDEN을 반환한다. 표식 제거 후 role === 'PENDING'이면 TOKEN_REFRESH_REQUIRED 오류 코드(HTTP 403 / T006)를 반환하도록 바꾸면, 일반 USER 권한 부족의 FORBIDDEN과 refresh 대상 요청을 프런트가 구분할 수 있다. 이 분기는 “stale인지 아직 미가입인지”를 토큰만으로 판정하는 것은 아니므로, 프런트는 refresh 1회와 원 요청 1회만 수행하고 같은 코드가 반복되면 가입 화면으로 보낸다.

미룬 범위: 즉시 USER 권한이 꼭 필요하다면 tokenRole과 effectiveRole을 명시적으로 분리하는 대안을 재검토한다. 지금은 표식과 매 요청 DB 조회를 제거하는 최소 변경만 제안한다.

변경 경계와 마이그레이션

  • users_email_unique 제약을 제거하는 Drizzle migration을 추가한다.
  • users.email 컬럼 자체와 social_account.email 저장은 유지한다.
  • AuthService.login의 findUserByEmail 사전 차단과 DuplicateEmailException → U012 분기를 제거한다.
  • (provider, providerUserId) unique와 (userId, provider) unique는 유지한다.
  • 이메일을 사용자 검색·계정 식별자로 쓰는 다른 인증 경로가 있는지 검색하고, 발견 시 이 설계의 범위에 포함해 함께 수정하거나 명시적으로 잔여 위험으로 기록한다.

롤백은 새 migration을 역순으로 실행할 수 있지만, 그 시점에 중복 이메일 행이 생성되어 있으면 제약 복원이 실패할 수 있다. 따라서 롤백 전 중복 이메일 점검이 필요하다.

검증 계획

  • AuthService 단위: 같은 이메일·다른 provider → 새 계정·NEW·서로 다른 userId.
  • AuthService 단위: 같은 provider·같은 subject → 기존 계정 RESUME 또는 REGISTERED.
  • AuthService 단위: social identity unique 충돌 후 exact identity를 재조회해 경쟁 요청의 사용자를 정상 재개하고, identity를 찾지 못한 persistence 오류는 그대로 전파하는지 확인한다.
  • 동시 로그인 integration: 같은 exact identity 두 요청이 users/social_account 1건, auth_sessions 2건, 같은 userId의 NEW/RESUME 결과가 되는지 확인한다.
  • 가입 완료 race: 두 PENDING 세션의 join 동시 요청에서 한 번만 USER 전이가 일어나고 두 번째 요청은 서로 다른 세션이면 새 USER 세션을 받는다. 같은 세션의 stale 요청은 Guard를 통과한 시점에 따라 성공 경합 후 403/T005가 될 수 있으며, 첫 응답의 replacement session이 남는지 확인한다.
  • repository/integration: users에 같은 email 두 행과 각각의 social identity가 저장된다.
  • schema/migration: 실제 DB에서 users_email_unique 제거 후 중복 이메일 insert가 성공하고 social identity unique는 여전히 동작한다.
  • 전체 검색·회귀: 이메일 기반 인증·세션·탈퇴·사용자 조회가 계정 식별자로 오인하지 않는지 확인한다.

기존 승인안은 provider별 독립 계정, PENDING token-role 유지, T006 분기까지 확정했다. 이번 리뷰에서 발견한 프런트 릴리스 의존성과 동일 세션 중복 가입 처리는 동작·계약을 바꾸므로 별도 결정했다. migration 적용 자체는 이번 결정의 대상이 아니다.

진행 상태
G1-A·G2-C 결정됨 · 구현 재승인됨
결정 트리
G1-A로 T006 서버 계약과 프런트 interceptor의 별도 릴리스 gate를 유지한다. 기존 G2-A의 U017 보장·자동 login 복구는 AUTH-005 검토에서 폐기하고, G2-C로 stale /join의 T005 허용과 프런트 single-flight·최신 pair 확인을 사용한다. 이 변경에 대한 구현 재승인은 2026-09-02 대화에서 확인되었다.
현재 frontier
G1-A·G2-C가 확정되었고 구현 재승인을 받았다. 설계-control에서 확인한 경계와 실패 시 후속 동작을 구현·검증 기록에 반영한다. 기존 U017 관련 기록은 대체됨으로 표시한다.
확정된 전제
일반 403/T004는 refresh 대상이 아니며, T006만 single-flight refresh 1회와 원 요청 1회를 허용한다. migration 미적용 상태로 새 provider 동작을 배포하지 않는다.

ID 결정 선택지 권고·트레이드오프
G1 T006 프런트 계약의 이번 작업 범위 A. 서버 T006 계약·백엔드 contract test·handoff를 고정하고 프런트 interceptor는 별도 릴리스 gate로 둔다. B. 서버가 매 요청 DB role 조회/자동 승격해 프런트 refresh 계약을 없앤다. A 선택: 현재 승인안과 일치하고 매 요청 DB 부하·권한 경계 변화를 피한다. 프런트 interceptor 없이는 stale 세션 UX가 완성되지 않으므로 별도 릴리스 gate로 추적한다.
G2 동일 currentSessionId의 중복 /join A. stale 요청을 명시적 U017으로 매핑하고 provider login으로 복구한다. B. idempotency key와 durable response replay를 도입한다. C. 서버의 세션 상태를 추가하지 않고 stale 요청의 T005를 허용하며, 프런트에서 join을 single-flight로 직렬화하고 같은 joinAttemptId의 최신 pair만 확인한다. C 선택: 서버 tombstone·멱등 응답 저장·추가 migration 없이 현재 세션 모델을 유지한다. 프런트는 같은 authGeneration의 진행 중 join 결과와 그 결과가 저장한 공용 token pair만 확인하고, pair가 없을 때만 로그인 화면으로 보낸다. stale token으로 /refresh를 반복하거나 T005에서 provider 자동 로그인을 수행하지 않는다. A는 logout과 replacement를 구분할 서버 상태가 필요하고, B는 token 결과 보관·암호화· 만료 정책이 추가되어 현재 범위보다 크다.
잔여 위험: 서버는 동일 세션 stale 요청에 T005를 반환할 수 있으므로 프런트가 이를 즉시 전역 로그아웃으로 처리하면 첫 요청의 최신 pair를 지울 수 있다. 프런트는 같은 authGeneration·joinAttemptId의 결과만 복구하고, generation이 바뀐 로그아웃·계정 전환 뒤에는 진행 중 응답을 폐기해야 한다. 이 single-flight·조건부 삭제를 프런트 릴리스 gate로 검증해야 한다. G1을 정하지 않으면 T006 배포 뒤 stale PENDING 세션이 로그인 화면으로 이탈하거나 무한 재시도할 수 있다.

설계 이해 점검

상태: 점검 제공됨. G1-A·G2-C 결정에 맞춰 동일 세션 stale 처리와 T006 릴리스 경계를 포함하도록 질문을 갱신했다. HTML의 로컬 선택 결과는 Codex에 자동 전달되지 않으며, 설계 승인은 대화에서 별도로 확인했다.
