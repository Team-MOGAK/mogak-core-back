목표와 비목표

그날 회차가 없는 조각에 POST /api/jogaks/:jogakId/executions/:scheduledDate/start를 보내면 일정은 그대로 두고 그날 실행 기록 하나만 만든다. 이 실행은 그날 GET /api/jogaks?date=와 GET /api/mogaks/:mogakId/jogaks?date=에 나타나고, success/fail과 게시글 작성을 받는다.

대상: 그날 요일이 아닌 루틴, 다른 날짜의 한 번 조각, 종료일이 지난 루틴, 아직 시작일 전인 조각. 그날 이미 회차가 있으면 지금 동작을 그대로 유지한다.

비목표: 일정(요일·시작일·종료일) 변경, “오늘 할 일에서 빼기”(B-5), 진척 집계(B-1), 지난 날 소급 체크 범위 정책(B-3), 실행 테이블 스키마 변경은 포함하지 않는다.

구현 지점

  1. Repository — MogakRepositoryPort.listOwnedExecutionRows({ userId, startDate, endDate, mogakId? }) 추가. jogak_executions → jogaks → mogaks → modarats(소유자) → mogak_categories 조인으로 실행과 표시 필드(mogakTitle, 카테고리, color, 제목 스냅샷)를 한 번에 가져온다. 기존 (jogak_id, scheduled_date) 유일 인덱스로 날짜 범위 조회가 가능하다.
  2. projectOccurrences — includeAdHoc 옵션(일별 목록 두 경로만 true). 일정 회차를 만든 뒤, 위 조회 결과 중 이미 만든 jogakId:date 키에 없는 실행을 AD_HOC 항목으로 추가하고 같은 정렬 규칙을 적용한다. 달성 수 조회 대상에 AD_HOC 조각 ID를 포함한다.
  3. commandExecution — 발생 일정이 없을 때 desiredStatus === 'IN_PROGRESS'이고 허용 범위 안이면 기존 INSERT/전이 경로로 진행, 아니면 그날 실행이 있을 때만 전이. 응답의 isRoutine=false, origin='AD_HOC'.
  4. resolveOwnedOccurrence — 일정 발생이 없으면 findExecution으로 한 번 더 확인. 게시글 서비스 코드는 바꾸지 않는다.
  5. 응답 타입 — OccurrenceResult와 실행 응답에 origin: 'SCHEDULE' | 'AD_HOC'.

검증 계획

  1. 단위(jogaks.service.spec.ts): 요일 아닌 루틴·다른 날 ONCE·종료된 루틴·시작 전 조각에 start → 201, origin=AD_HOC, 일정 저장 호출 없음.
  2. 단위: 회차 없는 날 실행 없이 success/fail → J017. start 뒤 success→fail→success 모두 성공, 같은 상태 반복은 200.
  3. 단위: 허용 범위 밖 start → J017. 그날 회차가 있는 조각은 응답·상태 코드가 지금과 같고 origin=SCHEDULE.
  4. 통합(mogaks.integration.spec.ts): AD_HOC start 뒤 GET /api/jogaks?date=와 모각 일별 목록에 항목이 정렬 규칙대로 나오고, 다음 날 목록에는 나오지 않으며, /jogaks/daily·/routines에는 나오지 않는다. 일정·요일 행 수와 ID가 그대로다.
  5. 통합: 같은 조각·날짜로 동시 start 두 번 → 실행 행 1개.
  6. 통합: AD_HOC 실행 날짜로 게시글 작성·조회 성공, 실행 없는 날은 J017.
  7. 관련 Jest·typecheck·lint.

결정된 사항 (2026-10-28 승인, 권장안 채택)

  1. 일정 편집으로 일정 밖에 남은 기존 실행 — 결정: 보이게 둔다. 안 A에서는 이런 실행도 그날 목록에 AD_HOC로 다시 나타난다. 지금은 기록이 있어도 숨겨져 있다. 권장: 보이게 둔다. 일정 편집 설계가 “실행은 그날 실제로 남긴 기록”이라고 정했으므로 숨기는 쪽이 오히려 기록 유실처럼 보인다. 배포 전 운영 DB에서 해당 건수를 한 번 조회해 확인한다.
  2. start로 이번 한 번을 만들 수 있는 날짜 범위 — 결정: KST 오늘 ~ 오늘+6일. 권장: KST 오늘부터 오늘+6일. 앱 시트가 “그날”을 고르는 구조라 미래 날짜는 필요하지만, 과거에 기록을 새로 만드는 것은 B-3(소급 체크) 정책과 함께 정해야 한다. 오늘만 허용하는 더 좁은 안도 가능하다.
