승인 상태: 사용자가 A 방향 선택과 상세 모델 공유 이해를 완료하고 구현을 승인했다. 일반 쓰기는 관련 계정의 존속을 공유 잠금으로 보장하고, 실제 충돌하는 자원은 별도로 잠근다. 탈퇴끼리만 DB 전역의 transaction-scoped mutex로 직렬화한다. 메모리 mutex나 연결 수 1에 의존하지 않는다.

L1모든 참여 사용자 ID를 중복 제거·오름차순 정렬하고, 각 사용자의 최종 잠금 모드를 미리 정한다. 한 ID씩 순서대로 잠가 planner/SQL 입력 순서에 기대지 않는다.서로 반대 방향의 관계 요청도 같은 순서로 기다린다. KEY SHARE를 잡은 뒤 UPDATE로 올리는 교착을 피한다.
L2자원 잠금 또는 DML 이후 새 사용자 잠금을 추가하지 않는다. 참여자 재조회에서 새 ID가 필요하면 전체 transaction을 종료한다. 계층 삭제로 참여자가 줄어들면 기존 잠금을 유지하며 게시글과 오류 계약을 재확인한다.서비스 사전조회 결과를 신뢰하거나 잠금을 늦게 추가하면 순서 규약이 깨진다. post.authorId, post.jogakExecutionId, execution.jogakId, jogak.mogakId, mogak.modaratId, modarat.userId는 재부모화하지 않는다는 전제를 검사한다.
L3자원 순서는 modarat→mogak→jogak→schedule→execution(daily_jogak)→post→말단이다. 한 계층의 여러 행은 PK 오름차순이다. 필요 없는 계층은 건너뛸 수 있지만 앞 계층으로 돌아갈 수 없다.post는 hierarchy 삭제 뒤에도 보존되므로 삭제된 execution을 잠금의 필수 전제로 만들지 않는다.
L4댓글 참조는 post KEY SHARE, 좋아요 toggle은 post NO KEY UPDATE, 게시글 삭제는 처음부터 post UPDATE 후 댓글·좋아요·이미지를 지운다. 용량/일정/실행 변경은 기존 계층의 UPDATE 잠금으로 직렬화한다.일반 댓글끼리는 병렬 유지하면서 부모 삭제와의 FK 경쟁을 막는다. INSERT의 FK나 CTE 나열 순서에 잠금 획득을 맡기지 않는다.
L5탈퇴는 사용자 잠금보다 먼저 동일한 advisory transaction mutex를 얻는다. 일반 쓰기는 이 mutex를 획득하지 않는다. session-scoped advisory lock과 shared→exclusive 승격은 금지한다.상호 댓글·좋아요·팔로우 행을 지우는 두 탈퇴의 경쟁을 분리한다. commit/rollback과 함께 해제되어 pool 연결에 남지 않아야 한다.
L6존재·소유·일정 유효성·용량·중복은 같은 transaction, 같은 연결, 잠금 이후 재검사한다. helper는 tx만 받고 root db를 사용하지 않는다.사전 SELECT와 실제 INSERT 사이의 삭제/수정을 처리한다. 결과만 재조회하는 것으로는 부족하다.
L7프로필/가입 등 users 자체를 UPDATE하는 연산은 시작부터 UPDATE 모드다. 순수 참조는 KEY SHARE다. 코드에 연산별 모드를 명시한다.특히 unique nickname 수정은 강한 행 잠금이 필요할 수 있다. 두 공유 보유자가 동시에 승격하는 교착을 설계에서 제외한다.
L8잠금 안에서 외부 API·스토리지·사용자 응답·임의 지연을 기다리지 않는다. 모든 내부 병렬 SQL은 순서 보장 필요성을 먼저 검토한다.긴 transaction이 탈퇴와 요청 처리를 붙잡지 않게 한다. 외부 효과의 rollback은 이 DB 규약이 보장하지 않는다.

위 규약의 근거는 PostgreSQL 17 행 잠금·교착·advisory lock 문서다. 공유 참조 잠금과 강한 삭제 잠금의 충돌, 필요한 강한 모드의 선취득, transaction 종료 시 해제 원칙을 적용했다. 여기서 제안하는 계정 단위 프로토콜의 충분성은 아래 경로 행렬과 PostgreSQL 통합 테스트로 별도 검증한다.

잠금 규약의 충분성을 어떻게 검토할 것인가

  1. 쓰기×탈퇴: 삭제 대상에 연결된 모든 사용자 관련 쓰기는 해당 사용자 KEY SHARE를 먼저 보유해야 하므로, 해당 users UPDATE를 보유한 탈퇴와 말단 변경이 동시에 진행하지 않는다.
  2. 쓰기×쓰기: 사용자 잠금은 정렬되고, 자원 잠금은 계층 순서대로다. 사용자 자체 수정은 UPDATE를 처음부터 얻어 승격 경쟁을 만들지 않는다.
  3. 탈퇴×탈퇴: 공유 관계 행을 삭제할 수 있는 두 탈퇴는 공통 mutex로 분리한다. 한 탈퇴가 자신의 사용자 잠금을 가진 상태로 다른 탈퇴의 mutex를 기다려서는 안 된다.
  4. 글 삭제×댓글/좋아요: 사용자 참조 잠금이 서로 호환되어도 post UPDATE와 KEY SHARE가 충돌하므로 자식 insert/delete와 부모 삭제의 순서가 고정된다.
  5. 발견한 참여자 집합이 삭제 대상의 소유자를 빠뜨리거나 하나의 writer라도 규약을 우회하면 위 논증은 성립하지 않는다. unique-index 대기·다중 행 처리·예외 helper는 목록과 테스트에서 추가 검토한다.

증명 범위: 현재 확인한 애플리케이션 writer, 고정된 부모·작성자·execution 식별자 관계, READ COMMITTED를 전제로 한 설계 논증이다. 전체 DB에서 모든 교착이 불가능하다고 주장하지 않는다. 격리수준의 재조회 동작과 데이터 변경 CTE 실행 규칙도 적용 전제다. CTE의 텍스트 순서만으로 잠금 순서를 증명하지 않는다.

읽기 전용 설계 감사의 직접 근거
  • AuthRepository: deleteUser/lockWithdrawalTree, 세션 생성·회전.
  • PostRepository: createForOccurrence, deleteOwnedPost, toggleLike, comment writes.
  • ConsentRepository: 다중 동의 DML 정렬.
  • 게시글 통합 테스트: 기존 교차 소유 회고의 탈퇴 삭제 계약 및 raw insert-only 좋아요 검사.
  • 모각 통합 테스트: 경합 결과와 generic lock wait 단언.

공통 protocol과 레거시 교차 소유 반례는 별도 읽기 전용 전략 감사로 교차 검토했다. 새 구현의 DB 테스트가 실행된 것은 아니다.

입력과 자원 상한 계약

  1. isValidDateRange에 해당하는 순수 predicate 하나가 날짜 형식·실제 날짜·순서·양끝 포함 일수를 확인한다. 잘못된 외부 입력에서는 false를 반환하고, 날짜 변환은 형식 확인 뒤에만 한다.
  2. HTTP schema는 predicate 실패를 기존 INVALID_PARAMETER → 400/Z005로 바꾼다. 직접 core 호출은 기존 INVALID_TARGET_DATE → 400/J017 정책을 유지한다. 성공 응답과 필드 이름은 바꾸지 않는다.
  3. 페이지 번호 0 이상, size 1~100, 안전한 offset 곱셈을 core의 한 정책으로 공유한다. 전송 계층은 coercion/default만 담당한다. 현재 두 offset predicate와 service의 중복 날짜 상한 계산은 같은 정책으로 수렴시킨다.
  4. 날짜 범위는 양끝 포함 1~366일이다. today는 한 작업 안에서 한 번 정해 저장소의 용량 재검사와 공유한다. 배열 전개와 DB 호출 전에 검증을 끝낸다.

운영 전제와 잔여 위험

  • 탈퇴 처리량은 DB별 한 번에 한 건으로 제한된다. 대규모 계정 purge가 뒤의 탈퇴를 오래 기다리게 할 수 있다. 비동기 탈퇴·soft delete로 바꾸는 것은 별도 데이터/제품 설계다.
  • 인기 글의 toggle은 post NO KEY UPDATE로 직렬화된다. 일반 댓글 참조와의 병렬성은 유지하되 실제 지연은 부하 검증이 필요하다. 개선 전부터 보장하지 않던 toggle 순차 의미를 수용 기준에 추가한다.
  • 새 프로토콜을 쓰는 버전과 이전 writer 버전이 동시에 실행되면 보장되지 않는다. 배포 시 기존 쓰기 요청을 drain하고 writer 버전을 맞춰야 한다. 롤백도 같은 경계가 필요하다. 이 문서는 배포 실행 승인이 아니다.
  • 현재 Pool 생성 코드에 별도 lock_timeout/statement_timeout 설정은 없다. 서버 설정은 아직 확인하지 않았다. 임의 숫자를 운영 기본값으로 추가하지 않는다. 운영 이행 전 DB 설정·lock wait·transaction duration·pool 대기·탈퇴 크기를 측정하고 SLO에 맞춘 한도를 정해야 한다.
  • transaction 잠금의 namespace/key를 공통 상수로 고정하고 다른 advisory 사용과 충돌 여부를 검사한다. 여러 인스턴스가 같은 DB와 키를 공유해야 한다. crash/rollback/connection 반환 뒤 해제 테스트가 필요하다.
  • metadata/직접 SQL/배치/스토리지 외부 효과는 목록에 포함 여부를 명시한다. 현재 disabled storage의 상태는 보장 전제이며, 파일 업로드를 활성화할 때 DB rollback만으로 파일 정리가 된다고 가정하지 않는다.

fixture/blocker/작업 A/작업 B/관찰용 연결을 분리한다. Promise를 즉시 settle handler에 연결하고, pg_blocking_pids와 backend PID로 의도한 대기를 확인한 뒤 barrier를 해제한다. 임의 sleep이나 wait_event_type = 'Lock' 하나로 순서를 증명하지 않는다. timeout은 테스트 실패이며 성공의 대체 결과가 아니다.

Promise.allSettled 자체는 사용 가능하지만 각 결과는 연산별 허용 집합과 정확히 일치해야 한다. 40P01, 23503, 55P03, 알 수 없는 SQL/runtime 오류를 묶어서 persistence 오류로 허용하지 않는다. finally에서 작업을 종료·drain하고 rollback과 연결 반환을 완료한 뒤 cleanup한다.

  5. 요약 feed에서 댓글 projection을 호출하지 않았는지 repository mock과 query-level 검증으로 확인한다.
