동일 소셜 계정 로그인 fallback

범위는 POST /api/auth/:provider/login의 계정 생성 경쟁 복구와, 같은 identity에 연결됐지만 role이 null/비정상인 레거시·불완전 데이터의 가입 재개 복구다. 이메일이 같은 다른 소셜 계정을 자동 연결하거나 가입 완료 상태를 재설정하지 않는다.

비목표

  • provider 재검증 생략
  • 이메일 기반 계정 병합
  • PENDING 사용자 삭제·재생성
  • DB 고유 제약 제거 또는 무제한 재시도

상태·경계 모델

  1. 외부 provider를 검증하고 요청 provider와 identity provider 일치를 확인한다.
  2. (provider, providerUserId)로 기존 사용자를 조회한다.
  3. 기존 사용자 role이 PENDING/USER면 그대로 사용한다. null/비정상값이면 가입 완료 판단에 쓰는 프로필 증거를 기준으로 상태를 판별하고, 해당 identity에 한정해 role을 조건부 정규화한다.
  4. 정규화된 사용자에 새 세션을 발급한다.
  5. 기존 사용자가 없으면 새 사용자와 social account를 transaction으로 생성한다.
  6. 생성 중 고유성 충돌이 나면 동일 identity를 한 번 재조회하고 같은 정규화·세션 발급 경로를 사용한다.

구현 경계와 복구

AuthService.login에서 DuplicateEmailException과 DuplicateSocialAccountException을 같은 exact-identity recovery helper로 보낸다. helper는 한 번만 findUserBySocialIdentity를 호출한다. 기존 identity 사용자는 role resolver를 통과한 뒤에만 세션을 발급한다.

role이 null인 경우의 완료 판단은 가입 완료에 필요한 모든 값과 유효성을 기준으로 한다. 즉 (1) trim 후 2~10자인 nickname, (2) jobId, (3) addressId, (4) 현재 활성·필수인 모든 consent item에 대한 agreed = true user consent가 모두 있어야 USER로 판별한다. 하나라도 없거나 nickname이 범위를 벗어나면 PENDING으로 판별해 가입 화면에서 누락·잘못된 정보를 보완하게 한다. null→PENDING 또는 null→USER 갱신은 WHERE user_id = ? AND role IS NULL 같은 compare-and-set으로 제한한다.

수정 대상: src/auth/application/service/auth.service.ts, src/auth/application/port/authPersistence.port.ts, src/auth/infrastructure/repository/auth.repository.ts, 관련 auth 단위·통합 테스트. 운영 DB constraint 이름이 실제와 다르면 repository의 충돌 분류도 호환 범위로 보완한다.

프런트 재시도 계약 (제안)

재시도 복구는 인증에 성공했고 가입을 계속하려면 access token이 필요하다. 따라서 HTTP 409 오류만 반환하면 프런트가 다음 POST /api/users/join을 인증할 수 없어 로그인 루프가 된다. HTTP 200을 유지하면서 최상위 응답 code를 구분한다.

POST /api/auth/:provider/login 응답 코드
조건HTTP / code프런트 동작
새 계정 생성 또는 일반 로그인200 / successisRegistered로 홈 또는 가입 화면 이동
같은 identity의 PENDING 계정 재발견·복구200 / AUTH_SIGNUP_RESUME_REQUIRED새 tokens 저장 후 가입 화면으로 이동, 재시도 안내 표시

같은 이메일, 다른 identity200 / successisRegistered로 새 계정 가입 화면 이동

응답 예시: { status: "OK", code: "AUTH_SIGNUP_RESUME_REQUIRED", result: { isRegistered: false, userId: 7, tokens: { ... } } }. 이 코드는 HTTP 오류가 아니라 프런트 분기·관측용의 복구 결과 코드이다.

최신 main 구조 반영: 재승인 대상

최신 main은 API·core·infrastructure를 분리했다. 따라서 core의 로그인 결과는 HTTP code가 아닌 의미 상태(NEW, RESUME, REGISTERED)만 반환하고, API controller가 RESUME을 AUTH_SIGNUP_RESUME_REQUIRED로 매핑한다.

가입 완결성 판정은 core policy로 옮긴다. infrastructure repository는 nickname/job/address/동의 snapshot을 조회하고 role IS NULL CAS 갱신만 수행한다. 이 변경은 fallback의 사용자 동작은 유지하면서 main의 의존성 방향을 보존한다.

검증 계획과 잔여 위험

  • unit: 이메일 중복 후 같은 identity 발견 → 성공·동일 userId·isRegistered: false.
  • unit: 이메일 중복 후 다른 identity → provider별 별도 계정 생성.
  • unit: social identity 중복 경로도 같은 helper로 성공.
  • unit: null role + nickname/job/address/활성 필수 동의 중 하나라도 누락 → CAS로 PENDING 정규화 후 가입 가능.
  • unit: null role + nickname/job/address/모든 활성 필수 동의 충족 → CAS로 USER 정규화 후 가입 완료 경로 유지.
  • integration 권장: 같은 identity의 동시 로그인 두 건이 모두 성공하고 users/social_account가 각 1건.
  • 운영 확인: null role 표본의 프로필·동의 완결성, social account의 실제 unique constraint 이름, provider 분리·T006·U017 응답 코드를 읽기 전용으로 점검.
