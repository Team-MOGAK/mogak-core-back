리뷰 범위와 의도

README가 약속한 NestJS API의 로컬 검증 가능성, JWT 기반 인증, 게시글 이미지 처리, 전역 요청 제한이 현재 코드와 작업 트리에서 성립하는지 확인했다. 제품 정책의 미확정 사항은 결함으로 단정하지 않았다.

실제 구현 흐름과 경계

JWT 경계
JWT_SECRET 또는 JWT_SECRET_KEY 문자열을 그대로 HS256 키로 사용한다.
요청 제한 경계
각 프로세스가 메모리의 BoundedThrottlerStorage를 독립 소유한다.
빌드 경계
tsconfig.json에는 include/exclude가 없어, 루트의 모든 TypeScript 파일이 typecheck 대상이 된다.

R-001 · openBlocker refactor/test/database/setup.ts:1와 test/database/setup.ts:1가 같은 전역 선언을 제공한다. 루트 tsconfig.json이 범위를 제한하지 않아 pnpm typecheck는 TS2451로 실패한다. 현재 품질 게이트가 깨져 새 타입 회귀를 신뢰성 있게 탐지할 수 없다. 중첩 복사본 refactor/를 작업 트리 밖으로 옮기거나, 의도된 별도 프로젝트라면 루트 TypeScript 검사·Docker build context에서 명시적으로 제외한다.
R-002 · openBlocker apps/api/src/api/posts/presentation/controller/post.controller.ts:67-78는 파일을 먼저 업로드하지만 반환된 storageKey를 PostService.createPost에 전달하지 않는다. 그 서비스와 PostRepository.createForOccurrence에는 post_img를 생성하는 입력도 없다. 저장소 어댑터를 활성화하면 성공 응답 뒤 이미지가 조회되지 않고 고아 파일이 남는다. 게시글·이미지 메타데이터 저장을 하나의 생성 유스케이스로 연결하고, DB 실패 시 업로드 보상 삭제 또는 임시 키 확정 전략을 추가한다. 생성·조회·실패 보상 통합 테스트를 둔다.
R-003 · openBlocker apps/api/src/infrastructure/auth/service/token.service.ts:31-34는 빈 문자열이나 짧은 JWT_SECRET을 허용한다. README의 “32자 이상”은 런타임에서 강제되지 않으므로, 배포 오설정 시 예측 가능한 HS256 키로 토큰 위조 위험이 생긴다. 기동 시 secret 존재·최소 바이트 길이(최소 32)를 검증하고, 빈 JWT_SECRET일 때만 legacy 키로 대체하지 않도록 명시한다. 실패 기동 테스트를 추가한다.
R-004 · openNon-blocking risk apps/api/src/composition/app.module.ts:19-22의 rate limit 저장소는 인스턴스 로컬이다. Cloud Run 등 다중 인스턴스 배포에서는 클라이언트가 인스턴스별로 제한을 다시 받으므로, “분당 300회”가 전역 남용 방어가 아니다. 전역 제한이 요구사항이면 Redis 등 공유 저장소 또는 인프라 레벨 WAF/rate limit을 사용한다. 인스턴스별 제한이 의도라면 운영 문서와 경보 기준에 그 한계를 기록한다.
R-005 · openNon-blocking risk 작업 트리의 추적되지 않은 refactor/는 별도 package.json, 소스, 테스트와 산출물을 포함한다. .dockerignore는 이를 제외하지 않아 Docker build context에 불필요한 복사본이 들어가며, R-001의 직접 원인이기도 하다. 이 디렉터리의 소유·목적을 확정하고, 별도 저장소/워크트리로 분리하거나 명시적으로 ignore·exclude한다.
R-006 · openBlocker (저장소 활성화 전) apps/api/src/api/common/http/imageUpload.options.ts:9-17는 클라이언트가 선언한 file.mimetype만 신뢰한다. FilesInterceptor는 메모리에 최대 5개의 5 MiB 파일을 받는다. 실제 이미지 형식 검증·재인코딩 없이 공개 가능한 저장소에 연결하면 위장 파일 업로드와 인스턴스 메모리 고갈 경로가 된다. 바이트 시그니처 검증과 안전한 이미지 디코드·재인코딩을 저장소 경계에 추가하고, 요청당 전체 크기·동시 업로드 제한을 인프라와 애플리케이션에서 함께 적용한다.
R-007 · openNon-blocking risk cloudbuild.yaml은 Docker build만 실행한다. Dockerfile의 pnpm build는 통과하지만 독립 pnpm typecheck가 실패하는 현재 상태를 차단하지 못한다. lint·단위 테스트·DB 통합 테스트도 CI gate에 없다. Docker image build 전에 format, lint, typecheck, 단위·HTTP 계약 테스트를 별도 CI 단계로 만들고, PostgreSQL 서비스가 있는 DB 통합 테스트를 보호 브랜치 gate로 추가한다.
R-008 · openBlocker (신규 DB 배포) cloudbuild.yaml은 이미지만 build/push하고, Dockerfile의 런타임 명령은 node dist/main.js뿐이다. pnpm db:migrate를 운영 DB에 실행하는 Job·release 단계가 저장소에 없다. 새 DB에는 schema와 필수 공개 metadata seed가 없어 로그인 이후 가입·도메인 API가 동작하지 않는다. 애플리케이션 rollout 전에 단일 실행되는 migration Job을 만들고, DB backup·실행자 권한·실패 중단·Drizzle journal 검증을 release 절차에 포함한다. 앱 컨테이너가 기동할 때마다 migration을 실행하지 않는다.
R-009 · openBlocker (장애 감지) apps/api/src/api/health/health.controller.ts는 DB 연결·간단한 query·외부 필수 의존성을 확인하지 않고 항상 200을 반환한다. Pool도 lazy이므로 DB URL 오설정이나 DB 장애 시 Cloud Run은 ready로 판단하고 요청만 5xx가 된다. liveness는 가볍게 유지하되 readiness endpoint 또는 startup probe에서 DB 연결과 최소 query를 확인한다. Cloud Run의 traffic 전환·알림은 readiness 실패와 API 5xx를 기준으로 설정한다.

검증 증거와 공백

  • pnpm build: 통과.
  • pnpm typecheck: 실패 — R-001의 TS2451 재선언 오류.
  • pnpm test --runInBand: 이 샌드박스에서는 HTTP 테스트의 임시 포트 bind가 EPERM으로 거부됐다. 코드 실패로 판정하지 않았으며, 포트 허용 CI/로컬에서 재실행이 필요하다.
  • pnpm lint, DB 통합 테스트, 배포 환경의 다중 인스턴스 rate limit: 앞 단계 실패 또는 환경 제약으로 이번 리뷰에서 완료 증거가 없다.

잔여 위험

일정·실행 처리에는 단위 테스트가 비교적 많지만, 현재 DB 통합 테스트와 HTTP 계약 테스트를 이 환경에서 통과시킨 최신 증거가 없다. 특히 동시 PATCH/삭제와 실제 PostgreSQL 제약은 별도 확인이 필요하다. trust proxy=1은 현재 Cloud Run 프록시 토폴로지와 공개 진입점 제약을 운영 환경에서 확인해야 한다. 그렇지 않으면 IP 기반 rate limit을 우회할 여지가 있다.

코드 품질 평가

계층(API/core/infrastructure)과 port 분리, strict TypeScript, Zod 요청 검증, 도메인 오류 매핑, 일정 규칙 단위 테스트는 좋은 기반이다. 다만 기능 경계가 실제 영속 경로까지 닫히지 않은 이미지 업로드(R-002), 깨진 typecheck(R-001), CI 품질 게이트 부재(R-007) 때문에 현재 품질 상태는 구조는 양호하지만 배포 신뢰도는 낮음으로 평가한다.

운영 전 기능 완결성

핵심 텍스트 기반 도메인(가입, 모각·조각, 실행, 게시글·댓글·좋아요·팔로우)은 구현되어 있다. 다만 Storage adapter가 의도적으로 disabled라 프로필 이미지 변경과 실제 게시글 이미지 첨부는 현재 항상 실패한다. Apple·Google 실제 client ID와 Kakao/Google/Apple 외부 egress도 운영 환경에서 준비·검증해야 소셜 가입이 기능적으로 열린다.
